# [Orchestrator-Worker로 AI 팀 만들어보기 (Supervisor & Sub-agent)]

## 1. 에이전트 개발 관점의 핵심 아키텍처 분석

### 1.1 기존 Orchestrator-Worker 패턴과 Supervisor 패턴의 아키텍처적 패러다임 차이 및 진화
에이전트 팀을 구성하는 오케스트레이션 패러다임은 고정된 일방향 배분 방식에서 자율적이고 동적인 양방향 소통 구조로 진화해 왔습니다. 기존의 Orchestrator-Worker 패턴과 현대적인 Supervisor 패턴은 제어 주권과 컨텍스트 전이 관점에서 다음과 같은 본질적인 구조적 차이를 보입니다.
*   **Worker 타입과 지능의 깊이**: 기존의 Orchestrator-Worker 패턴에서는 하부 워커(Worker)들이 스스로 도구를 소유하지 못하고 단순히 상위 오케스트레이터가 가공해서 넘겨준 프롬프트 페이로드에 의존해 일회성 텍스트를 디코딩하는 단순 LLM 호출기에 가까웠습니다. 반면 Supervisor 패턴 하에서의 서브 에이전트(Sub-agent)들은 자신만의 독자적인 도구셋(Tools)과 특화 시스템 지침을 탑재하고, 내부적으로 도구 호출, 검증, 자가 수정을 완수하는 독립된 자율 ReAct 루프를 전개합니다.
*   **소통 방식 및 위임의 동적 자율성**: 기존 패턴이 상위 에이전트의 Send API 호출을 통해 고정된 하위 태스크를 일방적으로 분할 배정하고 취합하는 정적 조립 라인(Assembly Line) 형태였다면, Supervisor 패턴은 상위 에이전트가 하위 에이전트를 하나의 '고수준 도구(High-level Tool)'로 인식하여 필요에 따라 동적으로 위임하고 결과를 보고받는 완벽한 양방향 소통 아키텍처를 가집니다.
*   **맥락 전달과 조율성**: 기존의 정적 워크플로우에서는 컨텍스트가 고정된 페이로드 구조에만 갇혀 있어 하위 단계에서 유연한 목표 수정이 불가능했으나, Supervisor 패턴에서는 `ToolRuntime`을 매개로 하여 상위 Supervisor의 전체 대화 역사와 거시적 작업 의도를 하위 에이전트까지 손실 없이 흘려보내 최적의 정렬(Alignment) 상태를 유지합니다.

### 1.2 3단 계층(3-Tier Hierarchy) 구조의 역할 분담과 고수준 도구 추상화
본 아키텍처는 에이전트 시스템 내부의 결합도를 극도로 낮추기 위해 **'3단 계층(3-Tier Hierarchy)'** 구조를 정립합니다. 최상위 오케스트레이션 레이어인 Supervisor와 중간 실행 에이전트 레이어, 그리고 물리적 도구들이 연동되는 최하위 툴 레이어로 역할을 명확히 격리 분리합니다.
*   **최상위 레이어 (Supervisor Agent)**: 사용자와 직접 마주하며, 거시적인 미션을 분석하여 전체적인 마일스톤 계획을 수립합니다. 하위 에이전트들을 각각 `research_topic`, `write_section`, `run_code`라는 고수준 도구로 래핑하여 들고 있으며, 이들이 수확해 반환한 고압축 결과물을 종합하는 최종 편집장 역할을 수행합니다.
*   **하부 전문가 레이어 (Sub-agents)**:
    *   **Research Agent**: EXA 시맨틱 웹 검색 및 실시간 뉴스 탐색 API를 독점적으로 다루며, 질문에 부합하는 사실 관계와 신뢰할 수 있는 출처 정보를 고해상도로 수집합니다.
    *   **Writer Agent**: 수집된 연구 자료에 기반하여 보고서 단락을 마크다운 양식으로 집필하고, 내부 로컬 도구인 `validate_markdown_section`을 활용해 단어 수 및 타이틀 무결성을 자율 검증 및 수정한 뒤 최종 완성본을 반환합니다.
    *   **Code Agent**: E2B 가상 MicroVM 터미널 도구를 독점 활용하여 데이터 분석, 정량 연산 및 시각화를 위한 코드를 스스로 빌드하고 실행 샌드박스로부터 피드백 스트림을 수집합니다.
*   **고수준 도구 추상화(Tool Wrapping)의 인프라적 가치**: Supervisor는 EXA API의 세부 파라미터 규격이나 E2B 샌드박스 보안 프로토콜 같은 로우레벨 도구를 직접 인지하지 않습니다. 오직 '리서치를 수행한다' 또는 '코드를 구동한다'와 같은 고수준 추상화 인터페이스 도구의 Docstring 명세만 판독하여 적절한 서브 에이전트에게 제어권을 신속하게 분기 이양합니다.

### 1.3 ToolRuntime을 통한 전역 맥락 전이(Context Propagation) 원리
기본적인 도구 호출 환경에서 하위 에이전트들은 상위 에이전트가 도구 인자로 매핑해 준 단순 텍스트 쿼리만을 입력받기 때문에, "대상 독자는 실무 개발자여야 한다"거나 "격식 있는 비즈니스 톤앤매너를 유지하라"와 같은 전역 제약조건을 인지하지 못해 결과물의 정합성이 붕괴되는 문제가 다발합니다.
*   **상태 공간 가상 투영**: `ToolRuntime` 인프라를 활용하면 하위 에이전트가 기동될 때 상위 Supervisor의 전역 활성 메시지 텐서(`runtime.state["messages"]`)에 동적으로 액세스할 수 있는 메모리 브리지가 개설됩니다.
*   **맥락 병입(Enriched Prompting)**: 하부 도구 함수 내부에서는 사용자가 최초에 하달한 휴먼 메시지를 역추적하여, "이 작업은 엔지니어를 타겟으로 작성되어야 합니다"와 같은 시스템 컨텍스트 메타데이터를 하위 에이전트의 프롬프트 전면에 동적으로 병입(In-Context Injection)시킵니다. 이로써 하부 에이전트는 독립된 메모리 격리 공간을 유지하면서도 상위 수준의 거시적 제약을 완벽히 준수한 맞춤형 결과물을 생성하게 됩니다.

### 1.4 HumanInTheLoopMiddleware를 활용한 동적 승인 거버넌스 및 상태 영속화
비결정론적인 인공지능이 실제 운영체제 가상 디렉토리 상에서 파일을 갱신하거나 타 시스템 API를 강제 기동하는 행위는 심각한 데이터 파괴와 인프라 무단 조작 위협을 동반합니다. 시스템의 물리적 안전과 거버넌스를 완벽히 수호하기 위해 `HumanInTheLoopMiddleware` 기반의 가드레일이 장착됩니다.
*   **인터럽트(Interrupt)와 제어권 반환**: 특정 고위험 도구(예: `e2b_code_interpreter` 코드 실행 등) 호출 명령이 디코딩되는 즉시, 그래프 엔진은 노드의 연산을 일시 중단(Suspend)시키고 제어권을 외부 휴먼 조작자에게 반환합니다.
*   **메모리 체크포인터(InMemorySaver/Durable Saver)의 개입**: 가동 중이던 모든 노드의 내부 메시지 상태 및 변수 테이블은 체크포인터 스냅샷에 실시간 직렬화(Serialize)되어 영속 기록됩니다. 사용자가 터미널이나 UI 콘솔을 통해 상태를 모니터링한 뒤 'Approve(승인)', 'Edit(수정)', 또는 'Reject(거부)' 등의 결정을 보낼 때까지 에이전트 추론 루프는 안전하게 대기 상태(Pending)를 유지합니다. 승인 신호가 전달되면, 체크포인터로부터 박제된 상태가 즉각 메모리로 언마운트 복원되어 실패 없는 실행의 영속성(Durable Execution)을 유지하게 됩니다.

## 2. 데이터 흐름 및 컨텍스트/토큰 관리 구조

### 2.1 Supervisor 패턴 기반 양방향 협업 에이전트의 종단간(End-to-End) 데이터 흐름도
아래 아키텍처 흐름도는 사용자의 복합 지시 사항이 최상위 Supervisor에 접수되어, 가용 서브 에이전트 도구를 분류 판독하고, `ToolRuntime`을 통해 맥락을 전수하며, `Human-in-the-loop` 동적 거버넌스를 관통한 뒤 최종 무결 보고서로 수렴 합산되는 텐서 데이터의 정사 흐름을 묘사합니다.

```
[사용자 복합 명령 인입 (거시 목표 하달)]
  - "Scaling Laws 연구 동향 리서치 및 2025/2026 모델 비교 코드 분석 후 보고서 작성"
       │
       ▼
[Supervisor Agent 기동 (최상위 컨텍스트 수립)]
  - System Prompt + User Message + High-level Tools Catalog
       │
       ▼ [태스크 세분 분석 및 첫 번째 위임 결정]
[research_topic_with_context 고수준 도구 호출]
       │
       ├─────────────────────────────────────────┐
       │ [ToolRuntime 작동: 전역 메시지 텐서 분석] │
       ▼                                         ▼
[Research Agent 기동 (Sub-context 형성)]        [EXA API 시맨틱 검색]
  - system_prompt + enriched_context            - search_web / search_news
       │                                         │
       ▼                                         ▼
[Research 완료 및 고압축 요약 반환] ◄───────────────┘
  - 출처 URL 및 연도 포함 핵심 팩트 텐서 반환 (수천 토큰 수준)
       │
       ▼ [두 번째 위임 결정: 수치 정량화 및 시각화]
[run_code_with_context 고수준 도구 호출]
       │
       ├─────────────────────────────────────────┐
       │ [Human-in-the-loop Middleware 인터럽트] │
       ▼                                         ▼
[Checkpointer 상태 영속화 및 대기]             [인적 승인 워크플로우 (Approve)]

       │                                         │
       ▼ ◄───────────────────────────────────────┘
[Code Agent 기동 (E2B 샌드박스 VM 가동)]
  - matplotlib 차트 생성 및 csv 파일 오프 로딩 분석
       │
       ▼ [세 번째 위임 결정: 최종 마크다운 집필]
[write_section_with_context 고수준 도구 호출]
  - Writer Agent -> validate_markdown_section 무결성 체크 루프 가동
       │
       ▼
[Supervisor 최종 응답 빌드 및 사용자 반환] ──► [END]
```

### 2.2 계층적 캡슐화(Encapsulation)를 통한 컨텍스트 폭주 방지와 VRAM 최적화
실제 프로덕션 비즈니스 환경에서 단일 에이전트 혹은 조밀하지 않은 멀티 에이전트 시스템이 웹 검색 덤프와 코드 에러 스택을 모두 하나의 상태 메모리(`MessagesState`)에 누적 연접하는 구조를 고수하면, 컨텍스트가 기하급수적으로 비대화되어 메모리 고갈과 도구 오작동을 초래하는 '컨텍스트 부패' 장벽에 마주하게 됩니다.
*   **상태 독립 격리(No-Share Context Partitioning)**:
    Supervisor 아키텍처는 하위 에이전트들이 구동되는 콘텍스트 공간을 메인 상태 공간과 물리적으로 차단 분리하는 '계층적 캡슐화' 규칙을 집행합니다. Research Agent가 EXA API를 수차례 난사하여 획득한 수만 자의 원시 텍스트 로우 정보나, Code Agent가 pandas 데이터프레임을 주무르기 위해 샌드박스로부터 뱉어낸 무거운 중간 콘솔 로그들은 오직 해당 하위 에이전트 내부의 로컬 `Sub-Context` 윈도우 안에서만 소모되고 기각됩니다.
*   **고압축 텐서 반환 수식**:
    하부 작업을 완수한 에이전트는 자신이 처리한 방대한 로우 콘텍스트 $C_{\text{raw}}$를 최종 LLM 디코더에 노출시키지 않고, 핵심 골자만을 발라낸 고순도 정보 메타 텐서 $\tilde{T}$($1,000 \sim 2,000$ 토큰 수준)로 고속 축축 요약(Summarize & Compress)합니다.
    $$\tilde{T} = \text{Compress}(C_{\text{raw}} \mid \text{System\_Manifesto})$$
    이 축약된 메타 텐서만이 `research_topic` 도구의 출력 스트림 형태로 상위 Supervisor의 전역 콘텍스트 창으로 수입 합산됩니다. 이에 따라 상위 오케스트레이터의 입력 시퀀스 팽창 부하는 상수 범위 내로 극단 억제되어, 셀프 어텐션 맵의 VRAM 계산 복잡도인 $O(T^2)$를 기하학적으로 최적화하며 전체 가동 비용을 $90\%$ 이상 절감시키는 놀라운 인프라 효율성을 선사합니다.

## 3. 에이전트 워크플로우 구현 및 API/설정 매핑 분석

### 3.1 LangGraph 기반 Supervisor & 3 Sub-agents 협업 마스터 소스코드
다음 파이썬 스크립트는 실시간 EXA 웹 검색, E2B 격리 샌드박스, `ToolRuntime` 컨텍스트 공유 및 `HumanInTheLoop` 가드레일이 하나의 통합된 백엔드 서비스 아키텍처 상에서 유기적으로 결합하여 동적 계획 수립 및 자율 계획서 수정을 완수하도록 설계된 프로덕션 코드 명세입니다.

```python
import os
import re
from typing import Dict, Any, List, Literal, Tuple
from dotenv import load_dotenv

# LangChain 및 LangGraph 핵심 패키지 임포트
from langchain_openai import ChatOpenAI
from langchain_core.messages import SystemMessage, HumanMessage, AIMessage, BaseMessage
from langchain_core.tools import tool
from langchain.tools import ToolRuntime
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.checkpoint.memory import InMemorySaver
from exa_py import Exa
from e2b_code_interpreter import Sandbox

# 1. 인프라 환경 변수 초기화 및 검증
load_dotenv()
os.environ["LANGSMITH_TRACING"] = "true"
os.environ["LANGSMITH_PROJECT"] = "supervisor-system-integration"

# API 인증 토큰 안전 획득
OPENAI_KEY = os.getenv("OPENAI_API_KEY", "MOCK_OPENAI_KEY")
EXA_KEY = os.getenv("EXA_API_KEY", "MOCK_EXA_KEY")
E2B_KEY = os.getenv("E2B_API_KEY", "MOCK_E2B_KEY")

# =====================================================================
# [인프라 레이어] 로우레벨 외부 API 통합 도구 설계 (EXA & E2B)
# =====================================================================
exa_client = Exa(api_key=EXA_KEY)
# 보안 호스트 가속 및 자원 회수 보호를 위해 Ephemeral VM 시동
sandbox = Sandbox.create(timeout=600)

@tool
def search_web(query: str, num_results: int = 3) -> str:
    # EXA API를 시동하여 최신 기술 트렌드, 연구 논문, 공식 웹 문서를 시맨틱 검색합니다.
    try:
        results = exa_client.search_and_contents(
            query=query,
            type="auto",
            num_results=num_results,
            text={"max_characters": 1500},
            highlights=True
        )
        if not results.results:
            return f"'{{query}}'에 부합하는 시맨틱 정보를 수집하지 못했습니다."
            
        output = []
        for i, r in enumerate(results.results, 1):
            output.append(f"{{i}}. 제목: {{r.title}}")
            output.append(f"   출처 URL: {{r.url}}")
            if r.highlights:
                output.append(f"   핵심 요약: {{' '.join(r.highlights)}}")
            output.append("")
        return "\n".join(output)
    except Exception as e:
        return f"EXA 검색 엔진 내부 통신 오류: {{str(e)}}"

@tool
def validate_markdown_section(section_name: str, markdown: str) -> dict:
    # 작성된 단락의 마크다운 정합성 및 품질 메트릭을 정량 검증합니다.
    issues = []
    word_tokens = re.findall(r"\b\w+\b", markdown)
    wc = len(word_tokens)
    
    if wc < 50:
        issues.append(f"단어 수 부족 경고: {{wc}}단어로 작성됨 (최소 50단어 요망)")
    if wc > 400:
        issues.append(f"콘텐츠 한계 초과: {{wc}}단어로 작성됨 (최대 400단어로 제한)")
    if "##" not in markdown[:100]:
        issues.append("마크다운 헤더 미준수: 상단 100자 이내에 '## {섹션명}' 포맷이 생략됨")
        
    return {"ok": len(issues) == 0, "word_count": wc, "issues": issues}

@tool
def e2b_code_interpreter(code: str) -> str:
    # 격리된 E2B 클라우드 샌드박스 가상 환경 터미널에서 파이썬 코드를 실행하고 결과를 가져옵니다.
    try:
        execution = sandbox.run_code(code)
        result_parts = []
        if execution.text:
            result_parts.append(execution.text)
        if execution.logs.stdout:
            stdout_stream = "".join(execution.logs.stdout).strip()
            if stdout_stream:
                result_parts.append(stdout_stream)
        if execution.logs.stderr:
            result_parts.append(f"[stderr] {{''.join(execution.logs.stderr).strip()}}")
        if execution.error:
            result_parts.append(f"Runtime Error: {{execution.error.name}} - {{execution.error.value}}")
            
        return "\n".join(result_parts) if result_parts else "스크립트가 성공적으로 수행되었습니다."
    except Exception as e:
        return f"샌드박스 내부 물리 런타임 오류: {{str(e)}}"
```

### 3.2 핵심 아키텍처 제어 파라미터 매핑 분석
위 아키텍처 구현에서 프로덕션 구동 시 에이전트 판단 신뢰성을 좌우하는 지배적인 설정 매개변수들의 역할은 다음과 같습니다.
*   **`ToolRuntime`과 비결정적 이중 대화 바인딩**: `ToolRuntime`은 상위 Supervisor 그래프의 실행 컨텍스트 메모리에 대한 가상 가교(Bridge)를 생성합니다. 하부 도구들이 구동될 때 이 런타임 환경에서 `original_human_msg`를 추출해 Sub-context에 인입시키지 않으면, 하위 에이전트들이 "AI 엔지니어를 설득할 수 있도록 코드 스니펫 위주로 서술하라"는 거시적 목표 지침을 영구 상실하여 지극히 일반적이고 조악한 답변을 도출하는 정합성 탈조를 겪게 됩니다.
*   **`checkpointer=InMemorySaver()`를 통한 수명 주기 영속 제어**:
    `HumanInTheLoopMiddleware`가 `interrupt_on` 지시를 받아 `e2b_code_interpreter` 직전 단계에서 런타임 제어권을 중지시킬 때, 체크포인터는 현재의 그래프 상태 객체를 직렬화하여 상태 테이블에 완전히 박제 수용합니다. 이 장치가 배제되면 런타임 엔진은 일시정지하는 즉시 이전까지 `research_topic`에서 기껏 비싼 토큰 비용을 지불하며 수집해 보존 중이던 상태 메시지 리스트 정보 전체를 가상 메모리 스택에서 유실하는 사태가 벌어집니다. 따라서 영속 체크포인터 세션을 연동하여 예외 디버깅과 동적 거버넌스를 완수해야 합니다.

## 4. 에이전트 구조적 메커니즘 자가 진단

### [질문 1]
`ToolRuntime`을 활용해 상위 Supervisor의 전역 메시지 이력(`runtime.state["messages"]`)을 하위 서브 에이전트에게 전수 주입할 때, 대화 턴이 장기 연쇄화됨에 따라 전역 메시지가 하부 캡슐화 메모리 영역까지 무단 중복 적재되어 입력 토큰 팽창 및 VRAM 폭주가 가속화되는 메모리 누출 병목이 발생합니다. 이 현상을 정량적으로 증명하고, 이를 원천 제어하기 위한 **'선택적 메시지 솎아내기(Selective Message Pruning)'** 수식과 메모리 리듀서 필터를 설계하십시오.

*   **정량적 증명**:
    상위 에이전트의 대화 턴 수를 $N$, 매 턴 발생하는 평균 메시지 토큰 길이를 $T_{\text{msg}}$라 하고, 하위 에이전트 호출 횟수를 $K$라 가정합니다. 만약 아무런 정화 필터 없이 `ToolRuntime`을 통해 상위 전역 메시지 풀 전체를 하위 서브 에이전트의 $i$번째 호출 시점에 투과 연접시키면, 하부 에이전트가 처리해야 하는 입력 토큰 크기 $I_i$는 다음과 같이 순차 가중 팽창합니다:
    $$I_i = T_{\text{system}} + T_{\text{sub\_instructions}} + \sum_{j=1}^{N} T_{\text{msg}, j}$$
    이로 인해 매 $K$번의 하위 호출마다 중복 프리필(Prefill) 토큰 연산 부하가 $O(K \cdot N^2 \cdot T_{\text{msg}}^2)$의 기하급수적 제곱 팽창 곡선을 타격하게 되며, 이는 트랜스포머 디코더 셀프 어텐션의 VRAM 공간을 즉각 고갈시켜 서비스 타임아웃 예외를 초래합니다.
*   **선택적 메시지 솎아내기(Selective Message Pruning) 설계 수식**:
    이를 완화하기 위해 하위 컨텍스트 인입 시점에 다음과 같은 의미론적 유사도 기반의 한계 슬라이딩 윈도우 마진 필터 수식 $\mathcal{F}$를 구현합니다:
    $$\mathcal{F}(\mathbf{M}_{\text{global}}) = \{ m \in \mathbf{M}_{\text{global}} \mid \text{CosineSim}(\mathbf{Vec}(m), \mathbf{Vec}(q_{\text{current}})) \ge \tau \ \vee \ \text{Type}(m) = \text{System} \}$$
    여기서 $\tau$는 최소 의미적 연관 마진 스레스홀드(통상 $0.75$)이며, $\mathbf{Vec}$는 임베딩 벡터입니다. 기저 LLM 프롬프트에 system 프로파일 메시지와 현재 당면 쿼리 $q_{\text{current}}$와 수학적 코사인 유사도 마진이 $\tau$ 이상인 유효 과거 힌트 메시지만을 슬라이딩 병입 연쇄시킵니다. 그리고 나머지는 물리 소멸(Eviction) 처리함으로써, $I_i$의 연산 비용 상한을 상수의 공간 범위 $O(C)$ 내로 구속 동결하여 VRAM 사용량을 완전히 제어해 냅니다.

### [질문 2]
`HumanInTheLoopMiddleware` 기동 시, 상태 일시 중단(Interrupt) 및 실행 재개(Resume)가 진행되는 내부 체크포인팅 과정에서 그래프 상태(State)가 메모리 상에서 어떻게 이진 데이터로 직렬화(Serialization)되는지 백엔드 시스템 관점에서 해설하고, 네트워크 단절이나 물리 디스크 충돌 시 영속 파일 세션 정보가 무단 부패(File Corruption)되는 위협을 격리 방어하기 위한 **'이중 분산 합의(Durable State Consensus) 가드레일'** 인프라 설계 방안을 수립하십시오.

*   **상태 직렬화 메커니즘**:
    LangGraph 엔진에서 노드가 인터럽트 시점(예: `e2b_code_interpreter` 실행 전)에 다다르면, 현재 스레드 ID(`thread_id`)를 식별자로 삼아 메모리 상에 존재하는 `TypedDict` 상태 데이터(메시지 리스트의 포인터 어레이, 런타임 변수 매트릭스, 이터레이션 카운터 수치 등)를 파이썬의 `pickle` 프로토콜 혹은 JSON 스키마 규격으로 즉시 변환하고 가상 영속 디렉토리에 바이너리 스트림 형태로 Write 디바이스 파일 쓰기를 수행합니다.
*   **이중 분산 합의(Durable State Consensus) 가드레일 설계**:
    로컬 파일 싱크 IO 도중 하드웨어 오류가 유발되면 바이너리 꼬리가 잘려나가는 상태 부패로 인해 영구적인 복구 불능 상태에 봉착합니다. 이를 원천 격리 차단하기 위해 다음과 같이 2단계 다중 가드 가드레일을 수립해야 합니다:
    1.  **쓰기-검증-이동(Write-Verify-Commit) 원자성 수호**: 상태 스냅샷을 곧바로 최종 체크포인트 경로에 기재하지 않고, 임시 격리 디렉토리에 우선 임시 쓰기(`.tmp` 확장자 마운트)를 전개한 뒤, 정상 체크섬(MD5 / SHA-256) 데이터 해시 대조 검증을 수행하여 손상이 없음이 규명된 시점에 한해서만 POSIX 원자적 시스템 호출인 `rename()` 명령을 활용해 마스터 체크포인트 파일로 동기 대치(atomic commit) 처리를 수행합니다.
    2.  **분산 WAL(Write-Ahead Logging) 체계 연동**: 상태 전이 정보 자체를 이벤트 로그 형태로 분산 SQLite 데이터베이스나 분산 영속 원격 인프라(Redis / PostgreSQL 클러스터) 상에 트랜잭션 수립(Write-Ahead Log) 후 저장하여, 특정 스토리지 하드웨어가 파괴되더라도 타 노드의 레플리카 덤프로부터 정상 세션을 지연 없이 재인양 복원하는 엔터프라이즈급 탄력 신뢰성을 확보합니다.

### [질문 3]
하위 에이전트(예: Code Agent) 내부의 자율 개선 ReAct 루프가 불량 코드 컴파일로 인해 무한 에러 디버깅 시도에 빠져 자원을 무한 소모하는 **'무한 루프 데드락(Infinite Loop Deadlock)'** 장애가 일어날 때, 이 시스템적 지연이 상위 Supervisor에게 동기식으로 전파되어 전체 워크플로우가 영구 중단(Hang)되는 문제를 규제해야 합니다. 이를 시스템 엔지니어링 관점에서 무력화하기 위한 **'시간 한계(Timeout SLA) 설정 정책'**과 **'단계별 예외 롤백(Exception Rollback) 엣지 회로'** 설계 구조를 구체적으로 수립 논술하시오.

*   **시간 한계(Timeout SLA) 설정 정책**:
    하부 에이전트의 오케스트레이션 정의 단계에서 독립적인 `thread_limit` 혹은 `run_limit` 타이머를 강제 연동합니다. 예를 들어, Code Agent의 런타임 수명 주기를 최대 60초 이내로 SLA 강제 규율하고, 이 타임아웃 임계치에 근접하도록 결과를 회수하지 못할 경우, 백엔드 오케스트레이터 프레임워크는 즉각 하위 가중치 연산 스레드를 물리 강제 사멸(SIGKILL) 처리하고 상태 전이를 정지시킵니다.
*   **단계별 예외 롤백(Exception Rollback) 엣지 회로**:
    하부 루프 파괴 시 상위 Supervisor까지 폭사 롤백되는 현상을 막기 위해, 고수준 도구 인터페이스(`run_code_reviewed`) 내부를 안전 격리 트랜잭션 블록(`try-except-rollback`) 레이어로 연접 감싸안습니다. 하부에서 물리 예외나 타임아웃 시그널이 방출되면, 도구 노드는 크래시 로그를 위로 던져서 상위 제어 흐름을 무너뜨리는 대신, 다음 예외 복구 회로 프로토콜을 수행합니다:
    1.  현재까지의 `todo.md` 진척 상태 파일과 변수 메모리를 가장 최근 정상 실행 시점의 체크포인트 버퍼($t-1$ 상태)로 리다이렉트 역롤백 전치시킵니다.
    2.  Supervisor에게 "하부 Code Agent가 $N$회차 연산 시도 도중 런타임 타임아웃 장애를 감지했습니다. 수집된 중간 차트 이미지를 유실한 채로 기 획득 팩트 텍스트 정보만으로 요약 보고서를 우회 빌드하십시오"라는 **'명시적 장애 복원 메타 텐서(Degraded Fallback Report)'**를 리턴시킵니다.
    상위 오케스트레이터는 이 폴백 텐서를 판독하여 전체 서비스의 중단(Hang) 없이 안전하고 결정론적인 차선책 정서 답변 단계로 제어 제어선을 리라우팅하여, 어떠한 비결정론적 하부 오류 상황에서도 무결 구동되는 강인한 가용성을 입증 수호할 수 있게 됩니다.
