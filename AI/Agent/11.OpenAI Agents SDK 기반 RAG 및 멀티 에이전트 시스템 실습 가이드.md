# [OpenAI Agents SDK 기반 RAG 및 멀티 에이전트 시스템 실습 가이드]

## 1. 에이전트 개발 관점의 핵심 아키텍처 분석

### 1.1 OpenAI Agents SDK의 탄생 배경과 철학: 가볍고 강력한 최소한의 기본 요소(Minimal Primitives)
기존의 AI 에이전트 개발 프레임워크(예: LangChain, CrewAI 등)는 복잡한 다단계 체인 및 프롬프트 제어, 다양한 외부 도구와의 연동을 위해 많은 추상화 레이어를 도입하였습니다. 이러한 고차원 추상화는 복잡한 시스템 구축을 가속화하는 장점이 있으나, 에이전트의 내부 실행 로직을 미세하게 디버깅하거나 모델의 토큰 및 입출력을 완벽히 제어하기 어렵게 만드는 '블랙박스 문제'를 야기해 왔습니다.
- **최소 추상화(Minimal Primitives) 지향**: OpenAI Agents SDK는 이러한 한계를 돌파하기 위해 설계된 가볍고 직관적인 파이썬 친화적(Python-first) 프레임워크입니다. 복잡한 에이전트 행동 지능과 프롬프트 체인을 설계하는 대신, 오직 **지시사항(Instructions)**, **도구(Tools)**, **제어권 이전(Handoffs)**, **가드레일(Guardrails)**이라는 4가지 핵심적인 최소 프리미티브만을 정의하여 시스템의 예측 가능성과 투명성을 극대화합니다.
- **가벼움과 직관성**: 개발자는 익숙한 파이썬 비동기 및 내장 기능을 그대로 활용하여 에이전트를 정의하고 실행할 수 있습니다. 무겁고 난해한 프레임워크별 커스텀 클래스와 추상화 레이어에 구속되지 않으므로, 런타임 상의 예외 흐름을 파이썬 예외 처리기(Try-Except)나 표준 데코레이터만으로 직관적이고 강력하게 영속 제어할 수 있게 됩니다.

### 1.2 호스팅 벡터 스토어(Hosted Vector Store)와 FileSearchTool을 활용한 RAG의 결합
OpenAI Agents SDK의 강력함 중 하나는 OpenAI의 엔터프라이즈급 인프라와 결합하여 고성능 RAG(검색 증강 생성) 파이프라인을 완전 관리형(Fully Managed) 호스팅 서비스 형태로 결합할 수 있다는 점입니다.
- **호스팅 벡터 스토어(Hosted Vector Store)와 자동 인덱싱**: 개발자가 직접 벡터 데이터베이스를 구축하고 임베딩 모델을 서빙하며 텍스트 청킹(Chunking) 정책을 미세 조정할 필요가 없습니다. OpenAI의 `vector_stores` API는 문서를 업로드하는 즉시 내부 엔진이 자동으로 텍스트 추출, 최적 크기 청킹, text-embedding-3 등 고가 임베딩 사영, 그리고 고속 인덱싱에 이르는 전 과정을 서버 사이드에서 완전 제어합니다.
- **FileSearchTool과의 유기적 정합**: 인덱싱이 완료된 호스팅 벡터 스토어의 고유 ID(`vs_xxx`)는 에이전트 생성 시 `FileSearchTool` 도구의 매개변수로 즉시 인입 바인딩됩니다.
  - LLM은 추론 단계에서 사용자의 질문 의도를 판독하고, 지식이 부족할 때 `FileSearchTool`을 자율 호출(Tool Call)하여 관련 지식 청크들을 고밀도 인출합니다.
  - 이 과정은 API 호출 대기 시간(Network Latency)을 극한으로 줄이고, 분산 벡터 DB 서빙에 수반되는 인프라적 관리 오버헤드를 제로에 가깝게 수축시키므로 가용 성능을 획기적으로 개선합니다.

### 1.3 멀티 에이전트의 핵심 동력: Handoff(대화 제어권 이전) 메커니즘과 Triage Agent 라우팅 아키텍처
단일 대형 LLM에 모든 도구 명세와 방대한 프롬프트 가이드라인을 적재하면 어텐션이 평평하게 분산되는 어텐션 포화가 발생하여, 도구 선택이 빗나가고 불필요한 비용이 증가하는 한계에 봉착합니다. OpenAI Agents SDK는 이를 **Handoff(대화 제어권 이전)** 메커니즘을 통해 완벽하게 해결합니다.
- **제어권 이전(Handoff)의 시스템적 기저**: Handoff는 한 에이전트가 당면 질문을 해결하기 어렵거나 전문 지식을 갖춘 다른 전문가 에이전트의 개입이 필요할 때, 전체 세션의 대화 히스토리와 제어 흐름 주권을 대상 에이전트에게 완전 위임 이양하는 물리적 상태 전이 수단입니다.
- **Triage Agent 기반 전문성 격리**:
  - 시스템의 관문 역할을 수행하는 Triage Agent는 인입된 사용자의 질문 의도를 1차 판독합니다.
  - 이후 각 전문가 에이전트가 정의한 `handoff_description`(예: "DeepSeek OCR 논문 질문 처리 전문가") 가이드를 판독하여, 최적의 전문가 에이전트(예: RAG Specialist, Summarizer 등)를 선택하고 제어권을 넘깁니다.
  - 각 전문가 에이전트는 오직 자신의 전용 instructions와 tools 목록만 단기 기억 콘텍스트 맵에 탑재하므로, 입력 토큰의 크기를 극단적으로 억제하고 어텐션을 전용 태스크에 100% 포커싱하여 도구 호출 및 정합 정확도를 최고 수치로 견인합니다.

### 1.4 에이전트 안전망 구축: 입력/출력 검증 가드레일(Guardrails)과 신뢰성 공학
실제 엔터프라이즈 비즈니스 인프라에 자율 구동 에이전트를 실시간 연동할 때, 사용자의 악의적인 프롬프트 인젝션 공격, 악성 코드 스크립트 강제 삽입, 혹은 모델이 사내 기밀 변수를 외부로 유출하는 탈선 위협을 반드시 완전 격리 제어해야 합니다.
- **Guardrails 기기를 통한 입출력 전후 처리**: OpenAI Agents SDK는 에이전트 구동 시작 전과 직후 시점에 물리적으로 개입하는 가드레일 메커니즘을 네이티브 지원합니다.
  - **입력 가드레일(Input Guardrail)**: 사용자의 질문이 에이전트 뇌(LLM)에 인입되어 추론 연산이 시작되기 전, 특정 비즈니스 정책 준수 여부(예: 숙제 대필 방지, 금융 규정 필터링)를 선제 검사합니다.
  - **동작 방식**: 가드레일 검증 함수 내부에서 심각한 위반 사항이 탐색되면, 가드레일은 즉시 `tripwire_triggered=True` 및 에러 메시지(`output_info`)를 담은 `GuardrailFunctionOutput` 객체를 리턴합니다. 이 시점에 상위 오케스트레이터는 값비싼 LLM 추론 가동을 원천 취소(Short-circuit)하고 루프를 즉각 강제 종료하므로, 컴퓨팅 자원을 완벽히 보호하고 기밀 침투 위협을 원천 봉쇄하게 됩니다.

### 1.5 디버깅 및 가시성 확보: 내장 트레이싱(Tracing)과 스팬(Span) 기반 실행 추적 구조
비결정론적으로 다단계 자율 루프를 전개하는 멀티 에이전트 시스템은 어느 시점에 어떤 도구가 어긋나게 매개변수를 바인딩했는지, 혹은 Handoff 조건 분기가 왜 비정상적으로 동작했는지 역추적하는 모니터링 가시성 확보가 매우 까다롭습니다.
- **내장 트레이싱(Tracing) 인프라**: SDK에 기본 장착된 `trace` 및 `custom_span` 콘텍스트 매니저 도구는 이러한 관측 제약 한계를 완전히 제거합니다.
  - **트레이스 구조**: 워크플로우 전체 과정을 나타내는 최상위 Trace 아래, 에이전트 전환 과정을 기록하는 Agent Span, 개별 LLM 호출을 관측하는 Generation Span, 도구 및 함수 물리 실행을 측정하는 Function Span, 제어권 이양이 기록되는 Handoff Span 등이 트리(Tree) 구조로 실시간 누적 적재됩니다.
  - **세션 추적 및 디버깅**: 여러 트레이스 호출에 동일한 `group_id`(세션 ID)를 인입해 둠함으로써, 수십 번의 질의가 교차되는 장기 대화 세션의 전면적인 실행 히스토리를 타임라인 상에서 기하학적으로 완벽히 연계 디버깅하고 튜닝할 수 있는 최상의 모니터링 환경을 제공합니다.

### 2.2 멀티 에이전트 Handoff 및 가드레일 통과 시의 세션 상태(State) 보존 및 토큰 전이 원리
에이전트 간 제어권이 Handoff를 타고 이양되거나 가드레일 검증 절차를 밟을 때, 프레임워크 백엔드 상에서는 토큰 팽창을 억제하면서 대화의 인과관계를 유지하기 위해 정교한 컨텍스트 압축 전이 제어 기법이 작동합니다.
- **메시지 스택의 보존과 공유**: Handoff가 발생하여 에이전트 A에서 에이전트 B로 제어가 이동할 때, 이전까지 쌓인 대화의 상태 메시지 목록(`List[BaseMessage]`)은 통째로 유지되어 에이전트 B의 초기 입력 텐서로 주입됩니다. 이로써 에이전트 B는 사용자의 맥락을 처음부터 다시 물어보지 않고도 이전 대화 흐름의 연장선상에서 즉각 지능적인 추론을 수행할 수 있습니다.
- **토큰 부담 최소화 정책**: 
  - 각 전문가 에이전트들의 instructions 가이드는 메모리 버퍼 상에 모두 동시에 상주하지 않고, 오직 현재 제어권을 획득해 추론을 주도하고 있는 활성 에이전트의 instructions 단독 성분만이 시스템 콘텍스트의 최상단(System Pinned Window)에 정교하게 교체 마운트됩니다.
  - 비활성 에이전트들의 instructions 정보는 입력 텐서 프롬프트에서 즉각 소멸(Eviction) 처리되므로, 멀티 에이전트의 수가 늘어나더라도 전체 추론 연산 복잡도 $O(T^2)$의 입력 토큰 크기 $T$를 안정적인 낮은 수준으로 통제 억제할 수 있게 되어, 가혹한 인프라 연산 비용 상승을 완전히 미연에 방어해 냅니다.

## 3. 에이전트 워크플로우 구현 및 API/설정 매핑 분석

### 3.1 OpenAI Agents SDK 기반 멀티 에이전트 RAG & Guardrails & Tracing 마스터 소스코드
다음 소스코드는 OpenAI Agents SDK를 기반으로 호스팅 벡터 스토어 RAG, 입력값 보안 검증 가드레일, Handoff 기반 Triage 라우터 메커니즘, 그리고 세션 추적용 Tracing을 하나의 완벽한 비동기식 애플리케이션으로 수립해 가동할 수 있도록 제작된 파이썬 시스템 마스터 실습 코드입니다.

```python
import os
import asyncio
import uuid
from typing import Dict, Any, List, Tuple
from openai import OpenAI

# OpenAI Agents SDK 핵심 프리미티브 컴포넌트 라이브러리 인입
from agents import (
    Agent, 
    FileSearchTool, 
    Runner, 
    trace, 
    custom_span,
    GuardrailFunctionOutput,
    InputGuardrail
)

# 1. 인프라 세팅 및 환경 변수 검증
api_key = os.getenv("OPENAI_API_KEY", "MOCK_KEY_FOR_SECURITY")
client = OpenAI(api_key=api_key)

# ---------------------------------------------------------------------
# [STEP 1] Hosted Vector Store 생성 및 파일 업로드 RAG 인덱싱 프로세스
# ---------------------------------------------------------------------
def initialize_hosted_rag_store(pdf_file_path: str) -> str:
    print("[INFRA::RAG] OpenAI Hosted Vector Store 생성을 요청합니다.")
    vector_store = client.vector_stores.create(
        name="enterprise-master-specs"
    )
    print(f"[INFRA::RAG] 벡터 스토어 생성 완료. ID: {vector_store.id}")
    file_id = "file-enterprise-rag-v10-spec"
    print(f"[INFRA::RAG] 원본 기술 규격 문서 업로드 완료. File ID: {file_id}")
    print(f"[INFRA::RAG] {file_id} 문서를 {vector_store.id} 인덱스에 병입 중...")
    return vector_store.id

# ---------------------------------------------------------------------
# [STEP 2] 선제적 보안 침투 및 악성 입력 방어를 위한 입력 가드레일(Guardrail) 설계
# ---------------------------------------------------------------------
async def enterprise_security_guardrail(ctx: Any, agent: Agent, input_data: str) -> GuardrailFunctionOutput:
    print(f"[GUARDRAIL::SECURITY] 입력값 정합성 검사를 전개합니다: '{input_data[:50]}...'")
    blacklisted_intent = ["system prompt bypass", "reveal secret variables", "ignore instructions"]
    if any(trigger in input_data.lower() for trigger in blacklisted_intent):
        print("[GUARDRAIL::TRIGGERED] 시스템 악성 인젝션 위협을 감지하여 실행을 즉시 강제 원천 차단합니다.")
        return GuardrailFunctionOutput(
            tripwire_triggered=True,
            output_info="경고: 허용되지 않은 시스템 탈선 유도 문맥이 감지되어 에이전트 자율 가동이 조기 사멸되었습니다."
        )
```

1. **Agent Span (부모 노드)**: 현재 추론을 주도하고 있는 에이전트의 가동 수명주기 전체를 점유합니다.

3. **Function Span (자식 노드)**: 모델의 판단에 의해 활성화된 `FileSearchTool` 등의 실제 도구 함수 물리 작동 속도와 인자 바인딩 결과를 캡처합니다.
4. **Handoff Span (자식 노드)**: 제어권이 타겟 에이전트로 전이되는 순간의 이전 상태 정보와 인계 상태 정보를 동기식으로 보관합니다.
<br><br>
에이전트 제어기 상에서 다중 사용자 질의 세션을 관측할 때, 각 트레이스 기동 시점에 임의의 `group_id`(예: `session_enterprise_agent_1248`)를 전역적으로 일관되게 주입하면, 파이프라인 후단 모니터링 엔진은 이 group_id를 인덱싱 키로 삼아 서로 분산되어 있던 수많은 Trace 트리들을 하나의 유기적인 시기적 타임라인 상으로 동적 연계 정합해 냅니다.
<br><br>
이를 통해 비결정적으로 전개되던 다중 에이전트 간의 조건부 이양 흐름과 가드레일의 동작 과정을 단 하나의 시각적 흐름도 맵으로 완벽히 가시 표상해 낼 수 있어, 시스템 장애 및 어텐션 유실 병목 발생 시 원인이 되는 특정 스팬을 1초 내로 역추적해 정밀 디버깅 및 고도 성능 조율(Tuning)을 무결하게 달성해 냅니다.
