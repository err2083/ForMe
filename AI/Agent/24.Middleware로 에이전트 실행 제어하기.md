# Middleware로 에이전트 실행 제어하기

---

## 1. 에이전트 개발 관점의 핵심 아키텍처 분석

### 1.1 Middleware 인터셉터 패턴의 도입과 에이전트 오케스트레이션 제어권 분리

자율형 에이전트 시스템을 엔터프라이즈 환경에서 운영할 때 마주하는 구조적 난제 중 하나는, 비즈니스 추론 논리(LLM의 생각과 도구 선택)와 인프라스트럭처 수준의 통제 논리(로깅, 보안 가드레일, 실행 시간 측정, API 호출 제한, 데이터 변조 방지)가 한 코드베이스 내에 어지럽게 뒤섞여 결합도가 높아지는 현상입니다. 

LangChain 1.0에서 본격적으로 지원하는 **Middleware(미들웨어) 시스템**은 소프트웨어 공학의 **관점 지향 프로그래밍(Aspect-Oriented Programming, AOP)** 및 **인터셉터(Interceptor) 패턴**을 에이전트 런타임에 이식한 코어 아키텍처 컴포넌트입니다. 이는 에이전트가 모델을 호출하거나 도구를 실행하는 물리적인 API 진입 및 진출로를 전방에서 가로채어, 비즈니스 노드 코드를 단 한 줄도 수정하지 않고도 실행 흐름을 통제하고 제어할 수 있는 고도의 디커플링 환경을 제공합니다.

미들웨어가 부재한 전통적인 환경에서는 LLM 호출 실패 시 재시도 로직을 가동하기 위해 개별 노드마다 복잡한 예외 처리 구문을 수없이 반복 작성해야 했습니다. 반면, 미들웨어 아키텍처를 도입하면 에이전트의 중심 실행 루프 외부에서 모든 공통 인프라 요구사항들을 모듈화된 파이프라인으로 격리 수용할 수 있게 됩니다.

### 1.2 모델 및 도구 호출 가로채기(Intercepting) 메커니즘의 물리적 구조

에이전트 제어 미들웨어는 개입하는 생명주기(Lifecycle) 시점에 따라 크게 두 가지의 물리적 가로채기 인터페이스를 형성합니다.

```
+-----------------------------------------------------------------------------------+
|                              Agent Runtime Engine                                 |
+-----------------------------------------------------------------------------------+
       |                                                               |
       | (LLM invoke 트리거)                                            | (Tool invoke 트리거)
       v                                                               v
+------------------------------------+                         +------------------------------------+
| wrap_model_call (ModelRequest)     |                         | wrap_tool_call (ToolCallRequest)   |
|------------------------------------|                         |------------------------------------|
| - LLM 진입 전: 프롬프트 변조/PII 스캔|                         | - 도구 진입 전: 인수 타입 강제 교정 |
| - LLM 진출 후: 응답 로깅 및 캐싱    |                         | - 도구 진출 후: 결과 변환 및 에러 가드|
+------------------------------------+                         +------------------------------------+
       |                                                               |
       v                                                               v
+------------------------------------+                         +------------------------------------+
|      Target LLM Provider API       |                         |      Executable Business Tool      |
+------------------------------------+                         +------------------------------------+
```

*   **`wrap_model_call` (모델 호출 가로채기)**: 에이전트가 상태 정보를 취합하여 LLM 호출(Inference)을 감행하는 직전과 직후 단계에 개입합니다. `ModelRequest` 객체를 통해 전달되는 현재 상태 스택(Messages), 연결 예정인 도구 메타데이터 목록, 그리고 하이퍼파라미터 설정을 판독할 수 있습니다. 개발자는 이 훅을 사용해 모델 호출 전에 악성 프롬프트 인젝션을 사전 차단하는 검증 장치를 가동하거나, 호출이 끝난 뒤 수신된 `ModelResponse`를 검사하여 실시간 캐싱 및 지표 수집을 수행할 수 있습니다.
*   **`wrap_tool_call` (도구 호출 가로채기)**: 에이전트가 도출한 도구 실행 페이로드(Tool Call Metadata)가 실제 파이썬 함수나 데이터베이스 커넥터로 전달되기 직전과 직후에 개입합니다. `ToolCallRequest` 명세를 기반으로 어떤 도구명과 아규먼트 세트가 바인딩되었는지 검증하고, 도구 함수가 연산을 마치고 리턴하는 아웃풋 객체를 캡슐화합니다. 특히 도구 실행 도중 발생하는 물리적 예외(Connection Timeout, DB Deadlock 등)가 에이전트 전체 엔진을 크래시시키는 사고를 막는 핵심적이고 강력한 예외 격리 보루 역할을 수행합니다.

### 1.3 `dynamic_prompt` 미들웨어를 통한 동적 런타임 가드레일 주입

에이전트가 상용 다중 테넌트(Multi-tenant) 환경에서 구동될 때, 사용자의 신원, 인가 등급, 소속 언어 영역에 맞추어 시스템 프롬프트를 실시간으로 바꾸어 주어야 하는 요구사항이 상시 존재합니다. 정적인 텍스트 템플릿에만 의존하게 되면 매번 런타임 시에 지저분하게 프롬프트를 갈아 끼우는 전처리 코드가 비즈니스 노드에 침투하게 됩니다.

`@dynamic_prompt` 데코레이터를 이용해 선언된 미들웨어 훅은 모델 호출이 성립되기 직전의 '가장 최신화된 런타임 컨텍스트 정보'를 주입받아, 즉석에서 **맥락 맞춤형 동적 시스템 프롬프트(Context-aware Dynamic System Prompt)**를 정교하게 컴파일하여 LLM의 입력값 맨 앞에 앵커링합니다.

이 메커니즘을 사용하면 다음과 같은 물리적 통제가 가능해집니다.
*   **인가 등급별 기밀 유출 통제**: 현재 실행을 지시한 사용자의 라이선스가 `standard` 등급인 경우, 기밀 데이터 분석 도구의 호출 규격과 시스템 준수 지침을 동적 시스템 프롬프트 단에서 기각 혹은 누락시켜, 모델이 애초에 기밀 정보에 대한 상상(할루시네이션)이나 도구 호출 도모 자체를 수행하지 못하도록 최전방에서 봉쇄합니다.
*   **런타임 로컬라이제이션**: 사용자의 지역 브라우저 헤더 세팅에 응하여 영어, 한국어, 일본어 등의 맞춤형 페르소나 지침을 동적으로 생성 주입하므로, 에이전트 작동의 일관성과 언어 정확성을 극대화합니다.

## 2. 데이터 흐름 및 컨텍스트/토큰 관리 구조

### 2.1 사용자 쿼리 인입부터 미들웨어 파이프라인 처리를 거치는 엔드투엔드 데이터 흐름(Data Flow)

미들웨어가 촘촘하게 결합된 LangChain 1.0 에이전트 환경에서 전체 트랜잭션이 종단 간 흘러가는 시퀀스와 데이터 변이 과정은 다음과 같은 흐름으로 정교하게 통제됩니다.

```
[ 사용자 발화 및 컨텍스트(UserContext) 진입 ]
        |
        v
[ 1단계: 에이전트 초기화 및 런타임 수립 ]
  - thread_id 기반 상태 로드 및 UserContext 바인딩 수행
        |
        v
[ 2단계: dynamic_prompt 미들웨어 인터셉트 및 가동 ]
  - 런타임에 바인딩된 UserContext(인증, 숙련도) 스캔
  - personalized_prompt 훅 작동 -> 맞춤형 시스템 프롬프트 즉석 컴파일 완료
  - 컴파일된 동적 프롬프트를 ModelRequest의 최상단 메시지 스택에 물리 병합
        |
        v
[ 3단계: wrap_model_call 미들웨어 1차 체인 진입 (Pre-Inference) ]
  - logging_middleware 작동 -> 현재 메시지 토큰 용량 측정 및 디버그 분석 기록
  - rate_limit_middleware 작동 -> 전역 카운터 및 슬롯 버킷 차단 검사 통과
        |
        v
[ 4단계: 물리 LLM API 엔드포인트 타격 및 추론 완료 ]
  - LLM이 추론 연산을 마친 뒤 도구 호출 ID 메타데이터가 담긴 AIMessage 방출
        |
        v
[ 5단계: wrap_model_call 미들웨어 2차 체인 진입 (Post-Inference) ]
  - logging_middleware 작동 -> 생성 결과 텔레메트리 보존 처리
        |
        v
[ 6단계: wrap_tool_call 미들웨어 체인 진입 (Pre-Tool Execution) ]
  - error_handling_middleware 작동 -> 인풋 인수 정밀 분석 수행
  - 비즈니스 도구(Tool) 비동기 호출 실행
        |
        |---> [ 정상 실행 성공 ]: 결과 데이터를 일반 관찰 텍스트로 보정
        |
        |---> [ 물리적 예외 크래시 발생 ]: error_handling_middleware가 예외 포획
              - ToolMessage(content="도구 실행 도중 에러가 발견되었습니다...", tool_call_id=...)로 캡슐화 완료
        |
        v
[ 7단계: 에이전트 루프 회귀 및 END 수렴 ]
```

### 2.2 미들웨어가 에이전트 예외 복구(Error Recovery)와 보안(PII, Rate Limiting)에 기여하는 인프라적 장점

프로덕션 환경의 에이전트는 불안정한 네트워크, 사용자의 유해한 발화, API 호출 속도 초과 등 무수한 물리적 붕괴 위협에 노출되어 있습니다. 미들웨어 계층은 이러한 위협으로부터 에이전트의 단기 메모리와 런타임 안정성을 수호하는 **완충 가드레일 방어막**을 제공합니다.

*   **시스템적 Rate Limiting의 보장**: 상용 LLM 및 외부 결제 시스템 도구를 이용하는 에이전트가 무제한적인 반복 도구 호출이나 모델 호출을 감행할 때 발생하는 과도한 예산 낭비를 막기 위해, `AgentMiddleware`의 클래스 인스턴스 멤버 변수 공간에 정교한 호출 카운터를 적재합니다. 만약 지정 임계치(예: 단일 세션당 최대 5회 호출)를 이탈할 시, API 소켓을 두드리기 전에 미들웨어 단에서 `RuntimeError`를 고의 발생시켜 에이전트의 무한 폭주를 강제 차단합니다.
*   **PII(개인식별정보)의 전방 감지 및 마스킹**: 사용자가 입력한 주민등록번호, 신용카드 번호 등 민감한 개인 정보 데이터셋이 LLM의 학습 및 로깅 스토리지 공간으로 침투하는 보안 누수를 막기 위해, `wrap_model_call` 진입 전 영역에서 정규식 및 자연어 처리 기술로 메시지 텍스트를 고해상도 검사(Scan)한 뒤, 위험 토큰들을 `[REDACTED]` 문양으로 마스킹하여 전송합니다. 이로 인해 강력한 컴플라이언스 준수 체계가 전역 에이전트 인프라에 안착됩니다.

### 2.3 복수 미들웨어 체인의 호출 스택 구조 및 토큰 비용 최적화 분석

미들웨어는 단 하나만 등록하는 것이 아니라, 수많은 검증 및 로깅 미들웨어들을 어레이 형태로 겹겹이 쌓아 올려 **체인 구조(Middleware Chain)**를 형성할 수 있습니다. 이때 등록되는 순서(Order)는 데이터 변이와 실행 순서에 심대한 시스템적 인과를 형성하므로 정밀히 설계되어야 합니다.

```
                    [ Middleware Chain 호출 스택 흐름 ]

          Request In인입 ->
            +-------------------------------------------+
            |  Middleware 1: Rate Limiter (호출 차단)    |
            |    +--------------------------------------+
            |    |  Middleware 2: PII Masker (개인정보)  |
            |    |    +---------------------------------+
            |    |    |  Middleware 3: Tracer (시간측정)|
            |    |    |    +----------------------------+
            |    |    |    |  Physical LLM/Tool Call    |
            |    |    |    +----------------------------+
            |    |    |  Tracer (시간 측정 완료)         |
            |    |    +---------------------------------+
            |    |  PII Masker (반환값 정제)             |
            |    +--------------------------------------+
            |  Rate Limiter (카운터 기록 완료)           |
            +-------------------------------------------+
          <- Response Out방출
```

이 다중 레이어 구조는 다음과 같은 토큰 비용의 가용성 효율화를 달성하게 해줍니다.
*   **Fail-fast 패턴을 통한 무용 토큰 소모 방지**: Rate Limit 및 인증 검증 미들웨어를 가장 외곽에 배치합니다. 만약 사용자의 호출 권한이나 예산 임계치가 이 시점에 기각 판정을 받는다면, 그 내부의 비싼 프롬프트 가공 및 LLM API 전송 단계를 원천 스킵하고 즉각 복구 안내 응답을 내보냅니다. 이를 통해 불필요한 GPU 사전 연산(Prefill) 토큰 부피를 완전히 통제할 수 있습니다.
*   **상태 보존형 메모리 압축과의 시너지**: 미들웨어 내부에서 상태 딕셔너리의 메시지 히스토리를 요약하거나 트리밍하는 처리를 Pre-Inference 단계로 결합함으로써, 물리적인 API 왕복 도중 어텐션 맵 상에서 낭비되는 가치가 하락한 대량의 토큰 소모 속도를 안정적으로 억제하는 상향적 가용 성능 평탄화를 이룩해 줍니다.

## 3. 에이전트 워크플로우 구현 및 API/설정 매핑 분석

### 3.1 클래스 기반 AgentMiddleware, 동적 프롬프트, 도구 및 에러 핸들링이 유기 통합된 완전 구현 코드

아래의 소스코드는 프로덕션 서비스 아키텍처 사양을 철저히 충족하도록 설계된 완전한 형태의 파이썬 스크립트입니다. 클래스 상속을 통한 상태 보존형 Rate Limiting 미들웨어, 타이밍 텔레메트리 수집기, `@wrap_tool_call`을 이용한 예외 방어 가드레일, 그리고 `@dynamic_prompt`가 주입되는 개인화 동적 컨텍스트 흐름을 단일 워크플로우 안에 온전히 구축하여 정상 구동을 시연합니다.

```python
import os
import time
import operator
from typing import TypedDict, Annotated, Sequence, Literal, Dict, Any, List
from dataclasses import dataclass
from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langchain.agents import create_agent
from langchain.agents.middleware import (
    wrap_model_call,
    wrap_tool_call,
    dynamic_prompt,
    AgentMiddleware,
    ModelRequest,
    ModelResponse,
    ToolCallRequest
)
from langchain_core.messages import BaseMessage, HumanMessage, AIMessage, ToolMessage

# ==========================================
# 1. 런타임 사용자 정보(UserContext) 및 전역 상태(State) 설계
# ==========================================

@dataclass
class EnterpriseUserContext:
    """런타임 시에 외부 시스템으로부터 에이전트 엔진에 주입되는 불변 유저 데이터 프로필"""
    user_id: str
    user_name: str
    tier_level: Literal["basic", "premium"]
    preferred_language: Literal["ko", "en"]


class AdvancedAgentState(TypedDict):
    """시스템 오퍼레이션 상태 딕셔너리 정보"""
    messages: Annotated[Sequence[BaseMessage], operator.add]
    system_execution_logs: List[str]


# ==========================================
# 2. 고강도 비즈니스 물리 도구 정의
# ==========================================

@tool
def execute_database_division(numerator: float, denominator: float) -> str:
    """지정된 두 숫자의 분수 나눗셈 연산을 수행하여 원격 데이터베이스 로그에 적재합니다."""
    # 만일 b가 0인 경우 파이썬 런타임은 ZeroDivisionError를 폭출시킵니다.
    # 이 예외는 미들웨어가 안전하게 포획할 예정입니다.
    calc_result = numerator / denominator
    return f"[연산 결과 성공] {numerator} / {denominator} = {calc_result:.4f}"

# 3. 객체 지향적 복합 AgentMiddleware 및 독립 미들웨어 체인 설계
# ==========================================

class EnterpriseGovernanceMiddleware(AgentMiddleware):
    """에이전트 무한 루프 폭주를 제한하고 물리 호출 지표를 기록하는 수호 가드레일 클래스 미들웨어"""
    
    def __init__(self, max_allowed_calls: int = 3):
        super().__init__()
        self.max_allowed_calls = max_allowed_calls
        self.active_counter = 0
        
    def wrap_model_call(self, request: ModelRequest, handler) -> ModelResponse:
        """모델 호출 전후에 개입하여 호출 횟수를 검문하고 시간 텔레메트리를 계산하는 핵심 인터셉터"""
        self.active_counter += 1
        
        # 1단계: Fail-fast 정책 가동 (호출 제한 임계 영역 사전 스캔)
        if self.active_counter > self.max_allowed_calls:
            print(f"🚨 [보안 차단] 에이전트 총 호출 횟수가 제한치({self.max_allowed_calls}회)를 완벽하게 돌파하여 물리 요청을 강제 기각합니다.")
            raise RuntimeError(f"API Rate Limit Exceeded: Single Session Call Count {self.active_counter} over Limit {self.max_allowed_calls}.")
            
        print(f"📊 [미들웨어 인프라] 모델 호출 감시 승인 통과. 현재 스레드 카운팅: {self.active_counter}/{self.max_allowed_calls}")
        
        # 2단계: 타이밍 텔레메트리 수집
        start_timestamp = time.time()
        
        # 하부 미들웨어 또는 최종 LLM 물리 드라이버로 요청 전달(핸들러 실행)
        response: ModelResponse = handler(request)
        
        end_timestamp = time.time()
        elapsed_seconds = end_timestamp - start_timestamp
        print(f"⏱️ [텔레메트리 분석 완료] LLM 서버 네트워크 왕복 및 추론 소요 시간: {elapsed_seconds:.4f}초")
        
        return response
        
    def reset_counter(self):
        """세션 초기화를 도울 카운터 클렌징 유틸리티"""
        self.active_counter = 0

# 4. 기능별 독립 미들웨어 훅 및 동적 프롬프트 데코레이터 선언
# ==========================================

@wrap_tool_call
def defensive_error_guard_middleware(request: ToolCallRequest, handler) -> ToolMessage:
    """도구 실행 시 발생하는 심각한 물리 시스템 크래시를 전방 가로채어 안정적인 메시지로 캡슐화 치유하는 훅"""
    tool_name = request.tool_call["name"]
    print(f"🔧 [도구 인터셉터 진입] '{tool_name}' 실행 시작. 전달 인수셋: {request.tool_call['args']}")
    
    try:
        # 실제 타깃 도구 함수의 비즈니스 로직을 호출 실행
        tool_output = handler(request)
        print(f"✅ [도구 인터셉터 종료] '{tool_name}' 정상 실행 성공.")
        return tool_output
    except ZeroDivisionError as zd_err:
        # ZeroDivisionError 특수 예외를 우아하게 포획하여 런타임 셧다운 위기 탈출
        print(f"⚠️ [도구 인터셉터 예외 포획] '{tool_name}' 실행 도중 치명적 수학 연산 에러 감지: 0으로 나누기 시도.")
        return ToolMessage(
            content=f"[시스템 자가 치유 피드백] '{tool_name}' 도구를 호출할 때 분모(denominator)를 0으로 기재하여 'ZeroDivisionError'가 촉발되었습니다. 신속히 다른 0이 아닌 유효 숫자를 배정하여 이 연산을 재수행하도록 아키텍처 판단을 다시 내리십시오.",
            tool_call_id=request.tool_call["id"]
        )
    except Exception as generic_err:
        # 일반 예외 캡슐화 처리
        print(f"🚨 [도구 인터셉터 예외 포획] 기타 시스템 오류 발생: {str(generic_err)}")
        return ToolMessage(
            content=f"[시스템 경고] 도구 구동 실패: {str(generic_err)}. 대안 복구 경로를 즉시 지시하십시오.",
            tool_call_id=request.tool_call["id"]
        )


@dynamic_prompt
def personalized_tenant_prompt_compiler(request: ModelRequest) -> str:
    """실행 시점에 주입된 사용자 컨텍스트를 스캔하여 맞춤형 시스템 가이드를 즉석 구성하는 컴파일러"""

    if user_ctx.tier_level == "premium":
        tier_instruction = "당신은 프리미엄 골드 회원을 전담 어시스트하고 있습니다. 최고의 정성 어린 전문 상세 리포트 형태로 상세히 안내를 수행하십시오."
        
    dynamic_instructions = (
        f"<인증 정보>\n"
        f"- 현재 제어 관리자명: {user_ctx.user_name}\n"
        f"- 테넌트 식별 키: {user_ctx.user_id}\n"
        f"</인증 정보>\n\n"
        f"<행동 가이드라인>\n"
        f"- {language_instruction}\n"
        f"- {tier_instruction}\n"
        f"</행동 가이드라인>"
    )
    
    return dynamic_instructions

class ProductionMiddlewareAgentBuilder:
    """통제 미들웨어와 가드레일들이 탑재된 엔터프라이즈 에이전트를 조립 생산하는 빌더"""
    
    def __init__(self):
        # 결정적 의사결정을 확보하기 위해 zero-temperature로 모델 인스턴스 초기화
        self.llm = init_chat_model(
            "openai:gpt-4o-mini",
            temperature=0.0,
            timeout=30.0,
            max_retries=2
        )
        
        # 상태 관리형 클래스 미들웨어 인스턴스 수립
        self.governance_guard = EnterpriseGovernanceMiddleware(max_allowed_calls=3)
        
        # 순서대로 엮이는 미들웨어 오케스트레이션 어레이 바인딩
        # 실행 단계는 기재된 순서대로 정렬하여 중첩 스택을 구성합니다.
        self.middleware_pipeline = [
            self.governance_guard,                # 1 레이어: 속도 제한 및 시간 지표
            defensive_error_guard_middleware,     # 2 레이어: 도구 실행 예외 철벽 포획
            personalized_tenant_prompt_compiler   # 3 레이어: 런타임 동적 가드레일 프롬프트 주입
        ]
        
        # create_agent 규약대로 조립 수립
        self.agent_application = create_agent(
            model=self.llm,
            tools=[execute_database_division],
            system_prompt="당신은 데이터베이스 원격 가산 및 분할 연산을 대리 제어하는 자동화 아키텍트입니다.",
            middleware=self.middleware_pipeline,
            context_schema=EnterpriseUserContext
        )
```

### 3.2 런타임 구동 관점의 핵심 API 매핑 및 매개변수 심층 해설

미들웨어가 에이전트 전역 수명주기에 미치는 시스템 엔지니어링적 인과관계와 각 개별 매개변수의 역할은 다음과 같습니다.

*   **`@wrap_model_call` 데코레이션**: 이 인터페이스로 정의된 함수는 에이전트 아키텍처에서 모델을 호출하기 전과 후에 공통적으로 실행되는 독립 프록시가 됩니다. 함수의 `handler` 매개변수는 다음 순번에 위치한 미들웨어나 최하단 LLM API 드라이버 자체를 호출하는 실행 체인 게이트웨이 역할을 전담합니다. 이 `handler`를 호출하지 않고 다른 응답을 임의 구성해 리턴하면 모델 호출 자체를 스킵하는 무음 가로채기가 현실화됩니다.
*   **`@wrap_tool_call` 데코레이션**: 도구가 호출되는 순간의 파라미터 세트와 예외 핸들링 스택을 관장하는 제어 인터셉터입니다. 도구 연산이 진행되다 하드웨어적 에러로 뻗을 경우, 미들웨어 내부의 `except` 블록이 `ToolMessage` 객체를 조립 리턴해 줌으로써, 모델이 "아, 내가 인수를 잘못 전달했거나 원격 서버가 죽었으니 다른 방식으로 대처해야겠다"는 자가 성찰 ReAct 루프를 지속하도록 연결고리를 구축해 줍니다.
*   **`@dynamic_prompt` 데코레이션**: 모델 호출 직전 작동하며 파이썬 `str` 타입의 시스템 메시지 가이드를 반환하도록 강제되는 전처리 가드레일러입니다. 이 훅 안에서 런타임 컨텍스트(`request.runtime.context`)에 접근하여 실시간으로 유효 범위와 제약 태그를 변경 생성할 수 있으므로, 비즈니스 코드에 프롬프트 조립 논리가 오염되는 기술적 부채를 차단합니다.
*   **`context_schema = EnterpriseUserContext`**: 에이전트 시스템이 외부로부터 받아들일 사용자/세션 정보 명세를 정적으로 규격화하고, 형변환 유효성 평가를 통과한 데이터만 `dynamic_prompt` 미들웨어로 수혈될 수 있도록 타입 가드레일을 수립하는 핵심 인자 설정입니다.

</ul>
<br>
<b>2. wrap_tool_call의 예외 포획 특성과 단기 메모리 영향:</b>
<ul>
    <li><b>물리적 타이밍:</b> 모델의 추론(AIMessage 내 tool_calls)이 완수된 직후, 실제 로컬/원격 파이썬 도구(Tool)를 점화 및 구동시키는 영역(Execution Phase)에 개입합니다.</li>
    <li><b>예외 상황과 대책:</b> 도구 내부의 예외(ZeroDivisionError, SQL Syntax Error 등)를 감지하여 <b>정식 <code>ToolMessage</code> 형태의 데이터셋 객체로 교정 및 캡슐화</b>하여 반환합니다.</li>
    <li><b>메모리 영속성 및 ReAct 연속성 측면:</b> 이 방식은 에이전트 아키텍처에 막강한 영속 안전성을 부여합니다. <code>wrap_tool_call</code>이 예외를 안전하게 <code>ToolMessage</code>로 바꾸어 전역 상태 딕셔너리에 삽입(operator.add)하면, 뒤이은 다음 ReAct 단계에서 모델은 <b>"[사용자 질문] -> [나의 도구 호출 시도] -> [도구의 상세 실행 에러 피드백 수신(ToolMessage)]"</b>이라는 기나긴 영속적 시계열 메모리를 온전히 상속받습니다. 모델은 자신의 실패를 명확히 관찰(Observation)하여, 인수를 다르게 수정해 도구를 재호출하거나 정중한 한계 사과를 표하는 등 <b>"전체 추론 루프의 단절 없는 유기적 자가 수정 및 우회 극복"</b>이 완벽히 가동됩니다.</li>
</ul>
</details>

### [질문 2]
**`dynamic_prompt` 미들웨어가 모델 호출 직전에 동적으로 작동하는 구체적인 메커니즘을 어텐션 윈도우(Attention Window) 최적화와 보안 멀티테넌시(Multi-tenancy) 관점에서 분석하고, 정적 프롬프트(Static Prompt Template) 대비 어떠한 아키텍처적 유용성을 추가로 획득할 수 있는지 시스템 아키텍트의 시야에서 상세히 기술하시오.**

<details>
<summary><b>[질문 2] 정답 및 상세 해설 보기</b></summary>
<br>
<b>정답 및 시스템적 해석:</b>
<br>
정적 프롬프트 템플릿(Static Prompt)은 배포 시점에 작성된 고정적인 지침에 아규먼트 문자열만 포맷팅하는 방식으로, 동적인 컨텍스트 변화와 멀티테넌트 격리 구조를 인프라 레이어에서 제어하기가 사실상 불가했습니다. <code>dynamic_prompt</code> 미들웨어는 이 통제 제어권을 에이전트 외부 엔진으로 인양하여 막강한 아키텍처적 우위를 실현합니다.
<br><br>
<b>1. 어텐션 윈도우(Attention Window) 제어 극대화:</b>
<ul>
    <li><b>프롬프트 토큰 다이어트:</b> 정적 템플릿에서는 모든 등급과 모든 사용자가 처리할 수 있는 모든 도구 규칙과 제약사항을 하나의 긴 프롬프트(System Prompt) 안에 우격다짐으로 상시 밀어 넣어야 했습니다. 이는 쓸데없는 입력 토큰 소모와 컨텍스트 유실(Lost in the Middle)을 조장했습니다.</li>
    <li><b>필수 토큰만 동적 선별 주입:</b> <code>dynamic_prompt</code>는 실행 시점에 주입된 <code>UserContext</code>를 확인하여, 해당 사용자 등급(Premium, Standard)에 매핑되는 <b>"최소한의 가용 수칙 블록과 바인딩 대상 도구 명세만 즉석에서 발췌 및 컴파일"</b>하여 프롬프트의 체력을 극적으로 낮춰 줍니다. 이로 인해 GPU 행렬 연산 코스트가 비선형적으로 최적화되고 첫 번째 토큰 처리 레이턴시(TTFT) 또한 혁신적으로 감축됩니다.</li>
</ul>
<br>
<b>2. 보안 멀티테넌시(Multi-tenancy) 영역의 영속 격리 경계 수립:</b>
<ul>
    <li><b>프롬프트 탈옥 및 권한 탈취 원천 방어:</b> 사용자가 악의적인 프롬프트 인젝션을 날려 에이전트의 페르소나를 탈취하려 시도하더라도, <code>dynamic_prompt</code> 내부의 로직은 모델이 전혀 조종하거나 수정할 수 없는 불변의 읽기 전용 인프라 객체(<code>UserContext</code>)를 기반으로만 가이드라인을 동적 생성합니다.</li>
    <li>예컨대 관리자 전용 데이터베이스 조회 도구를 트리거하는 수칙 지침은 오직 관리자 신원 토큰이 확인된 <code>UserContext</code> 런타임에서만 미들웨어 내부 조건문에 의해 프롬프트 상단에 포함됩니다. 일반 사용자의 세션에서는 도구 가이드라인 자체가 프롬프트에서 완벽히 소거되므로, 모델이 탈옥당해 <i>"관리자 도구를 강제 호출하라"</i>는 명령을 수신하더라도 아예 호출 스키마 자체를 몰라 실행하지 못하는 <b>"논리적 제로 트러스트(Zero Trust) 격리 장치"</b>가 단단히 구축됩니다.</li>
</ul>
</details>

### [질문 3]
**클래스 기반 `AgentMiddleware`를 활용하여 에이전트의 모델 호출 횟수를 실시간 제어하는 속도 제한(Rate Limiting)과 PII(개인식별정보) 필터링 가드레일을 다중 스레드 병렬 실행 환경(Multi-threaded Parallel Execution)에서 구현하려 합니다. 이때 전역 임계 영역(Critical Section)의 동시성 경쟁 문제를 방어하고 토큰 낭비를 최소화하기 위한 아키텍처 설계 방안을 제안하시오.**

<details>
<summary><b>[질문 3] 정답 및 상세 해설 보기</b></summary>
<br>
<b>정답 및 시스템적 해석:</b>
<br>
다중 스레드 병렬 환경에서 다수의 에이전트 세션이 하나의 전역 공유 미들웨어 인스턴스에 동시다발적으로 쓰기(Write) 연산을 타격하면, 카운팅 동기화 불일치로 인해 Rate Limit 임계치가 무너지거나 스레드 데드락(Deadlock) 병목이 발생하여 시스템 가용성이 훼손될 수 있습니다.
<br><br>
<b>1. 동시성 경쟁 방어를 위한 스레드 안전성(Thread-safety) 확보 설계:</b>
<ul>
    <li><b>원자적 락킹(Atomic Locking) 기법 도입:</b> <code>AgentMiddleware</code> 내부의 카운터 변수 갱신 영역에 파이썬의 <code>threading.Lock()</code> 메커니즘을 명시 도입하여, 자원 락을 안전하게 확보한 단 하나의 스레드만 슬롯을 갱신하도록 임계 영역을 격리 수립해야 합니다.</li>
    <li><b>분산 Redis 토큰 버킷 아키텍처 확장:</b> 만일 다중 컨테이너 및 복수 노드로 인프라가 수평 확장(Horizontal Scaling)되는 쿠버네티스 환경인 경우, 로컬 락만으로는 동시성을 감당할 수 없습니다. 이때는 미들웨어 내부에서 분산 메모리 격리 장치인 Redis에 접속하여 <b>"분산 토큰 버킷 알고리즘(Distributed Token Bucket with Redlock)"</b>을 실행하는 Lua 스크립트를 원자적으로 트리거해야 합니다. 이를 통해 전체 분산 스레드가 동일한 세션 속도를 실시간으로 추적 감시하는 스레드 세이프 안정성을 획득합니다.</li>
</ul>
<br>
<b>2. 토큰 낭비 최소화를 위한 Fail-fast 가드레일 설계:</b>
<ul>
    <li><b>PII 사전 스캔 및 기각 필터 레이어 배치:</b> 사용자의 발화가 미들웨어 파이프라인의 최외각에 있는 <code>wrap_model_call</code> Pre-Inference 단계로 인입되는 즉시, 비싼 정규식 파싱 검사 및 프레임워크 기반 개인정보 스캐너(Presidio 등)를 선제 구동합니다. 만약 주민등록번호와 같은 심각한 PII 침투가 발견되면, LLM API 호출 <code>handler(request)</code> 자체를 <b>물리적으로 격리 및 트리거 거부</b>하고 즉시 오류 전이 응답(<code>"개인정보가 포함되어 요청이 거부되었습니다."</code>)을 방출시킵니다.</li>
    <li>이 필터 레이어 순서가 LLM 호출 뒤나 도구 실행 뒤에 가동되도록 설계하는 실수를 저지르면, 개인정보 스캔을 수행하기 위해 이미 수만 개의 사전 연산 입력 토큰 비용이 허망하게 소진되는 치명적인 누수가 유발됩니다. 반드시 <b>"Rate Limit 확인 -> PII 스캐닝 -> dynamic_prompt 결합 -> 최종 모델 호출"</b>의 물리 순서로 미들웨어 파이프라인 스택을 엄밀하게 레이아웃해야만 비용 파멸적 낭비를 극한으로 제어할 수 있게 됩니다.</li>
</ul>
</details>
