# [Evaluator-optimizer로 자율 개선 만들기]

## 1. 에이전트 개발 관점의 핵심 아키텍처 분석

### 1.1 Evaluator-Optimizer 디자인 패턴의 동작 본질과 자기 개선(Self-Correction) 피드백 루프
단일 LLM의 일방향성 생성 흐름은 복잡한 도메인 지식 구축이나 고난도 추론 작업에서 품질의 균일성을 영위하기 어렵고, 사소한 논리 오류로 인한 연산 폭사를 제어할 수 없는 한계에 봉착합니다. 이를 극복하기 위해 설계된 **Evaluator-Optimizer 패턴**은 고성능 생성기(Generator)가 도출한 출력 초안을 엄격한 평가기(Evaluator)가 분석·진단한 뒤, 불합격 요소를 구체적인 피드백 매트릭스로 변환하여 다시 생성기에게 연쇄 주입하는 자율 순환 자기 개선(Self-Correction) 아키텍처입니다.
*   **관심사 분리(Separation of Concerns)**: 복합 임무를 단일 프롬프트 내부에서 동시에 집필하고 자체 비평하게 하면 모델에 심각한 인지적 과부하가 초래되어 평가 기준 준수율이 붕괴됩니다. 생성과 평가의 역할을 독립된 프롬프트와 서로 다른 하이퍼파라미터 컨디션을 장착한 노드로 분리함으로써, 각 단계의 어텐션 분배 밀도를 극한으로 끌어올립니다.
*   **인과적 점진 정제(Iterative Refinement)**: 생성기는 매 회차 루프를 돌 때마다 기저 LLM 가중치를 직접 미세조정(Fine-Tuning)하지 않고도, 인-컨텍스트(In-Context) 상에 전달된 이전 실패 회차의 비평 피드백 정보를 인과적 조건으로 수용하여 출력을 점진적으로 고밀도 정제해 나갑니다.

### 1.2 with_structured_output을 활용한 구조화된 평가(Structured Evaluation) 스키마와 Pydantic 매핑 원리
비평가(Evaluator)의 피드백이 정형화되지 않은 자연어로 분산되면, 생성기는 무엇을 어떻게 고쳐야 할지 의미론적 정합성을 인지하지 못하고 방황하다가 환각을 반복 생산하게 됩니다. 따라서 현대 에이전트 설계에서는 비평가의 출력을 이진 평점(Grade)과 정량적 개선 피드백(Feedback)으로 명확히 구조화하는 **with_structured_output** 가드레일이 수반되어야 합니다.
*   **Pydantic 스키마를 통한 출력 통사 제약**: Pydantic의 `BaseModel`을 상속한 `Feedback` 데이터 구조를 정의하고, 평점 필드를 `Literal`이나 구체적인 열거형(Enum)으로 바인딩하여 모델에 인입시킵니다. API 컴파일러는 이 규격을 기저 LLM이 강제 수용하도록 JSON Schema 명세로 하달하며, 최종 반환 텍스트가 해당 스키마를 100% 만족할 때까지 로우레벨 디코딩 단계에서 문법 정적 필터링을 집행합니다.
*   **평가 결정론성 확보**: 평가 결과가 비정형 문자열 구조를 가질 때 발생하는 정성적 평가의 무작위성을 격격히 통제하고, 자율 개선 분기 제어를 가동하는 조건부 라우터 노드가 완벽히 분석 및 분기 처리할 수 있는 결정론적 자료형(Deterministic DataType)을 수립해 줍니다.

### 1.3 조건부 엣지(Conditional Edge)와 최대 반복 횟수(Max Iterations) 컷오프를 통한 루프 발산 방지 거버넌스
순환(Cycle) 구조를 허용하는 LangGraph 오케스트레이션에서 발생하기 쉬운 가장 파멸적인 런타임 위협은 생성기와 평가기가 팽팽한 논리 대립을 유지하며 무한히 루프를 공전하는 **무한 루프 데드락(Infinite Loop Deadlock)**과 이에 수반되는 가공할 만한 API 요금 및 인프라 자원 폭사입니다.
*   **루프 발산 억제를 위한 컷오프 가드레일**: 시스템 상태 채널인 `State` 내에 현재의 반복 횟수를 추적하는 `iteration` 카운터 변수를 의무 탑재합니다. 조건부 라우터 함수인 `route_joke`는 평가기의 평점 판독과 더불어 누적 카운터를 상시 감시하며, 약속된 최대 한계 임계치(Max Iterations, 예: 3회)에 다다르면 최종 합격 여부와 무관하게 제어권을 강제로 `__end__`(END) 노드로 인양 방출시킵니다.
*   **상태 보존형 복구 가치**: 이 컷오프 안전망을 전개함으로써 시스템은 무한 리바운드 폭사를 완벽히 우회 제어하고, 최악의 경우에도 그 시점까지 도달한 최선의 대안적 정제 출력 상태를 유지하며 세션을 안전하게 반환할 수 있게 됩니다.

## 2. 데이터 흐름 및 상태 제어 모델

### 2.1 Evaluator-Optimizer 루프의 종단간 데이터 흐름 및 상태 전이도
아래 흐름도는 사용자가 하달한 주제로부터 Generator 노드가 초안을 작성하고, Evaluator 노드가 구조화된 Pydantic feedback을 동적으로 획득하여 분석한 뒤, 합격/불합격 여부 및 카운터 한계 도달에 의거해 제어권을 순환시키거나 무결 종결 처리하는 데이터의 전이 맵을 나타냅니다.

```
[사용자 타겟 주제 인입 (User Topic)]
       │
       ▼ [State: "topic" 초기화 및 루프 개시]
[llm_call_generator 노드 (Generator)] ◄─────────────────────────────────────────┐
  - "topic" + state.get("feedback")을 수용한 초안 집필                          │
       │                                                                       │
       ▼ [joke 초안 반환 및 State 누적 적재]                                    │
[llm_call_evaluator 노드 (Evaluator)]                                          │
  - Pydantic BaseModel로 구조화된 feedback 및 grade 강제 도출                   │
       │                                                                       │
       ▼ [funny_or_not & feedback 상태 업데이트]                                │
[route_joke 조건부 라우팅 판단 (Router)]                                        │
  - 이진 평점(funny) 혹은 최대 시도 횟수(iteration >= 3) 도래 여부 검사           │
       ├─────────────────────────────────────────┐                             │
       ▼ [YES: Accepted / Max Cut-off]          ▼ [NO: Rejected & 피드백 순환] │
[최종 정제 출력 노출 및 보존]                     [state["iteration"] + 1 업데이트]
       │                                         │                             │
       │                                         └─────────────────────────────┘
       ▼
     [END]
```

### 2.2 반복 피드백에 수반되는 컨텍스트 팽창(Context Inflation) 병목과 윈도우 슬라이딩 제어 전략
*   **피드백 누적으로 인한 Context Rot 위협**: Evaluator-Optimizer 루프를 회차별로 지속 가동하면, 이전 회차에서 실패한 모든 정성적 비평 내용(Observation)이 프롬프트 버퍼에 무제한 누적 연접됩니다. 이는 어텐션 맵 내부에서 가중치의 의미론적 희석과 VRAM 제곱 부하 $O(T^2)$ 팽창을 연쇄 도출하여, 생성기가 최신 피드백에 집중하지 못하고 1차 피드백 조건과 혼동을 일으키는 어텐션 포화(Attention Saturation) 장애를 초래합니다.
*   **Curation 기반 컨텍스트 정제 가이드라인**:
    *   **최신 피드백 Pinned 마운트 정책**: 루프 전개 시 전역 메시지 리스트에 매회차 원시 로그 전체를 보존하는 비효율을 기각하고, 오직 "직전 1회차의 핵심 feedback 문자열"만을 단일 채널 변수로 유지 갱신(Overwrite)하도록 설계하여 입력 토큰 길이를 상수의 정상 범위 내로 동결시킵니다.
    *   **결정론적 상태 소거 기제**: 이미 반영이 완료된 과거 히스토리 텍스트들은 과감히 세션 버퍼에서 제외 탈락(Eviction)시켜, 생성기의 셀프 어텐션 주의 분배력이 타겟 피드백 스키마에만 정밀 조율되도록 물리 인프라를 보존합니다.

## 3. 실전 워크플로우 구현 및 API 매핑 분석

### 3.1 LangGraph 기반 Evaluator-Optimizer 자율 개선 시스템 파이썬 프로덕션 스크립트
다음 소스코드는 Pydantic 라이브러리의 엄격한 출력 통제 기제와 LangGraph의 상태 기하 제어선을 융합하여, 비결정론적 AI가 스스로 비평을 받아 가며 한계 조건 내에서 완벽하게 점진 진화하도록 구성한 파이썬 오케스트레이터 전체 명세입니다.

```python
import os
from typing import Literal, Dict, Any
from pydantic import BaseModel, Field
from dotenv import load_dotenv

# LangChain 및 LangGraph 핵심 API 수입
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END

# 1. 시스템 구동 환경 변수 초기 세팅
load_dotenv()
if not os.getenv("OPENAI_API_KEY"):
    os.environ["OPENAI_API_KEY"] = "your-openai-api-key"

# 2. 구조화된 비평(Evaluator) 피드백 정량 도출을 위한 Pydantic 스키마 정의
class Feedback(BaseModel):
    """
    비평가(Evaluator)가 생성물 품질을 평가하고 불합격 시 고쳐야 할 지침을 담는 정형 컨테이너
    """
    grade: Literal["funny", "not funny"] = Field(
        description="농담이 참신하고 재미있는지 여부에 대한 최종 이진 판단 평점"
    )
    feedback: str = Field(
        description="만약 재미가 없다면(not funny), 구체적으로 무엇을 어떻게 수정하고 보완해야 하는지 제시하는 행동 피드백 지침"
    )

# 3. 오케스트레이션 세션에서 지속 보존될 에이전트 상태(State) 선언
class State(TypedDict):
    joke: str           # 생성기가 최종 도출한 농담 텍스트
    topic: str          # 사용자가 최초 지시한 농담 주제
    feedback: str       # 평가기가 동적으로 주입해 준 줄글 비평 가이드
    funny_or_not: str   # 조건부 분기 라우팅의 제어 지표가 될 이진 평가 상태
    iteration: int      # 무한 발산 및 자원 폭사를 차단하기 위한 현재 루프 카운터

# 4. 생성 및 비평 LLM 컴포넌트 격리 인스턴스화
# 생성기는 다양성과 창의적 발상을 도모하기 위해 온도를 0.7로 여유롭게 설정
generator_llm = ChatOpenAI(model="gpt-4o-mini", temperature=0.7)

# 평가기는 정량적 판단의 신뢰성과 객관 무결성을 사수하기 위해 온도를 0.0으로 완전 구속
evaluator_llm = ChatOpenAI(model="gpt-4o-mini", temperature=0.0)
structured_evaluator = evaluator_llm.with_structured_output(Feedback)

# 5. 그래프 노드(Nodes) 비즈니스 로직 구체화
def llm_call_generator(state: State) -> Dict[str, Any]:
    """
    Generator 노드: 주제 분석 및 피드백 점진 반영 농담 작성
    """
    iteration = state.get("iteration", 0) + 1
    print(f"\\n✍️ Generator: 농담 생성 구동 시작 (시도 회차 #{iteration})")
    
    # 누적 적재된 피드백 텐서가 존재한다면 인-컨텍스트 상에 전치 결합하여 개선 유도
    if state.get("feedback"):
        prompt = (
            f"주제: {state['topic']}\\n"
            f"이전 생성에 대한 불합격 비평 피드백: {state['feedback']}\\n"
            f"위 피드백을 철저하게 수용하여 개선된 농담을 다시 정성껏 집필해 주세요."
        )
    else:
        prompt = f"주제: {state['topic']}\\n재미있고 센스 넘치는 농담을 창작해 주세요."
    
    response = generator_llm.invoke(prompt)
    print(f"   📝 생성된 후보 농담: {response.content[:80]}...")
    
    return {"joke": response.content, "iteration": iteration}

def llm_call_evaluator(state: State) -> Dict[str, Any]:
    """
    Evaluator 노드: 생성물의 구조화 검증 및 이진 평가
    """
    print(f"\\n🔍 Evaluator: Pydantic 구조화 비평 검사 진입")
    
    grade_feedback = structured_evaluator.invoke(
        f"다음 농담을 엄정하게 평가해 주세요: {state['joke']}"
    )
    
    print(f"   판단 결과 -> {'✅' if grade_feedback.grade == 'funny' else '❌'} Grade: {grade_feedback.grade}")
    if grade_feedback.grade != "funny":
        print(f"   💬 반환된 피드백: {grade_feedback.feedback}")
        
    return {
        "funny_or_not": grade_feedback.grade, 
        "feedback": grade_feedback.feedback
    }

# 6. 제어 주권 확보를 위한 조건부 라우팅 및 엣지 로직 설계
def route_joke(state: State) -> Literal["Accepted", "Rejected_and_Loop"]:
    """
    조건부 엣지: 루프 지속성 및 오프셋 수렴 조건 판정
    """
    # 1. 합격 조건 충족 시 무결 종결 전치
    if state["funny_or_not"] == "funny":
        print("\\n🎉 품질 요건 달성: 재미있는 농담이 완성되어 수렴 종료합니다.")
        return "Accepted"
        
    # 2. 최대 시도 한계(3회) 도달 시 무조건적인 컷오프 탈출 집행
    if state.get("iteration", 0) >= 3:
        print("\\n⚠️ 최대 반복 허용치 도달: 자원 보존을 위해 강제 컷오프를 실행합니다.")
        return "Accepted"
        
    # 3. 불합격 요건 존재 시 피드백 탑재 후 생성 노드로 순환 리라우팅
    print("\\n🔄 피드백 불만족: 자율 교정 루프를 재가동합니다.")
    return "Rejected_and_Loop"

# 7. 상태 그래프(StateGraph) 컴파일 및 파이프라인 활성화
builder = StateGraph(State)

# 노드 등록 수립
builder.add_node("llm_call_generator", llm_call_generator)
builder.add_node("llm_call_evaluator", llm_call_evaluator)

# 흐름 제어선 정적 매핑
builder.add_edge(START, "llm_call_generator")
builder.add_edge("llm_call_generator", "llm_call_evaluator")

# 조건부 제어선 동적 매핑
builder.add_conditional_edges(
    "llm_call_evaluator",
    route_joke,
    {
        "Accepted": END,
        "Rejected_and_Loop": "llm_call_generator"
    }
)

# 최종 자율 개선 실행기 빌드 완성
optimizer_workflow = builder.compile()
print("✅ Evaluator-Optimizer 시스템 엔진 컴파일 수립 완료!")
```

### 3.2 주요 하이퍼파라미터 및 설계 설정 분석
*   **Generator의 창의적 온도(`temperature=0.7`) 설계**: 동일한 문장이나 상투적인 템플릿에 갇히는 확률적 고착을 도파하기 위해 생성기의 엔트로피 분포를 살짝 넓혀 둡니다. 온도가 충분히 보장되어야 Evaluator가 하달한 교정 피드백 지침을 해석할 때 이전 시도와 확연히 다른 새로운 차원의 어휘 융합과 아이디어를 도출하여 무결 수렴할 확률이 비약적으로 증가합니다.
*   **Evaluator의 결정론적 온도(`temperature=0.0`) 구속**: 평가의 엄격성과 안정성을 확보하기 위해 비평가의 활성화 분포를 0으로 얼려 버립니다. 평가기의 온도가 0이 아닐 경우, 동일한 생성 초안에 대해 어떤 회차에는 합격점을 주고 어떤 회차에는 불합격 판독과 정반대의 피드백을 내리는 확률적 모순에 부딪혀 에이전트 인프라 전체의 상태 전이가 파멸적인 모순 교착 상태(Contradictory Livelock)에 폭사하게 되므로 무조건적인 0도 구속이 수반되어야 합니다.

## 4. 에이전트 구조적 메커니즘 자가 진단

### [질문 1]
Generator의 생성적 탐색(Exploration)과 Evaluator의 엄밀한 비평(Exploitation) 사이에서 발생하는 최적의 `temperature` 트레이드오프 및 분리 설계 이유 분석
*   **해설**: 에이전트 시스템에서 생성기와 평가기가 동일한 언어 모델 인스턴스 혹은 동일한 온도 값을 활용할 경우, 시스템은 논리적 모순이나 한계 상태에 도달합니다. 온도가 균일하게 낮게 설정되면 생성기는 평가기의 교정 피드백을 수용하는 척하면서도 어휘 사영 공간의 제약으로 인해 전 회차와 문법 구조 및 핵심 단어가 유사한 동형 반복 문장만을 복사 도출하게 되어 무의미한 턴만 낭비하다 컷오프됩니다. 반대로 온도가 균일하게 높게 설정되면 평가기 자체가 주관적 판단 편향에 휘말려 일관된 합격 스펙트럼을 수호하지 못하고 루프 흐름이 비결정론적으로 방황하게 됩니다. 따라서 탐색이 중심인 생성기는 높은 온도를 통해 최적의 개선 대안을 거시적으로 탐색(Exploration)하게 유도하고, 평가기는 극한의 무온도 설정을 통해 사전에 약속된 JSON Schema 제약 사항과 가이드라인을 미시적이고 냉정하게 검증(Exploitation)하도록 분리 구축해야 인프라의 최종 결과 정합 신뢰도를 수학적으로 보장할 수 있습니다.

### [질문 2]
Evaluator-Optimizer 루프 가동 시 피드백 이력이 누적되면서 유발되는 VRAM 제곱 부하 $O(T^2)$를 격리하고 제어하기 위한 "이전 피드백 동적 이탈(Eviction) 및 슬라이딩 윈도우(Sliding Window) 컨텍스트 Curation" 설계 논술
*   **해설**: 트랜스포머의 어텐션 가중치는 입력 텍스트 전체 $T$에 대한 전역 쌍방향 유사도 계산을 집행하므로, 매 루프마다 생성문과 평가문 로그가 단순 누적 연접되면 입력 볼륨이 기하급수적으로 팽창하여 하드웨어 VRAM의 전력 및 연산 부하가 제곱 단위로 치솟습니다. 이 장벽을 격리 타개하기 위해, LangGraph 상태 변수 중 `feedback` 필드는 다중 메시지 어레이 형태가 아닌 단일 텍스트 문자열(Overwrite 리듀서 스키마)로 제한 선언합니다. 매 평가 회차가 완료되면 후속 생성 노드 실행 단계 이전에 과거의 원시 생각 로그나 중복 찌꺼기 텍스트를 메모리 버퍼 레이아웃 상에서 결정론적으로 이탈 소멸(Eviction)시킵니다. 오직 최신의 수렴 가이드 텐서 1단락만을 슬라이딩하여 프롬프트의 지침(Instructions) 바로 다음 입력 필드로 동적 전이 바인딩함으로써 VRAM 연산 복잡도를 정상 범위 내로 격리 제어하는 쾌거를 실현합니다.

### [질문 3]
LLM-as-a-Judge(비평가 에이전트)가 평가 단계에서 지닐 수 있는 관점적 편향(Bias)이나 형식 준수 실패를 구조적으로 원천 무력화하기 위한 Pydantic 가드레일 및 다중 비평 교차 합의(MoA 기반 Consensus) 인프라 연동 방안 분석
*   **해설**: 단일 비평 모델에만 품질 통제를 전적으로 의존하는 구조는 비평가 자체의 환각이나 편향적 무작위 평점으로 인해 정합성 필터 장치가 무력화될 소지를 안고 있습니다. 이를 방어하기 위한 궁극적인 보안 아키텍처는 Pydantic Schema 가드레일을 기본 전제 레이어로 설계하는 한편, 평가 노드 전위에 다중 관점 비평 합의제(Mixture of Evaluators)를 병렬 가동하는 것입니다. 각각 독립적인 검증 프롬프트를 무장한 리스크 비평 노드, 톤앤매너 검토 노드, 문법 완결성 검증 노드를 정적 병렬(Fan-Out) 배치하여 동시에 평가를 전개하고, 수확된 구조화 평점 데이터들을 최종 취합 노드(Consensus Aggregator)로 팬인(Fan-In) 수렴시킵니다. 이 Aggregator에서 과반수의 정량적 찬성(Majority Voting) 혹은 논리적 무결성이 완전히 확보될 때에만 수렴 종료 엣지를 타도록 통제함으로써, 개별 비평 모델의 일시적 환각 오인이나 형식 유실 장애를 완벽하게 중첩 차단하고 초고해상도의 자가 개선 거버넌스를 이륙하게 됩니다.
