# [심화 분석 학습 노트] 스프링 배치: 원격 청킹 - 전역 보복과 데이터 배송 아키텍처

## 1장. 작전의 실체: 원격 파티셔닝을 넘어선 전면전

기존의 파티셔닝이 부대마다 구역을 정해주고 알아서 정찰하게 하는 방식이었다면, **원격 청킹(Remote Chunking)**은 지휘부가 직접 목표물(데이터)을 확보하여 각 부대에게 '공격할 물건'을 직접 배송하는 방식입니다.

### 1. 원격 청킹의 정의와 차별성

* **원격 파티셔닝:** Manager는 작전 지침(`StepExecution Context`)만 보냅니다. Worker는 그 지침에 따라 자신의 구역에서 직접 데이터를 찾아 처리합니다.
* **원격 청킹:** Manager가 직접 데이터를 읽어서 **청크(Chunk)** 단위로 묶은 뒤, 이 **데이터 덩어리 자체**를 Worker에게 보냅니다. Worker는 전달받은 데이터 청크를 처리하고 결과를 보고합니다.

### 2. 역할 분담의 진실

* **Manager (ChunkProvider):** 데이터 수집 및 '핵탄두 데이터 청크' 생성/배송 담당.
* **Worker (ChunkProcessor):** 배송된 청크의 가공(Process) 및 저장(Write) 담당.

### 3. 전술적 가치와 사용 시나리오

* **Worker 측 부하 극심:** 읽기는 빠르지만 가공(Processor)이나 쓰기(Writer)가 매우 복잡하고 느릴 때 효과적입니다.
* **데이터 소스 분할 불가능:** 단일 스트림으로만 제공되는 데이터, 순서가 중요한 메시지 큐, 또는 파티셔닝 키가 없는 레거시 소스 처리에 유일한 대안입니다.

### 4. 치명적 약점 (한계점)

* **네트워크 대역폭 소모:** 실제 데이터가 이동하므로 통신망 과부하가 발생할 수 있습니다.
* **Manager 읽기 병목:** 중앙 지휘부 혼자 데이터를 읽어야 하므로, 읽기 속도가 전체 시스템의 한계가 됩니다.

## 2장. Manager 지휘 통제소: 데이터 판독과 배송 시스템

Manager 노드는 데이터 판독, 청크 생성, Worker 발송 및 결과 취합을 담당하는 시스템의 두뇌입니다.

### 1. Manager Step 설계 및 코드 분석

`RemoteChunkingManagerStepBuilderFactory`를 사용하여 통합 작전을 설계합니다.

```java
@Bean
public Step managerStep() {
    return remoteChunkingManagerStepBuilderFactory
        .get("globalRetaliationStep:manager") // 스텝의 고유 식별자 지정
        .chunk(3) // 한 번에 보낼 데이터 꾸러미(청크)의 크기 설정
        .reader(globalResistanceDataReader()) // Manager가 직접 데이터를 읽어오는 시작점
        .outputChannel(outboundChunksToWorkers()) // 생성된 청크를 Worker에게 보낼 채널 연결
        .inputChannel(inboundRepliesFromWorkers()) // Worker로부터 응답을 수신할 채널 연결
        .build();
}
```

* **chunk(3):** 3개의 데이터를 하나의 `ChunkRequest`로 묶어 발송 준비를 합니다.
* **outputChannel():** 읽어온 `ChunkRequest` 메시지가 통신망(Kafka 등)으로 나가는 출구입니다.
* **inputChannel():** 작업 결과인 `ChunkResponse`가 돌아오는 입구입니다.

### 2. 내부 전송 메커니즘: ChunkMessageChannelItemWriter

빌더는 내부적으로 `ItemWriter` 자리에 `ChunkMessageChannelItemWriter`를 배치합니다. 이 컴포넌트는 실제 저장이 아닌 **네트워크 전송**을 수행합니다.

```java
public class ChunkRequest<T> implements Serializable {
    private final long jobId; // 현재 작전(Job)의 식별자
    private final Chunk<? extends T> items; // 실제 배송되는 데이터 아이템 리스트
    private final StepContribution stepContribution; // 현재까지의 작업 통계 상태
    private final int sequence; // 청크의 순번 (라우팅 및 정렬에 사용)
}
```

* **items:** 데이터 자체가 네트워크를 타고 이동한다는 증거입니다.

### 3. 통신 인프라 및 라우팅 설정

Kafka를 통해 명령을 하달하고 응답을 수신하는 흐름(Integration Flow)을 구축합니다.

```java
// Manager -> Kafka 전송 Flow
@Bean
public IntegrationFlow outboundChunkFlow(
    KafkaTemplate<Long, ChunkRequest> kafkaTemplate,
    ChunkRequestPartitionRouter chunkRequestPartitionRouter
) {
    KafkaProducerMessageHandler<Long, ChunkRequest> messageHandler = new KafkaProducerMessageHandler<>(kafkaTemplate);
    messageHandler.setTopicExpression(new LiteralExpression("chunk-request")); // 요청용 토픽
    // 청크 순번(sequence)을 기반으로 워커(파티션)에게 분배하는 전략
    messageHandler.setPartitionIdExpression(new FunctionExpression<>(
        chunkRequestPartitionRouter::routeToKafkaPartition));

    return IntegrationFlow
        .from(outboundChunksToWorkers()) // 출구 채널로부터 데이터를 받아
        .log()
        .handle(messageHandler) // Kafka로 발사
        .get();
}

// 카프카 파티션 분산 로직 (Round-robin 효과)
public static class ChunkRequestPartitionRouter {
    private final int partitionSize;
    public ChunkRequestPartitionRouter(int partitionSize) { this.partitionSize = partitionSize; }

    public Long routeToKafkaPartition(Message<ChunkRequest> message) {
        ChunkRequest chunkRequest = message.getPayload();
        int chunkSequence = chunkRequest.getSequence();
        long partitionId = chunkSequence % partitionSize; // 순번에 따른 파티션 결정
        return partitionId;
    }
}
```

## 3장. Worker 타격 플랫폼: 청크 수신과 결과 보고

Worker 노드는 Manager로부터 배송된 '데이터 핵탄두'를 받아 실제로 가공하고 결과를 보고하는 처형장입니다.

### 1. Worker Integration Flow 및 로직 분석

`RemoteChunkingWorkerBuilder`를 사용하여 메시지 수신과 처리 흐름을 정의합니다.

```java
@Bean
public IntegrationFlow workerIntegrationFlow() {
    return this.remoteChunkingWorkerBuilder
        .inputChannel(inboundChunkRequestsFromManager()) // Manager의 명령을 받는 입구
        .outputChannel(outboundRepliesToManager()) // 결과 보고서를 보낼 출구
        .itemProcessor(nuclearStrikeProcessor()) // 수신된 데이터를 분석하고 가공
        .itemWriter(damageReportWriter()) // 가공된 결과를 실제 저장소에 기록
        .build();
}
```

* **itemProcessor / itemWriter:** 원격 청킹의 진정한 목적입니다. 가장 부하가 큰 이 두 단계를 Worker들이 병렬로 나누어 집행합니다.

### 2. 내부 처리 메커니즘: ChunkProcessorChunkHandler

Manager로부터 메시지가 오면 `ChunkProcessorChunkHandler`가 가동됩니다.

* **작동 원리:** 수신된 `ChunkRequest`에서 데이터를 꺼내 `SimpleChunkProcessor`에게 전달합니다. 처리가 끝나면 `ChunkResponse`를 생성하여 Manager에게 돌려보냅니다.

### 3. 결과 취합(Aggregation)의 마법

Worker가 보낸 `ChunkResponse`에는 가장 중요한 정보인 **stepContribution**이 담겨 있습니다.

```java
// ChunkResponse의 핵심 역할
public class ChunkResponse implements Serializable {
    private final StepContribution stepContribution; // Worker가 처리한 '부분 전과 기록'
    // ...
}
```

* **메커니즘:** Manager는 네트워크를 통해 응답을 받을 때마다, 각 응답의 `stepContribution` 값을 **자신의 메인 StepExecution 상태 정보에 계속해서 합산(Aggregate)**합니다.
* **결과:** 이를 통해 원격지의 작업을 중앙에서 실시간 파악하고, 전체 처리가 끝났을 때 정확한 성공/실패 상태를 결정합니다.

### 4. 필수 보급품: SerDes(직렬화/역직렬화)

객체를 네트워크로 보내기 위해서는 전용 변환기가 필요합니다.

```yaml
# application.yml 설정 예시 (Manager 측)
spring:
  kafka:
    producer:
      value-serializer: com.system.batch.killbatchsystem.ChunkRequestSerDes$ChunkRequestSerializer
    consumer:
      value-deserializer: com.system.batch.killbatchsystem.ChunkResponseSerDes$ChunkResponseDeserializer
```

* **주의:** Manager는 요청을 **직렬화**하고 응답을 **역직렬화**해야 하며, Worker는 그 반대로 설정해야 합니다.

## [개념 검증용 자가 진단 질문]

### 원격 청킹 아키텍처 및 데이터 전파 메커니즘 진단

1. 원격 파티셔닝(Remote Partitioning)과 원격 청킹(Remote Chunking)은 모두 분산 처리를 수행하지만, 데이터의 '위치'와 '이동' 관점에서 결정적인 차이가 무엇인지 설명하고, 왜 원격 청킹이 네트워크 대역폭(Bandwidth) 측면에서 더 위험한 선택이 될 수 있는지 논술하시오.
2. `ChunkMessageChannelItemWriter`가 Manager 노드에서 수행하는 역할은 일반적인 `ItemWriter`와 어떻게 다르며, Worker로부터 돌아온 `ChunkResponse` 속의 `StepContribution`이 Manager의 `StepExecution` 통계치에 어떻게 반영되어 최종 작전 성공 여부를 결정하게 되는지 그 인과관계를 기술하시오.
3. 원격 청킹 작전에서 Manager의 `reader()`가 읽기 속도가 매우 느린 레거시 시스템일 경우, Worker 노드를 아무리 늘려도 전체 처리 속도가 개선되지 않는 아키텍처적 원인은 무엇이며, 이 상황에서 `RemoteChunkingManagerStepBuilderFactory`를 사용하는 것이 비효율적인 이유를 설명하시오.

<details>
<summary>💡 자가 진단 질문 정답 및 해설 보기</summary>

* **1번 질문 해설:** 원격 파티셔닝은 데이터가 있는 위치의 '좌표(범위)'만 보내고 워커가 직접 조회하게 하지만, 원격 청킹은 매니저가 직접 읽은 '데이터 본체(Items)'를 메시지에 실어 보냅니다. 따라서 원격 청킹은 데이터 자체가 네트워크를 타고 이동하므로, 데이터 크기가 크거나 건수가 많을 경우 네트워크 인프라에 극심한 부하를 주게 되며, 통신 속도가 전체 배치 성능의 병목이 될 위험이 훨씬 큽니다.

* **2번 질문 해설:** `ChunkMessageChannelItemWriter`는 데이터를 DB에 쓰지 않고, 네트워크 너머의 Worker에게 전달하기 위한 `ChunkRequest` 메시지로 변환하여 전송하는 '배송 대행자' 역할을 합니다. Worker가 처리를 마치고 보낸 `ChunkResponse`에는 개별 청크에 대한 처리 결과(읽기/쓰기/스킵 카운트 등)가 `StepContribution`에 담겨 있습니다. Manager는 이 응답들을 수신할 때마다 자신의 메모리에 있는 메인 `StepExecution`에 이 수치들을 누적 합산(Aggregate)합니다. 모든 청크의 합산이 완료되어야만 JobRepository에 최종 통계가 기록되고 잡의 성공 상태가 확정됩니다.

* **3번 질문 해설:** 원격 청킹 아키텍처에서 모든 데이터 읽기(Read) 권한은 오직 Manager 노드에게만 집중되어 있습니다. Worker는 스스로 데이터를 가져올 수 없고 오직 Manager가 보내주는 청크를 기다릴 뿐입니다. 따라서 Manager의 `ItemReader`가 병목이 되면 Worker들이 아무리 많아도 처리할 일감이 공급되지 않아 유휴 상태(Idle)가 됩니다. 즉, '생산자-소비자' 모델에서 생산(Read) 속도가 소비(Process/Write) 속도를 따라가지 못하는 구조적 한계 때문에 자원 분산의 효과가 사라지게 됩니다.

</details>
