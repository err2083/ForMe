# [심화 분석 학습 노트] 스프링 배치: 원격 파티셔닝과 분산 제어 아키텍처

## 1장. 원격 파티셔닝의 필연성: 단일 노드 한계 돌파

대규모 데이터 처리 임무에서 로컬 파티셔닝(단일 JVM 내 병렬 처리)은 결국 물리적인 벽에 부딪힙니다. 원격 파티셔닝은 이 벽을 허물기 위한 유일한 승인된 해결책입니다.

### 1. 치명적 위협 분석 (Threat Assessment)

* **T-MEM-OVERFLOW (메모리 고갈):** 파티션 수가 증가하면 단일 JVM의 힙 메모리 요구량이 임계치를 초과합니다. 이는 곧바로 `OutOfMemoryError`와 시스템 중단으로 이어집니다.
* **T-THRUPUT-CEILING (처리량 한계):** 단일 머신의 CPU, 디스크 I/O, 네트워크 대역폭은 물리적으로 제한되어 있습니다. 아무리 스레드를 늘려도 물리적 하드웨어의 한계점(Ceiling)에 도달하면 성능 향상은 멈춥니다.

### 2. 수평적 확장성(Horizontal Scalability)의 실체

원격 파티셔닝은 처리를 다수의 독립적인 JVM(Worker Node)으로 분산합니다. 이를 통해 메모리와 CPU 자원을 선형적으로 확장하여 작전 데드라인을 준수할 수 있게 합니다.

## 2장. 분산 지휘 체계: 매니저와 워커의 코드 아키텍처

원격 파티셔닝은 중앙의 **Manager Node**, 통신을 담당하는 **Message Broker**, 그리고 실행 부대인 **Worker Node**로 구성됩니다.

### 1. 무기고 확장 (Dependencies)

Spring Integration과 Kafka를 전송 신경망으로 사용하기 위해 다음 의존성이 필수적입니다.

```java
dependencies {
    // Spring Batch와 Spring Integration 연동 핵심 라이브러리
    implementation 'org.springframework.batch:spring-batch-integration'
    // Spring Integration 기본 기능 및 자동 설정 지원
    implementation 'org.springframework.boot:spring-boot-starter-integration'
    // Spring Kafka 클라이언트 및 Integration 연동 지원
    implementation 'org.springframework.kafka:spring-kafka'
    implementation 'org.springframework.integration:spring-integration-kafka'
}
```

### 2. Manager Node: 전략적 지휘 및 명령 하달

매니저는 작업을 분할하고 워커에게 메시지를 발송하는 사령부입니다.

#### [ManagerConfiguration 분석]

```java
@Profile("manager")
@EnableBatchIntegration // Spring Batch Integration 핵심 컴포넌트 활성화
@Configuration
@AllArgsConstructor
public class ManagerConfiguration {
    private final JobRepository jobRepository;
    // 원격 파티셔닝 전용 매니저 스텝 빌더 팩토리
    private final RemotePartitioningManagerStepBuilderFactory remotePartitioningManagerStepBuilderFactory;
    private final DailyTimeRangePartitioner dailyTimeRangePartitioner;

    @Bean
    public Step managerStep() {
        return remotePartitioningManagerStepBuilderFactory.get("managerStep")
            .partitioner("workerStep", dailyTimeRangePartitioner) // 데이터 분할 전략 설정
            .gridSize(4) // 파티션 개수 설정
            .outputChannel(outboundRequestsToWorkers()) // 명령을 내보낼 통로 지정
            .build();
    }

    @Bean
    public DirectChannel outboundRequestsToWorkers() {
        return new DirectChannel(); // 메시지 전송을 위한 기본 채널
    }
}
```

* **RemotePartitioningManagerStepBuilderFactory:** 원격 작업을 위해 `MessageChannelPartitionHandler`를 자동으로 구성해주는 특수 빌더를 제공합니다.
* **outputChannel():** 생성된 파티션 요청(`StepExecutionRequest`)이 메시지 브로커로 전달되는 시작점입니다.

### 3. Worker Node: 독립적 처형 및 임무 수행

워커는 매니저의 명령을 수신하여 실제 데이터 로직을 집행합니다.

#### [WorkerConfiguration 분석]

```java
@Profile("worker")
@EnableBatchIntegration
@Configuration
@AllArgsConstructor
public class WorkerConfiguration {
    // 워커 스텝 구성을 위한 전용 팩토리
    private final RemotePartitioningWorkerStepBuilderFactory remotePartitioningWorkerStepBuilderFactory;

    @Bean
    public Step workerStep() {
        return remotePartitioningWorkerStepBuilderFactory.get("workerStep")
            .inputChannel(inboundRequestsFromManager()) // 명령을 받을 통로 지정
            .itemReader(reader())
            .itemProcessor(processor())
            .itemWriter(writer())
            .build();
    }

    @Bean
    public QueueChannel inboundRequestsFromManager() {
        return new QueueChannel(); // 비동기 처리를 위해 메시지를 저장하는 큐 채널
    }
}
```

* **inputChannel():** 메시지 브로커로부터 도착한 `StepExecutionRequest`를 수신하는 지점입니다. 수신 자체가 워커 스텝 실행의 트리거가 됩니다.

## 3장. 내부 동작의 진실: 메시징 프로토콜과 결과 취합

단순한 데이터 전송이 아닙니다. 원격 파티셔닝은 **메시지와 메타데이터 저장소의 정교한 협력**으로 완성됩니다.

### 1. StepExecutionRequest: 경량화된 명령서

매니저가 워커에게 보내는 메시지 페이로드에는 실제 데이터가 담기지 않습니다. 오직 다음 세 가지 식별자만 포함됩니다.

* **stepName:** 실행할 워커 스텝의 이름.
* **jobExecutionId:** 현재 실행 중인 잡의 식별자.
* **stepExecutionId:** 처리해야 할 파티션의 식별자.

### 2. 워커의 데이터 복원 메커니즘

워커는 메시지를 받으면 `StepExecutionRequestHandler`를 통해 작전을 수행합니다.

#### [StepExecutionRequestHandler.handle() 내부]

```java
public StepExecution handle(StepExecutionRequest request) {
    // 1. 메시지에서 ID 추출
    Long jobExecutionId = request.getJobExecutionId();
    Long stepExecutionId = request.getStepExecutionId();

    // 2. JobExplorer를 사용하여 중앙 DB(JobRepository)에서 실제 StepExecution 조회
    // 여기에 파티션 범위 정보(ExecutionContext)가 들어있다!
    StepExecution stepExecution = jobExplorer.getStepExecution(jobExecutionId, stepExecutionId);

    // 3. StepLocator로 워커 스텝 빈을 찾아 실행
    String stepName = request.getStepName();
    Step step = stepLocator.getStep(stepName);
    step.execute(stepExecution); // 실제 비즈니스 로직 집행

    return stepExecution; // 결과 반환
}
```

* **핵심 원리:** 데이터 자체를 전송하지 않고 ID만 보낸 뒤 워커가 직접 DB에서 상세 정보를 조회하게 함으로써 네트워크 부하를 최소화합니다.

### 3. 결과 취합(Aggregation)의 두 가지 전략

매니저는 워커들이 임무를 마쳤는지 어떻게 알 수 있을까요?

* **전략 1: 저장소 폴링 (Default Polling):** 매니저가 주기적으로(기본 10초) DB를 조회하여 모든 워커의 상태가 `COMPLETED`인지 확인합니다. 설정이 간단하지만 반응성이 느립니다.
* **전략 2: 메시지 기반 응답 (Messaging Replies):** 워커가 완료 후 응답 메시지를 보내고 매니저가 이를 수집합니다. 반응성이 뛰어나며 `correlationId`와 `sequenceSize` 헤더를 통해 그룹핑 및 완료 여부를 판단합니다.

## [개념 검증용 자가 진단 질문]

### 원격 파티셔닝 분산 아키텍처 심화 진단

1. 원격 파티셔닝 작전에서 매니저 노드가 워커 노드에게 `StepExecutionRequest` 메시지를 보낼 때, 파티션 범위 정보가 담긴 `ExecutionContext`를 메시지에 직접 포함하지 않고 오직 **ID 식별자들만 전송하는 아키텍처적 의도**와 이 방식이 전제하는 **인프라적 제약 조건**은 무엇인가?
2. `MessageChannelPartitionHandler`가 워커의 작업 결과를 취합할 때 사용하는 **'메시징 기반 응답(Messaging-based Replies)'** 방식에서, 비동기적으로 도착하는 여러 워커의 응답들이 서로 뒤섞이지 않고 특정 잡 실행에 정확히 매핑되기 위해 Spring Integration이 사용하는 **두 가지 핵심 헤더 정보**와 그 동작 원리를 논술하시오.
3. 원격 파티셔닝은 성능 면에서 강력하지만 실무적으로 **'복잡성의 괴물'**이라 불린다. 특히 상태 관리를 위해 반드시 **공유된 메타데이터 저장소(RDB)**를 사용해야만 하는 이유는 무엇이며, 이 제약이 메모리 기반 `JobRepository`를 선호하는 소규모/경량 배치 환경에서 어떤 설계적 충돌을 일으키는지 설명하시오.

* **1번 질문 해설:** 매니저가 ID만 전송하는 이유는 네트워크 전송 부하를 최소화하고 데이터 정합성을 중앙 집중적으로 관리하기 위해서입니다. 메시지 브로커를 통해 거대한 객체를 주고받는 것은 비효율적이며 보안상 위험할 수 있습니다. 대신 워커가 ID를 받아 직접 DB에서 정보를 조회하게 합니다. 이 방식이 작동하려면 **모든 매니저와 워커 노드가 동일한 중앙 메타데이터 저장소(JobRepository)에 접근할 수 있어야 한다**는 물리적인 인프라 제약이 필수적입니다.

* **2번 질문 해설:** 핵심 헤더는 `correlationId`와 `sequenceSize`입니다. `correlationId`는 동일한 잡과 스텝 실행에 속하는 모든 메시지에 부여되는 고유 식별자로, 이를 통해 흩어져서 도착하는 응답들을 하나의 그룹으로 묶습니다. `sequenceSize`는 해당 그룹에 포함된 총 파티션 개수를 나타냅니다. 매니저 노드의 Aggregator는 `correlationId`가 같은 응답이 `sequenceSize`만큼 모였는지를 확인하여 전체 작업의 완료 여부를 판단하고 최종 결과를 도출합니다.

* **3번 질문 해설:** 원격 파티셔닝은 매니저가 생성한 실행 이력(StepExecution)을 원격의 워커가 조회하고 업데이트해야 합니다. 각 노드는 독립적인 JVM 메모리를 가지므로 메모리 기반 저장소로는 이 상태를 공유할 수 없습니다. 따라서 원격 노드 간의 상태 동기화를 위해 무거운 RDB 기반의 `JobRepository`가 강제됩니다. 이는 DB 의존성을 없애고 단순하게 운영하려는 경량 배치 설계 철학과 정면으로 충돌하며, 시스템 구축 및 운영 비용(메시지 브로커 + 공유 DB)을 급격히 상승시키는 원인이 됩니다.
