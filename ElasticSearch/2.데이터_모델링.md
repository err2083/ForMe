# [Mastering Elasticsearch: 텍스트 분석 및 데이터 모델링 심화 학습 노트]

## 제 1장: ES Analyzer 구조와 토큰 스트림 변환 파이프라인

엘라스틱서치에서 텍스트 데이터가 검색 가능하게 되는 핵심 과정인 '분석(Analysis)'은 **Character Filters, Tokenizer, Token Filters**라는 세 가지 컴포넌트가 순차적으로 상호작용하며 수행됩니다.

### 1. Analyzer의 내부 구성 요소 분석

* **Character Filters (문자 필터):** 텍스트 분석의 가장 앞단에서 원문(Raw Text)을 정제합니다. 텍스트가 토크나이저에 전달되기 전, HTML 태그를 제거(`html_strip`)하거나 특정 문자를 다른 문자로 치환(`mapping`)하는 역할을 수행합니다. 한 분석기는 0개 이상의 문자 필터를 가질 수 있습니다.
* **Tokenizer (토크나이저):** 분석기의 심장부로, 단 하나의 토크나이저만 설정 가능합니다. 문자 스트림을 받아서 단어 단위인 '토큰(Token)'으로 분리하고 토큰 스트림을 생성합니다. 분리 시 각 토큰의 시작/종료 오프셋과 위치(Position) 정보를 기록하여 문구 검색(Phrase Search) 정보를 생성합니다.
* **Token Filters (토큰 필터):** 토크나이저에 의해 분리된 토큰 스트림을 후가공합니다. 대문자를 소문자로 변환(`lowercase`), 불용어 제거(`stop`), 동의어 추가(`synonym`), 혹은 단어를 어근으로 축약(`stemmer`)하는 작업을 수행합니다. 필터는 설정된 순차적 파이프라인에 따라 실행되므로 순서가 결과에 큰 영향을 미칩니다.

### 2. 내부 파이프라인의 인과관계 과정

1. **입력:** 유저가 전송한 원문 텍스트가 입력됩니다.
2. **정제 (Char Filter):** 문자 필터가 문장 내 불필요한 노이즈를 제거합니다. 예를 들어 `&`를 `and`로 바꾸어 의미적 일관성을 확보합니다.
3. **분리 (Tokenizer):** 정제된 문자열이 토크나이저를 거치며 개별 토큰으로 쪼개집니다. `standard` 토크나이저는 유니코드 텍스트 세그먼테이션 알고리즘을 사용해 단어 경계를 찾습니다.
4. **변환 및 필터링 (Token Filter):** 분리된 토큰들이 필터를 거쳐 정규화됩니다. 예를 들어 `Quick` 토큰이 `lowercase` 필터를 지나 `quick`이 됨으로써 대소문자 구분 없는 검색을 가능케 합니다.
5. **최종 출력:** 모든 과정을 거친 '토큰 스트림'이 역색인(Inverted Index)에 저장됩니다.

## 제 2장: 명시적 매핑(Explicit Mapping)과 멀티 필드 설계

엘라스틱서치에서 필드 타입은 검색 성능과 메모리 사용량에 직결됩니다. 특히 문자열 데이터를 `text`와 `keyword` 두 가지 목적으로 모두 활용하기 위해 **멀티 필드(Multi-fields)** 설계가 필수적입니다.

### 1. Text vs Keyword의 본질적 차이

* **Text 타입:** 전문 검색(Full-text search)을 위해 설계되었습니다. 분석기를 거쳐 역색인이 생성되며, 문장 속 단어를 찾는 데 최적화되어 있습니다.
* **Keyword 타입:** 분석 과정을 거치지 않고 입력값 그대로 색인됩니다. 정확한 일치(Exact match), 필터링, 정렬, 집계(Aggregation)에 사용됩니다.

### 2. 노리(Nori) 분석기를 적용한 명시적 매핑 설계
한국어 형태소 분석기인 `nori`를 사용하여 전문 검색용 `text` 필드를 정의하고, 동일 필드를 집계용 `keyword`로도 사용하는 멀티 필드 매핑 JSON 예시입니다.

```json
PUT /korean_products
{
  "settings": {
    "analysis": {
      "analyzer": {
        "nori_search_analyzer": {
          "type": "custom",
          "tokenizer": "nori_user_dict_tokenizer",
          "filter": [
            "nori_readingform",
            "lowercase",
            "nori_part_of_speech"
          ]
        }
      },
      "tokenizer": {
        "nori_user_dict_tokenizer": {
          "type": "nori_tokenizer",
          "decompound_mode": "mixed",
          "user_dict": "user_dic.txt"
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "product_name": {
        "type": "text",
        "analyzer": "nori_search_analyzer",
        "fields": {
          "raw": {
            "type": "keyword"
          }
        }
      },
      "price": {
        "type": "integer"
      },
      "description": {
        "type": "text",
        "analyzer": "nori_search_analyzer"
      }
    }
  }
}
```

**[코드 라인별 상세 분석]**
* **`"decompound_mode": "mixed"`**: 복합 명사를 분해하는 방식 설정입니다. `mixed`는 복합 명사를 전체로도 저장하고 개별 어근으로도 쪼개어 검색 정확도를 높입니다.
* **`"user_dict": "user_dic.txt"`**: 사용자 사전을 등록하여 신조어나 브랜드명이 잘못 분석되는 것을 방지합니다.
* **`"nori_part_of_speech"`**: 한국어의 조사나 어미 등 검색에 불필요한 품사를 필터링합니다.
* **`"fields": { "raw": { "type": "keyword" } }`**: `product_name` 필드 하나로 `product_name`으로는 전문 검색을, `product_name.raw`로는 정확한 상품명 정렬 및 집계를 수행할 수 있게 합니다.

## 제 3장: Dynamic Mapping의 메커니즘과 아키텍처적 한계

엘라스틱서치는 매핑 정의 없이 데이터를 입력받으면 내부 엔진이 타입을 추론하는 **Dynamic Mapping**을 지원합니다.

### 1. 내부 메커니즘

엘라스틱서치는 JSON 문서의 데이터 값을 보고 타입을 추측합니다.
* 숫자만 있으면 `long` 혹은 `float`으로, 따옴표로 감싸진 문자열은 `text` 필드이면서 하위에 `keyword` 멀티 필드를 가진 구조로 자동 생성합니다.
* 날짜 형식 문자열은 `date` 타입으로 감지(`date_detection`)하려 시도합니다.

### 2. 아키텍처적 한계와 프로덕션 위험성

* **매핑 폭발(Mapping Explosion):** 로그 데이터처럼 키값이 무작위로 생성되는 문서를 다이나믹 매핑으로 받을 경우, 인덱스 매핑 필드 수가 기하급수적으로 늘어납니다. 이는 클러스터 상태(Cluster State) 정보를 비대하게 만들어 메모리 부족과 성능 저하를 야기합니다.
* **잘못된 타입 추론:** 특정 필드의 첫 번째 데이터가 숫자로 들어와 `long`으로 결정되면, 이후 들어오는 소수점 데이터나 문자열 데이터는 타입 불일치로 색인에 실패하게 됩니다.
* **분석기 제어 불가:** 문자열 필드는 기본적으로 `standard` 분석기가 적용되므로, 한국어와 같은 언어 특화 분석기를 자동으로 적용할 수 없습니다.

### 3. 명시적 매핑 강제(Strict Mode) 권장 이유

프로덕션 환경에서는 시스템의 안정성과 데이터 정합성을 위해 명시적 매핑을 강제해야 합니다.

```json
PUT /my_production_index
{
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "user_id": { "type": "keyword" },
      "message": { "type": "text" }
    }
  }
}
```

* **`"dynamic": "strict"`**: 매핑에 정의되지 않은 필드가 포함된 문서가 들어오면 색인을 거부하고 에러를 발생시킵니다. 이는 개발 단계에서 데이터 구조 변경을 엄격히 관리하게 하며, 예상치 못한 필드 추가로 인한 장애를 방지하는 강력한 보호막 역할을 합니다.

### [텍스트 분석 및 매핑 아키텍처 자가 진단]

1. **상황:** `nori` 분석기를 사용하여 "엘라스틱서치 검색"이라는 문장을 색인했습니다. 만약 `Tokenizer` 단계 이후에 `Token Filter`에서 모든 조사를 제거하도록 설정했다면, 내부 파이프라인의 각 단계에서 데이터는 어떻게 변하며 최종적으로 '역색인' 구조에 미치는 영향은 무엇인지 인과관계 중심으로 서술하세요.
2. **상황:** 멀티 필드(Multi-fields)를 설계할 때, 전문 검색용 필드에는 `nori` 분석기를 적용하고 정렬용 하위 필드에는 왜 `keyword` 타입을 지정해야 하는지, 만약 정렬용 필드에도 `nori` 분석기가 적용된 `text` 타입을 사용한다면 어떤 기술적 문제가 발생하는지 분석하세요.
3. **상황:** 대규모 로그 수집 시스템에서 `dynamic: true` 설정을 유지했을 때, 수천 명의 유저가 서로 다른 키값으로 JSON 로그를 전송할 경우 '매핑 폭발(Mapping Explosion)'이 발생하는 내부 메커니즘과 이것이 클러스터의 안정성(Master Node 부하 등)에 미치는 영향을 설명하세요.
