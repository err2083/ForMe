# [Elasticsearch 분산 아키텍처 및 고가용성 심화 분석 학습 노트]

## 제 1장: 노드(Node)의 역할 분담 아키텍처와 상호작용

엘라스틱서치는 분산 시스템으로서 각 노드가 특정 역할을 수행하며 클러스터를 유지합니다. 노드는 실행 중인 엘라스틱서치 인스턴스이며, 동일한 `cluster.name`을 가진 노드들이 모여 하나의 클러스터를 형성합니다.

### 1. 마스터 노드(Master Node)와 데이터 노드(Data Node)의 역할

* **마스터 노드(Master Node):** 클러스터 전체의 조율을 담당합니다. 인덱스 생성 및 삭제, 클러스터에 참여하거나 탈퇴하는 노드 관리 등 **클러스터 수준의 메타데이터 변경**을 전담합니다.
* **데이터 노드(Data Node):** 실제 **데이터의 색인(Indexing)과 검색(Search)**을 담당합니다. 문서 수준의 CRUD 작업과 집계 연산이 수행되는 곳입니다.
* **코디네이팅 노드(Coordinating Node):** 유저의 요청을 처음 받는 노드입니다. 마스터 노드를 포함한 클러스터 내 모든 노드는 코디네이팅 노드 역할을 할 수 있으며, 요청을 분석하여 데이터가 있는 샤드로 라우팅하고 결과를 취합(Gathering)하여 반환합니다.

### 2. 내부 설정 및 안정성 확보 (elasticsearch.yml)

프로덕션 환경에서는 클러스터의 안정성을 위해 아래와 같은 설정을 반드시 관리해야 합니다.

```yaml
# 클러스터 이름 설정: 동일 네트워크 내 다른 클러스터와 섞이지 않도록 방지함
cluster.name: elasticsearch_production

# 노드 이름 설정: 장애 발생 시 로그에서 물리적 서버를 즉시 식별하기 위함
node.name: es_node_001_data

# 네트워크 호스트: 외부 통신을 위해 바인딩할 IP 주소
network.host: 192.168.1.10

# 유니캐스트 호스트 리스트: 노드가 클러스터에 참여하기 위해 통신할 초기 대상 목록
discovery.zen.ping.unicast.hosts: ["host1", "host2"]

```

* **`cluster.name`**: 기본값인 `elasticsearch`를 유지하면 우발적으로 다른 노드가 클러스터에 합류하여 데이터 재배치가 일어나는 대참사가 발생할 수 있습니다.
* **`discovery.zen.ping.unicast.hosts`**: 운영 환경에서는 멀티캐스트 대신 유니캐스트를 사용하여 명시적으로 정의된 노드들하고만 통신해야 클러스터 형성이 안정적입니다.

특히 **Split Brain(뇌분할)** 현상을 방지하기 위해 `minimum_master_nodes` 설정이 결정적입니다.

```json
# 동적 설정을 통한 최소 마스터 후보 노드 수 지정
PUT /_cluster/settings
{
  "persistent" : {
    "discovery.zen.minimum_master_nodes" : 2
  }
}
```

* **`discovery.zen.minimum_master_nodes`**: 마스터 선출에 필요한 최소 투표권 수를 정의합니다. 공식은 `(마스터 후보 노드 수 / 2) + 1`이며, 이를 통해 네트워크 단절 시 클러스터가 두 개로 갈라져 각각 마스터를 선출하는 상황을 방지합니다.

## 제 2장: 샤드(Shard) 분산과 데이터 라우팅 메커니즘

엘라스틱서치는 데이터를 **샤드**라는 단위로 쪼개어 노드에 분산 저장합니다.

### 1. 프라이머리 샤드(Primary Shard)와 레플리카 샤드(Replica Shard)

* **프라이머리 샤드:** 데이터의 **원본**이며, 인덱스 생성 시 개수가 고정됩니다. 모든 쓰기 작업은 먼저 프라이머리 샤드에서 완료된 후 레플리카로 복제됩니다.
* **레플리카 샤드:** 프라이머리의 **복사본**입니다. 하드웨어 장애 시 데이터 유실을 방지(Failover)하고, 검색 요청을 분산 처리하여 읽기 성능을 향상시킵니다. 레플리카 개수는 운영 중 동적으로 변경 가능합니다.

### 2. 도큐먼트 라우팅 공식과 구조적 한계

문서가 유입될 때 엘라스틱서치는 아래의 **해시 기반 라우팅 공식**을 통해 저장될 샤드 번호를 결정합니다.

**라우팅 공식:**
`shard = hash(routing) % number_of_primary_shards`

* **`routing`**: 기본적으로 문서의 `_id` 값이 사용되지만, 특정 필드를 지정할 수도 있습니다.
* **`number_of_primary_shards`**: 인덱스가 가진 총 프라이머리 샤드 개수입니다.
* **구조적 불가 변성**: 인덱스 생성 후 **프라이머리 샤드 개수를 변경할 수 없는 이유**가 여기에 있습니다. 만약 분모인 샤드 개수가 바뀌면, 기존에 저장된 문서들의 해시 결과값이 달라져 검색 시 해당 문서를 찾을 수 없게 됩니다. 따라서 용량이 부족할 경우 더 많은 샤드를 가진 새로운 인덱스를 만들어 데이터를 옮기는 **Reindex** 과정이 필요합니다.

## 제 3장: 장애 조치(Failover) 및 샤드 재배치(Rebalancing)

엘라스틱서치는 노드 장애 시 마스터 노드의 주도하에 클러스터의 건강 상태를 회복합니다.

### 1. 클러스터 상태(Cluster State)의 변화

* **Green:** 모든 프라이머리 샤드와 레플리카 샤드가 활성화되어 노드에 정상 할당된 상태입니다.
* **Yellow:** **모든 프라이머리 샤드는 활성화**되어 서비스는 가능하지만, 일부 레플리카 샤드가 할당되지 않은 상태입니다. 노드 하나가 다운되어 해당 노드에 있던 레플리카가 유실되었을 때 주로 발생합니다.
* **Red:** **하나 이상의 프라이머리 샤드가 유실**된 상태입니다. 데이터 일부에 접근할 수 없으며 검색 결과가 불완전해집니다.

### 2. 장애 조치 및 재배치 내부 흐름 (인과관계)

특정 데이터 노드가 다운되었을 때의 복구 프로세스는 다음과 같습니다.

1. **장애 감지:** 마스터 노드가 해당 노드의 연결 끊김을 인지합니다.
2. **새 마스터 선출(필요 시):** 다운된 노드가 마스터였다면, 남은 마스터 후보 노드들이 투표를 통해 새 마스터를 선출합니다.
3. **레플리카 승격(Promotion):** 유실된 프라이머리 샤드의 복제본(Replica)이 다른 노드에 존재한다면, 마스터는 해당 **레플리카를 즉시 프라이머리로 승격**시킵니다. 이 과정은 즉각적으로 일어나며 상태는 **Yellow**가 됩니다.
4. **샤드 재배치(Rebalancing):** 클러스터에 여유 노드가 있다면, 마스터는 유실된 레플리카 개수를 채우기 위해 새로운 복제본 생성을 지시하거나, 노드 간 샤드 개수 균형을 맞추기 위해 샤드를 이동시킵니다.
5. **복구 완료:** 모든 샤드가 복제 및 할당되면 클러스터 상태는 다시 **Green**으로 돌아옵니다.

**대규모 클러스터 재시작 시 팁:**
노드들이 순차적으로 켜질 때 불필요한 재배치를 막기 위해 아래 설정을 활용합니다.

```yaml
# 8개의 노드가 합류할 때까지 복구 프로세스 대기
gateway.recover_after_nodes: 8
# 10개의 노드가 다 모이거나, 혹은 8개 합류 후 5분을 기다린 뒤 복구 시작
gateway.expected_nodes: 10
gateway.recover_after_time: 5m
```

* **`recover_after_nodes`**: 최소 이 정도 노드는 모여야 데이터 복구를 시작하라는 지침으로, 네트워크 지연으로 인한 샤드 복제 비용을 절감해 줍니다.

### [분산 아키텍처 및 고가용성 메커니즘 자가 진단]

1. **상황:** 3대의 마스터 후보 노드로 구성된 클러스터에서 네트워크 파티션 장애로 인해 1번 노드와 나머지 2, 3번 노드 간의 통신이 단절되었습니다. 이때 `minimum_master_nodes` 설정이 2로 되어 있을 때와 1로 되어 있을 때, 클러스터의 마스터 선출 방식과 데이터 정합성 관점에서 어떤 차이가 발생하는지 기술하세요.
2. **상황:** 현재 5개의 프라이머리 샤드로 구성된 인덱스에 데이터가 가득 차서 검색 성능이 저하되었습니다. 인프라 팀에서 데이터 노드 5대를 추가로 증설했지만, 특정 인덱스의 검색 속도는 개선되지 않았습니다. 라우팅 공식과 샤드의 물리적 배치 관점에서 이 현상이 왜 발생하는지, 그리고 아키텍처적으로 이를 해결하려면 어떤 작업을 수행해야 하는지 설명하세요.
3. **상황:** 데이터 노드 하나가 불시에 종료되어 클러스터 상태가 `Yellow`로 변했습니다. 이후 마스터 노드가 유실된 프라이머리 샤드를 복구하기 위해 수행하는 '레플리카 승격' 단계부터 '샤드 재배치'까지의 과정을 하드웨어 자원(네트워크, 디스크 I/O) 사용의 인과관계와 연계하여 상세히 서술하세요.

- **1번 질문 해설:**
    * **설정이 2인 경우:** 2, 3번 노드 구역은 과반수(Quorum)를 만족하므로 새 마스터를 선출하고 정상 작동합니다. 반면 1번 노드 구역은 투표권 부족으로 마스터가 될 수 없어 서비스를 중단합니다. 이는 데이터 정합성을 지키는 정상적인 동작입니다.
    * **설정이 1인 경우:** 1번 노드도 스스로 마스터가 되고, 2, 3번 구역에서도 마스터가 선출되어 **Split Brain** 상태가 됩니다. 양쪽 구역에서 서로 다른 데이터를 쓰게 되어 나중에 네트워크가 복구되어도 데이터를 합칠 수 없는 심각한 정합성 오류가 발생합니다.

- **2번 질문 해설:**
    * **원인:** 엘라스틱서치의 라우팅 공식(`hash % shard_count`)에 따라 프라이머리 샤드 개수는 생성 시점에 고정됩니다. 노드를 5대에서 10대로 늘려도, 이미 생성된 인덱스의 프라이머리 샤드가 5개뿐이라면 각 샤드는 최대 5대의 노드에만 분산될 수 있습니다. 나머지 5대의 신규 노드는 해당 인덱스의 검색 작업에 참여할 샤드가 없어 자원이 유휴 상태가 됩니다.
    * **해결책:** 샤드 개수를 늘리기 위해 인덱스를 직접 수정할 수는 없으므로, 더 많은 프라이머리 샤드(예: 10개)를 가진 새로운 인덱스를 생성하고 **Reindex API**를 사용하여 기존 데이터를 이관해야 합니다. 그래야만 모든 노드의 CPU/RAM을 골고루 활용할 수 있습니다.

- **3번 질문 해설:**
    * **과정:** 마스터 노드는 즉시 유실된 프라이머리 샤드의 위치를 파악하고, 다른 노드에 살아있는 레플리카 샤드를 프라이머리로 **승격**시킵니다. 이 승격은 메타데이터 업데이트이므로 네트워크 비용이 거의 들지 않는 '스위치 조작'과 같습니다.
    * **인과관계:** 하지만 승격 직후에는 레플리카 개수가 부족해지므로 클러스터는 **Yellow** 상태가 됩니다. 이를 해결하기 위해 마스터는 새로운 레플리카 샤드를 생성(복제)하도록 명령합니다. 이 단계에서 프라이머리 노드로부터 데이터를 복사해 와야 하므로 **대량의 네트워크 대역폭과 디스크 I/O 자원이 소모**됩니다. 재배치가 완료되면 모든 노드의 샤드 균형이 맞춰지고 상태는 다시 **Green**이 됩니다.
