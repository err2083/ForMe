# [Mastering Elasticsearch 8.x: 구조화된 심화 분석 학습 노트]

## 제 1장: ES 핵심 데이터 구조와 RDB의 구조적 차이

엘라스틱서치는 Apache Lucene을 기반으로 구축된 분산 검색 및 분석 엔진으로, 일반적인 관계형 데이터베이스(RDB)와는 데이터 저장 및 관리 방식에서 근본적인 차이를 보입니다.

### 1. 핵심 구성 요소의 정의

* **Index (인덱스):** RDB의 '테이블'과 유사한 개념입니다. 유사한 특성을 가진 문서들의 논리적인 집합이며, 모든 검색과 분석 작업의 대상이 됩니다.
* **Document (문서):** 인덱스에 저장되는 데이터의 기본 단위로, JSON 객체 형태입니다. RDB의 '행(Row)'에 해당하지만, 계층 구조를 가질 수 있는 유연한 스키마를 제공합니다. 각 문서는 여러 '필드(Field)'로 구성됩니다.
* **Mapping (매핑):** RDB의 '스키마' 정의와 같습니다. 문서와 그 필드들이 어떻게 저장되고 색인(Index)될지를 정의하는 과정입니다. 필드의 데이터 타입(Text, Keyword, Integer, Date 등)을 설정하고, 메타데이터 필드(예: `_source`)의 처리 방식을 결정합니다.

### 2. 구조적 분석: ES vs. RDB

RDB는 정해진 스키마에 맞춰 데이터를 저장하고 B-Tree 구조의 인덱스를 통해 '검색'보다 '무결성'과 '정규화'에 집중합니다. 반면, 엘라스틱서치는 다음과 같은 구조적 이점을 가집니다.

* **비정규화된 데이터 모델:** 복잡한 Join 연산을 피하기 위해 데이터를 비정규화하여 저장합니다. 이는 분산 환경에서 빠른 검색 성능을 보장합니다.
* **유연한 매핑:** 'Dynamic Mapping'을 통해 스키마 없이도 데이터를 바로 입력할 수 있지만, 운영 환경에서는 성능과 정확성을 위해 'Explicit Mapping'을 통해 필드 타입을 명시적으로 제어하는 것이 권장됩니다.
* **멀티 필드 활용:** 하나의 문자열 필드를 검색용 `text` 타입과 정렬/집계용 `keyword` 타입으로 동시에 색인하는 등, 목적에 따른 중복 색인이 가능합니다.

## 제 2장: 역색인(Inverted Index)의 내부 동작 원리

엘라스틱서치가 대용량 텍스트 데이터에서 RDB보다 압도적으로 빠른 검색 속도를 내는 핵심 이유는 '역색인' 구조에 있습니다.

### 1. 역색인의 생성 과정 (인과관계)

일반적인 DBMS가 "문서 ID -> 내용" 순으로 데이터를 찾는다면, 역색인은 **"단어(Token) -> 문서 ID 리스트"** 순으로 구조를 뒤집어 저장합니다.

1. **텍스트 분석(Analysis):** 문서가 색인될 때 '분석기(Analyzer)'가 텍스트를 최소 단위인 '토큰(Token)'으로 분리합니다. 이 과정에서 소문자 변환, 불용어 제거, 형태소 분석 등이 수행됩니다.
2. **용어 사전(Term Dictionary) 생성:** 추출된 토큰들을 알파벳 순으로 정렬하여 유일한 단어들의 목록을 만듭니다.
3. **포스팅 리스트(Posting List) 연결:** 각 단어가 어떤 문서(ID)에 포함되어 있는지, 어느 위치에 있는지에 대한 정보를 연결합니다.

### 2. 검색 속도가 빠른 이유

RDB에서 특정 단어를 찾으려면 `LIKE %keyword%` 쿼리를 사용하여 모든 행을 스캔(Full Table Scan)해야 합니다. 하지만 엘라스틱서치는 이미 생성된 **용어 사전**에서 단어를 즉시 찾고, 그 단어에 연결된 **포스팅 리스트**만 바로 읽어오기 때문에 데이터 양에 상관없이 매우 빠른 응답 속도를 유지할 수 있습니다.

## 제 3장: 기본 CRUD REST API (Kibana Dev Tools)

Kibana의 Dev Tools에서 직접 실행할 수 있는 JSON 기반 CRUD 명령과 각 설정의 기술적 역할을 상세히 설명합니다.

### 1. Create (문서 생성)

문서를 생성할 때는 `_doc` 엔드포인트를 사용합니다. ID를 자동 생성하거나 직접 지정할 수 있습니다.

**자동 ID 생성 (POST 사용):**

```json
curl -X POST "localhost:9200/products/_doc" -H "Content-Type: application/json" -d'
{
  "name": "블루투스 이어폰",
  "price": 49900,
  "category": "전자기기"
}'
```

* **POST:** 시스템이 고유한 문서 ID를 자동으로 생성합니다.

**지정 ID 사용 (PUT 사용):**

```json
curl -X PUT "localhost:9200/products/_doc/prod-001" -H "Content-Type: application/json" -d'
{
  "name": "블루투스 이어폰",
  "price": 49900,
  "category": "전자기기"
}'
```

* **PUT:** 특정 ID(`prod-001`)를 지정하여 문서를 생성하거나 교체합니다.

**중복 방지 (create only):**

```json
# op_type=create: 이미 존재하면 오류 발생
curl -X PUT "localhost:9200/products/_doc/prod-001?op_type=create" \
  -H "Content-Type: application/json" -d'
{
  "name": "블루투스 이어폰"
}'

# 또는 _create 엔드포인트 사용
curl -X PUT "localhost:9200/products/_create/prod-001" \
  -H "Content-Type: application/json" -d'
{
  "name": "블루투스 이어폰"
}'
```

### 2. Read (문서 조회)

```json
# 단건 조회
curl -X GET "localhost:9200/products/_doc/prod-001"

# 특정 필드만 선택 조회
curl -X GET "localhost:9200/products/_doc/prod-001?_source=name,price"

# 다건 조회 (mget)
curl -X GET "localhost:9200/products/_mget" -H "Content-Type: application/json" -d'
{
  "ids": ["prod-001", "prod-002", "prod-003"]
}'
```

* `_source`: 원본 JSON 데이터를 담고 있는 필드로, 필요한 필드만 필터링하여 네트워크 비용을 줄일 수 있습니다.

### 3. Update (문서 수정)

엘라스틱서치의 문서는 불변(Immutable)입니다. 수정 요청 시 내부적으로 기존 문서를 삭제 표시하고 새 문서를 색인합니다.

**부분 업데이트 (POST _update):**

```json
curl -X POST "localhost:9200/products/_update/prod-001" -H "Content-Type: application/json" -d'
{
  "doc": {
    "price": 59900,
    "on_sale": true
  }
}'
```

* `doc`: 변경할 필드 정보만 전달합니다.

**스크립트 기반 업데이트 (Painless 스크립트):**

```json
# 가격 10% 할인 연산
curl -X POST "localhost:9200/products/_update/prod-001" -H "Content-Type: application/json" -d'
{
  "script": {
    "source": "ctx._source.price = (int)(ctx._source.price * 0.9)"
  }
}'
```

* `script`: 프로그래밍 방식으로 필드 값을 계산하여 업데이트합니다.

**Upsert (문서가 없으면 생성, 있으면 수정):**

```json
curl -X POST "localhost:9200/products/_update/prod-999" -H "Content-Type: application/json" -d'
{
  "doc": {
    "view_count": 1
  },
  "upsert": {
    "name": "새 상품",
    "price": 10000,
    "view_count": 1
  }
}
```

### 4. Delete (문서 삭제)

```json
# 단건 삭제
curl -X DELETE "localhost:9200/products/_doc/prod-001"

# 쿼리 조건 삭제 (delete_by_query)
curl -X POST "localhost:9200/products/_delete_by_query" -H "Content-Type: application/json" -d'
{
  "query": {
    "term": { "is_active": false }
  }
}'

# 인덱스 전체 삭제
curl -X DELETE "localhost:9200/products"
```

## 제 4장: Near Real-Time(NRT)과 Refresh 메커니즘

엘라스틱서치는 'Near Real-Time' 검색 엔진입니다. 데이터가 입력된 후 검색 가능해지기까지 내부적으로 거치는 단계는 다음과 같습니다.

### 1. 내부 메커니즘 흐름

1. **In-memory Buffer:** 문서 색인 요청이 들어오면 데이터는 먼저 메모리 버퍼에 쌓입니다. 이때까지는 검색이 불가능합니다.
2. **Refresh 발생:** 버퍼에 데이터가 쌓이거나 일정 시간이 지나면, 버퍼의 내용을 새로운 **세그먼트(Segment)** 파일로 변환하여 운영체제의 **파일 시스템 캐시(System Cache)**에 기록합니다.
3. **Search Open:** 캐시에 기록된 세그먼트가 '열리게(Open)' 되면 비로소 검색 엔진이 이 데이터를 인지하고 검색 결과에 포함시킵니다.
4. **Flush (Disk Commit):** 시스템 캐시에만 머물던 데이터는 물리적으로 매우 비싼 `fsync` 연산을 통해 디스크에 완전히 기록(Commit)됩니다.

### 2. refresh_interval의 역할

* `index.refresh_interval` 설정은 버퍼의 데이터를 세그먼트로 변환하여 검색 가능하게 만드는 주기를 결정합니다.
* 기본값은 `1s`(1초)입니다. 즉, 입력된 데이터는 최대 1초 후에 검색이 가능해집니다.
* **대량 데이터 색인(Migration) 시 최적화:** 100만 건 이상의 데이터를 넣을 때는 이 값을 `-1`(비활성화)로 설정하여 불필요한 세그먼트 생성 오버헤드를 줄이고, 작업이 끝난 후 수동으로 `_refresh`를 호출하거나 주기를 다시 돌려 성능을 최적화합니다.

```json
# 대량 색인 전 refresh 비활성화 설정 예시
curl -X PUT "localhost:9200/products/_settings" -H "Content-Type: application/json" -d'
{
  "index": { "refresh_interval": "-1" }
}'
```

### [개념 검증용 자가 진단 질문]

1. **상황:** 백엔드 API에서 사용자가 상품 정보를 수정한 직후, 목록 페이지로 리다이렉트했는데 간헐적으로 수정 전 데이터가 보입니다. 엘라스틱서치의 NRT(Near Real-Time) 아키텍처 관점에서 이 현상이 왜 발생하는지, 그리고 API 수준에서 응답 지연을 감수하더라도 이를 해결하려면 어떤 옵션을 사용해야 하는지 메커니즘 중심으로 설명하세요.
2. **상황:** 수백만 건의 로그 데이터를 마이그레이션할 때, 단건 API 대신 `_bulk` API를 사용하고 `number_of_replicas`를 0으로, `refresh_interval`을 -1로 설정하는 것이 왜 성능 향상에 결정적인 기여를 하는지 내부 리소스 소모 관점에서 분석하세요.
3. **상황:** 특정 문자열 필드에 대해 검색 속도를 높이기 위해 '역색인'이 생성되었습니다. 이때 엘라스틱서치의 '분석기(Analyzer)'가 수행하는 내부 동작(토큰화, 필터링 등)이 검색 퀄리티와 역색인 구조에 어떤 영향을 미치는지 서술하세요.

* **1번 질문 해설:** 이 현상은 엘라스틱서치의 **Refresh** 주기 때문입니다. 데이터는 메모리 버퍼에 즉시 저장되지만, 기본 1초 주기의 Refresh가 발생하여 세그먼트가 생성되고 검색 엔진에 Open되기 전까지는 검색 결과에 반영되지 않습니다. 이를 해결하려면 문서를 색인/수정할 때 `?refresh=wait_for` 옵션을 사용해야 합니다. 이 옵션은 요청이 들어오면 다음 Refresh 주기가 완료될 때까지 클라이언트 응답을 대기(Wait)시키므로, 사용자는 항상 최신화된 검색 결과를 보장받을 수 있습니다. 다만, 응답 시간이 늘어나는 트레이드오프가 있습니다.

* **2번 질문 해설:**
    1. **_bulk API:** 매 요청마다 발생하는 HTTP 헤더 처리 오버헤드와 네트워크 왕복 시간을 줄여줍니다.
    2. **number_of_replicas: 0:** 마이그레이션 도중 프라이머리 샤드의 데이터를 레플리카 샤드로 복제하고 동기화하는 네트워크 및 CPU 비용을 제거합니다.
    3. **refresh_interval: -1:** 루씬 세그먼트를 1초마다 생성하는 작업을 중단합니다. 세그먼트 생성은 메모리 버퍼 비우기, 캐시 기록 등 시스템 자원을 소모하므로 이를 꺼두면 오직 데이터 색인에만 자원을 집중할 수 있어 속도가 비약적으로 향상됩니다.

* **3번 질문 해설:** 분석기는 입력된 텍스트를 용어 사전(Term Dictionary)에 등록하기 위해 가공하는 역할을 합니다. **토큰화(Tokenizer)**를 통해 문장을 단어로 쪼개고, **토큰 필터(Token Filter)**를 통해 불필요한 관사 제거 및 형태소 원형 변환(Stemming)을 수행합니다. 이 과정이 정교할수록 역색인 사전에는 '의미 있는' 핵심어들만 최적화되어 저장됩니다. 검색 시에도 동일한 분석기를 거치기 때문에, 사용자가 'running'으로 검색해도 사전에 'run'으로 정규화되어 저장된 역색인 포스팅 리스트를 정확히 찾아낼 수 있게 되어 검색의 정확도(Relevance)가 높아집니다.
