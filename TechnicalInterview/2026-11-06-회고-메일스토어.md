## 0. 프로젝트 전체 그림

**무엇을 만들었나.** 기존 C로 된 메일 스토어(사용자 메일함 DB와 메일 원문을 관리하는 데몬)를 Java·Spring으로 다시 만드는 일이었다. 바뀐 점은 두 가지다.
- 디스크 확장 한계 때문에 메일 원문(mdata)을 로컬 디스크에서 GCS로 옮겼다. GCS 저장소 구현은 seungjin 님 담당이고 내 커밋은 3건뿐이다(리서치 노트 기준).
- 전송 계층은 Netty TCP 서버(store-d)로 했다. MTA·IMAP·웹메일이 길이 prefix 프로토콜로 요청을 보낸다.

**모듈.** `store-d`(Netty 서버·프로토콜 파싱), `mailbox`(메일함 도메인·SQLite 접근), `indexer`(검색 색인), `search-parser`, `mime-parser`.

**데이터 구조.** 사용자마다 개인 SQLite 파일이 있다. `ConnectionType`은 `MINDEX`(메일 목록·메타), `BIG_ATTACH`(대용량 첨부), `MDN`(수신 확인), `WEB_FOLDER`(웹폴더/자료실) 4종이다. 처음에는 여기에 공용 `RESERVE`(`_Reserve.db`, 예약 메일) 1개가 더 있었는데 2025-01-22에 내가 지웠다(사건 2).

**내 역할** (2026-11-05 사용자 확인 + 기록):
- 외주(C만 해 온 분)가 메일 API 요구사항과 전체 아키텍처를 설계했다. 나는 그 C 중심 설계를 Spring 구조로 옮기는 재설계를 맡았다. 메일 개발은 이때가 처음이었다.
- 직접 만든 것: 사용자별 SQLite 커넥션·트랜잭션 구조(`common/connection`), Netty 수신부(`stored/netty`), append 수신, 그 밖의 프로토콜 다수(X-Thread, MBOX-DELETE, FLAG-UPDATE 다건, 자료실, UID/Sequence, sort, x2me, BigAttach, 중복 검사 등).
- 메일 **검색 구조 설계는 내 작업이 아니다.** 이 문서에서는 다루지 않는다.
- 개발이 끝나자 바로 마이그레이션에 투입됐고 운영은 다른 담당자가 이어받았다.

**배포 (사용자 확인, 이 저장소에는 근거 없음).** 클러스터 9개 × store 2대이고, 3대로 늘릴 수 있게 설계했다. 사용자를 만들 때 담당 store가 DB에 지정되므로 한 사용자는 한 store에만 붙는다. SQLite 파일은 k8s에서 NFS 위에 있어서 WAL을 쓸 수 없었고 rollback journal로 운영했다.

## 사건 1. 사용자별 SQLite를 TCP 채널에 묶다 — 커넥션 컨텍스트

> **요약**
> - 요청마다 대상 사용자가 다르고 DB도 4종이라서, 커넥션 풀 하나로는 다룰 수 없었다.
> - 사용자 1명분 DB 묶음을 `ConnectionContext`로 만들고 Netty 채널에 붙여 재사용했다. 실제로 쓰는 DB만 열고, 파일이 없으면 그 자리에서 스키마를 만들었다.
> - 나중에 "채널에 붙은 사용자와 다른 사용자의 요청"을 막는 검증(2025-02)과 "다른 store로 온 요청"을 막는 hostname 검증(2025-05)을 덧붙였다.

### 그때 뭘 하고 있었나
C 스토어를 Java로 옮기면서 가장 먼저 부딪힌 게 DB 접근 방식이었다. C에서는 사용자 디렉터리의 SQLite 파일을 그냥 열어서 썼다. Spring에서 흔히 하듯 DataSource 하나에 커넥션 풀을 거는 방식은 여기 맞지 않았다. DB 파일이 사용자 수만큼 있고, 한 사용자에게도 mindex·대용량 첨부·MDN·웹폴더 4개가 따로 있었기 때문이다.

### 무엇이 어려웠나
- 어떤 DB를 열지는 요청이 올 때까지 모른다. 요청 안의 `messageStore` 경로(`/mindex/companyGroup/company/userGroup/user`)로 정해진다.
- MTA·IMAP는 TCP 연결을 유지한 채 요청을 계속 보낸다. 그러니 요청마다 SQLite를 열고 닫으면 매번 파일을 여는 비용이 든다. 파일이 NFS 위에 있으니 그 비용은 더 크다.
- 처음 접속한 사용자는 DB 파일이 아직 없다. 기본 메일함 디렉터리와 테이블을 만들어 줘야 한다.

### 코드를 열어보니 (init 시점 구조)
- `ConnectionContext` 하나가 사용자 1명의 `Map<ConnectionType, SqlSession>`을 들고 있다. `getSqlSession(type)`을 처음 부를 때만 DB를 연다(lazy).
- `ThreadLocalConnectionManager`가 현재 스레드의 `ConnectionContext`를 `ThreadLocal`에 둔다. 리포지토리는 `SqlSessionTemplate.execute(...)`로 여기서 세션을 꺼내 쓴다.
- Netty 핸들러는 채널 attribute(`"SqlSessionContext"`)에 컨텍스트를 붙여 둔다. 같은 채널로 다음 요청이 오면 그걸 ThreadLocal에 다시 꽂아 재사용한다. 채널이 끊기면(`channelInactive`) 닫는다.
- Netty 채널은 항상 같은 이벤트 루프 스레드에서 처리된다. 그래서 요청 처리 동안 ThreadLocal에 넣어 두는 방식이 성립했다(추정 — 내가 이걸 의식하고 설계했는지는 확인 필요).
- 채널이 없는 경로(테스트 등)를 위해 `checkAndCreateSingleUse`를 뒀다. 이 경로에서는 일회용 컨텍스트를 만들고 요청이 끝나면 닫는다.

### 처음 시도와 그게 안 된 이유
- **스키마 생성 조건.** init에는 "디렉터리가 새로 만들어졌으면 테이블 생성"이었다. 내 TODO가 이미 걱정하고 있었다: `todo-star: mIndex가 아닌 다른 타입의 DB를 먼저 보는 경우가 존재하는지 확인 폴더뿐만 아니라 파일체크를 해야함`. 2025-02-04에 이승진 님이 판단 기준을 DB 파일 경로로 바꿨다가(`7c7779b7`) 다음 날 롤백했다(`471eb9ae`). 그 뒤 2025-02-07에 내가 "SQLite 파일이 없으면 생성"으로 정리했다(`d30706b7 createTable 조건 변경`). 같은 날 테이블 생성 SQL도 문자열 JDBC에서 MyBatis `InitTableMapper`로 옮겼다(`8f799ed2`).
- **채널 재사용의 구멍.** 채널에 컨텍스트를 한 번 붙이면, 그 채널로 **다른 사용자** 요청이 와도 첫 사용자의 DB에 쓰게 된다. 2025-02-06 DOPMAIL-427(`feature/DOPMAIL-427_valid_messageStore`)에서 `validateMessageStore`를 추가했다. 요청의 messageStore 앞 6단계를 잘라 채널 컨텍스트와 비교하고, 다르면 `InvalidMessageStoreException`을 던지고 받은 큐 파일을 지운다(`1d77afef`). 그런데 경로 뒤에 `/etc/WEBFOLDER` 같은 하위 경로가 붙어 와서 2025-02-12에 비교 로직을 고쳤다(`f7198947`, 테스트 `/mindex/2/2/33/33/aa/bb`). 같은 날 서비스 코드가 요청의 messageStore 대신 `ConnectionContext`의 값을 쓰도록 바꿨다(`8e714ac4`). 요청 값은 "메일 데몬이 보내 주는 경로"일 뿐이고, 실제로 쓰는 경로는 컨텍스트 하나로 맞춘 것이다.
- 무엇이 427을 촉발했는지(실제로 섞인 사례가 있었는지, 예방이었는지)는 기록에 없다. 다만 `mail-daemon` 코드를 보면 클라이언트는 연결 하나에 사용자를 섞지 않는다. MSS(메일 수신 데몬)는 수신자마다 그 사용자의 담당 store로 새로 연결해 append 한 건을 보내고 바로 닫는다(`localwrite_tims.c` `stored_connection_call` → `stored_connection_close`). IMAP은 로그인한 세션마다 연결 하나를 연다(`im_auth.c`). 그래서 427은 실제 사고 대응보다 **방어 검증**이었을 가능성이 크다(추정). → Q1-2

### 최종 결정과 대가
- 결정: 사용자 단위 컨텍스트 + 채널 바인딩 + lazy open + 파일 없으면 스키마 생성. 채널과 사용자가 어긋나면 거부.
- 대가:
  - DB 처리가 Netty 워커 이벤트 루프 스레드에서 그대로 돈다. 파이프라인에 별도 `EventExecutorGroup`이 없다. busy 대기(최대 3초)나 GCS 업로드가 길어지면 같은 루프의 다른 채널도 같이 멈춘다(코드상 사실. 당시 이걸 감수한 이유는 확인 필요 → Q1-3).
  - 채널이 오래 붙어 있으면 사용자 DB 파일 핸들도 그만큼 오래 열려 있다.
  - 내 마지막 버전의 `SqlSessionAspect`는 `begin()`을 먼저 하고 `checkAndCreateSingleUse()`를 나중에 부른다. 그래서 채널이 없는 경로에서는 BEGIN 없이 autocommit으로 돈다. init에서는 순서가 반대였는데 `d82a07e0`(2025-01-21)에서 바뀌었다. 운영 경로는 모두 Netty를 거치므로 영향은 없었을 것이다(추정).
- 한 사용자 = 한 store는 DB에서 정해진다(사용자 확인). store 쪽 방어는 2025-05-12~13 DOPMAIL-677에서 넣었다. 프로토콜 헤더에 hostName을 넣게 하고, 내 호스트명과 다르면 `Invalid hostId`로 RETURN(500)한다(`8d29742c` → `a61bab37`). 처음에는 `/opt/dop/config/global.config`의 hostId를 읽었는데 하루 만에 `InetAddress.getLocalHost().getHostName()`으로 바꿨다. → Q1-4
  - 상대편(`mail-daemon`, 계동욱 님 DOPMAIL-676)과 짝으로 움직였다: 05-12 16:02 "헤더에 hostid 추가"(`d18c1b12`) → 내 16:53 `8d29742c`, 05-13 14:23 "hostid 대신 host_name 사용"(`c6b43086`) → 내 14:14 `a61bab37`. 데몬은 사용자 DB의 담당 메일호스트 정보(`mailhost`/`mailhostFqdn`, 05-19 `ee0edc7b`에서 이름 통일)로 FQDN에 접속하고 헤더에 호스트명을 싣는다. store는 그걸 자기 호스트명과 비교한다. 즉 "사용자 생성 시 지정된 담당 store"가 곧 이 호스트명이다. 별도 hostId 설정 파일을 맞출 필요가 없어지므로 hostname으로 바꾼 것으로 보인다(추정).
  - `a61bab37`의 `SystemConfigLoader`는 호스트명을 구하고도 맵에 넣지 않아 기동 시 예외가 나는 구조였고, 05-19 `d8716e78 누락된 로직 추가`에서 `SYSTEM_CONFIG.put`을 넣었다.

## 사건 2. 여러 DB를 한 번에 begin/commit — reserv를 묶었다가 직접 지우다

> **요약**
> - 메일 삭제(expunge)는 mindex·MDN·reserv 세 DB를 함께 고쳐야 해서, 어노테이션 하나로 여러 DB를 같이 begin/commit/rollback하는 구조를 만들었다.
> - 이건 Spring `@Transactional`이 아니라 **직접 만든 AOP(`@UseSqlSession` + `SqlSessionAspect`) + ThreadLocal**이다. 저장소 어디에도 `@Transactional`이나 `TransactionManager`는 없다.
> - 공용 reserv는 2025-01-21~22에 내가 직접 지웠다(DOPMAIL-376). 그 뒤로 묶이는 건 expunge의 {MINDEX, MDN}뿐이고, 커밋은 DB별로 차례대로 하므로 원자성은 보장되지 않는다.

### 그때 뭘 하고 있었나
C 스토어의 동작을 Java로 옮기는 중이었다. 메일을 지우면 mindex에서 메일 행을 지우고, 수신확인(MDN) 기록과 예약 메일(reserv) 등록도 같이 지워야 했다.

### 무엇이 어려웠나
- DB 파일이 여러 개이고, 그중 하나(reserv)는 모든 사용자가 같이 쓰는 공용 파일이었다.
- DataSource가 고정돼 있지 않다. 요청한 사용자와 DB 종류에 따라 그때그때 정해진다. 그래서 DataSource 하나에 묶이는 Spring 트랜잭션 매니저를 그대로 쓸 수 없었다(사용자 확인 2026-11-06: Spring tx는 프로퍼티에서 DB를 미리 정하는 구조라 사용자당 SQLite 4개 구조에 맞지 않아, Spring tx의 AOP+ThreadLocal 방식을 보고 직접 구현했다 → Q2-1).

### 코드를 열어보니 (init, 2024-10-30)
- `@UseSqlSession(value = {...})`가 붙은 메서드를 `SqlSessionAspect`가 감싼다. 성공하면 `connectionManager.commit(value)`, `MailBoxException`이 나면 `rollback(value)`을 부른다.
- 사용자 DB는 JDBC `autoCommit(false)`로 열고 `sqlSession.commit(true)`로 커밋했다.
- reserv는 SQLite 파일 하나(`_Reserve.db`)를 **Hikari 커넥션 풀**로 열었다(`ConnectionPoolConfig.reserveDataSource`, `connectionInitSql: 'PRAGMA busy_timeout = 500'`). 이 풀 옵션에 내가 남긴 TODO가 있다: `todo-star: 옵션 튜닝 확인 (?journal_mode=WAL&cache_size=10000&synchronous=NORMAL/OFF&cache=shared) 테스트 해봐야함`. 이때는 WAL을 검토 대상으로 두고 있었다.
- 여러 DB를 묶은 곳은 단 하나, `expunge`의 `@UseSqlSession(value = {MINDEX, MDN, RESERVE})`였다. 나머지 reserv 사용은 `reserveAdd/AddRetry/Read/Del`의 단독 RESERVE였다. **append(메일 수신)는 MINDEX 단독**이었다.

## 사건 3. SQLite busy lock과 씨름한 2주 (DOPMAIL-290)

> **요약**
> - 같은 사용자의 mindex에 쓰기가 동시에 두 개 들어오면 `database is locked`(busy)가 났다. 코드 주석에 남은 원인은 "나에게 쓰기" 때 MSS(받은메일함)와 IMAP(보낸메일함) APPEND가 동시에 들어오는 경우다.
> - 2025-01-08 하루에 busy_timeout 값·BusyHandler를 바꾸고 로그를 넣는 커밋을 9개(PR #179~#186) 올렸지만 해결되지 않았다.
> - 2025-01-21에 방향을 바꿨다. autoCommit(true) + 쓰기 요청은 시작부터 `BEGIN EXCLUSIVE`, 읽기는 `BEGIN`으로 하고, 대기 시간은 MyBatis statement timeout(최종 3초)에 맡겼다.

### 그때 뭘 하고 있었나
기능 개발을 마치고 실제 메일 흐름(MTA 수신, IMAP, 웹메일)을 붙여 돌리던 시기다. 어느 환경(개발계·스테이징·부하 테스트)에서 터졌는지는 기록에 없다. → Q3-1

### 뭐가 터졌나
- 브랜치 `bugfix/DOPMAIL-290_sqlite_busy_lock`. 2025-01-08 `134528c4`에서 내가 남긴 주석:
  > "나에게 쓰기시 MSS, IMAP 동시에(받은메일함, 보낸메일함) APPEND가 들어오는 경우가 발생 / 최소 1초 이상으로 설정 필요"
- 사용자 기억은 "주로 mindex, 같은 사용자가 Outlook(IMAP)과 웹메일을 동시에 쓸 때"다. 기록에 남은 첫 사례는 "나에게 쓰기"의 동시 APPEND다. 둘 다 "한 사용자 mindex에 동시 쓰기"라는 점은 같다. → Q3-2

### 코드를 열어보니
- init 때 사용자 DB 커넥션은 `autoCommit(false)`에 `busy_timeout(500)`이었다. 내 TODO: `todo-star: busyTimeout이 내부적으로 최적화하여 더 좋을거같음, handler를 사용할 필요가 있나 싶음`.
- `autoCommit(false)`이면 sqlite-jdbc가 첫 SQL 전에 DEFERRED `BEGIN`을 보낸다. 두 커넥션이 둘 다 먼저 읽고(SHARED) 나중에 쓰려고(RESERVED로 승격) 하면, SQLite는 교착을 피하려고 한쪽에 busy_timeout을 무시하고 바로 SQLITE_BUSY를 돌려준다. 그래서 timeout을 늘려도 효과가 없었던 것으로 보인다(추정 — SQLite 동작에 근거한 해석이고, 당시 내가 이렇게 진단했는지는 확인 필요 → Q3-3).

### 최종 결정과 대가
**2025-01-21 `d82a07e0` "busy_lock 에러"** (14개 파일)
- `autoCommit(false)` → `autoCommit(true)`. 트랜잭션은 SQL로 직접 연다: `ConnectionMapper.beginTransaction` = `BEGIN EXCLUSIVE;`.
- 쓰기 요청은 시작 시점에 쓰기 락을 먼저 잡는다. 그러면 기다림이 BEGIN에서 일어나고, 그 기다림은 timeout이 제대로 걸리는 대기다.
- BusyHandler(300ms × 20)를 다시 넣었다가 같은 날 `b9cdfa8e`에서 주석 처리했다: `// timeout 시간을 설정하여 동작안함, 팔요시 사용`. 대신 MyBatis `defaultStatementTimeout(30)`을 넣었다. sqlite-jdbc는 statement에 query timeout이 있으면 실행하는 동안만 커넥션 busy_timeout을 `queryTimeout × 1000`ms로 바꿨다가 끝나면 되돌린다(`JDBC3Statement.withConnectionTimeout`, 로컬에 있는 3.45.1.0 jar 바이트코드로 확인. 프로젝트가 쓴 3.47.2.0도 같을 것으로 추정). 그래서 MyBatis statement timeout 3초 = `BEGIN EXCLUSIVE`의 busy 대기 3초다. → Q3-4

**2025-01-23 readOnly 정리**

- `0079b08e`/`7a3ef177`/`9a4c816c`: 메일함 존재 확인·생성을 `@ValidMailBox`(`MailBoxAspect`, `@Order(1)`)로 뺐다. `SqlSessionAspect`(`@Order(2)`)보다 먼저, **자기만의 짧은 `BEGIN EXCLUSIVE` → COMMIT**으로 처리한다. readOnly 요청인데 폴더를 만들어야 하는 경우(`needToCreate = true`)를 본 트랜잭션과 떼어 놓은 것으로 보인다(추정).
- `f1845e97 예외시 commit 호출`: 검증 예외로 빠질 때도 열어 둔 EXCLUSIVE를 COMMIT으로 닫게 했다. 안 그러면 다음 요청이 락에 막힌다.

**2025-02-18 timeout 숫자 확정** (DOPMAIL-422 브랜치 안)

**대가**
- 쓰기는 사용자 DB 단위로 완전히 직렬화된다. EXCLUSIVE라서 그동안 같은 사용자의 읽기도 막힌다(rollback journal 모드).

## 사건 4. append 수신 — 패킷이 붙어 오고 잘려 오던 문제와 본문 파일 스트리밍

> **요약**
> - init 때 디코더는 "버퍼에 온 걸 통째로 문자열로 읽기"였다. TCP는 경계를 지켜 주지 않으니, 요청이 잘리거나 두 개가 붙어서 오면 파싱이 깨졌다(2024-11 packet error).
> - 2024-12-04~05에 4바이트 길이 prefix 프레이밍으로 바꿨다. 본문(리터럴)은 헤더 → `OK` continuation → 다시 4바이트 길이 + 본문 순서로 받게 하고, 길이가 맞는지도 검증했다.
> - 본문은 메모리에 올리지 않고 받은 즉시 큐 파일(`.received.emlq`)로 흘려 쓴다. 이 틀은 Apache James의 IMAP 디코더를 본떴다.

### 그때 뭘 하고 있었나
MTA(C로 된 mail-daemon)와 IMAP 쪽이 store-d로 append(메일 저장)를 보내는 경로를 붙이고 있었다. 큰 첨부가 달린 메일도 들어온다.

### 뭐가 터졌나
- 2024-11-08 DOPMAIL-85 `MBOX_UPDATE_packet_error`. 하루에 `60f9abca`(패킷 오류 로그) → `c4973a3c`·`0be5cbbf`(packet error) → `804883ae`(decoder 로그)가 이어졌다. 첫 시도에서는 같은 버퍼를 US_ASCII·ISO_8859_1·UTF_8로 각각 찍어 보는 로그를 남겼다. 처음엔 인코딩 문제로 의심했던 것이다.
- 2024-12-02 DOPMAIL-203 `Outlook_append_에러` — Outlook이 보낸 문자열에 `"`·`\`가 섞여 응답 문자열이 깨졌다. 이스케이프를 추가했다(`2fb648f3`).

### 코드를 열어보니 (init)
```java
String bufferString = in.toString(StandardCharsets.UTF_8);
in.clear();
String[] parts = bufferString.split(DELIMITER, 4);
```
버퍼에 지금 와 있는 바이트가 곧 요청 하나라고 가정한 코드다. 덜 왔으면 잘린 요청을 파싱하고, 두 요청이 붙어 오면 뒤의 것을 `in.clear()`로 버린다.

본문 쪽은 James `ImapRequestFrameDecoder`와 같은 구조였다. attachment 맵에 `NEEDED_DATA`/`SINK`를 두고 `obtainInputStream`으로 파일에 이어 쓴다. 로컬 `james-project`의 `ImapRequestFrameDecoder`에서 같은 이름(`NEEDED_DATA`, `SINK`)을 확인했다.

### 처음 시도와 그게 안 된 이유
- 11-08 `0be5cbbf`: `in.maxFastWritableBytes() == 0`이면 return하는 가드를 넣었다. 경계 문제를 근본적으로 풀지는 못했다.
- 12-04 DOPMAIL-216 `TCP_요청패킷_사이즈_추가`, 하루에 4번 왕복했다:
  - `d3fd195e` 앞 4바이트를 **문자열 숫자**로 읽기(`Integer.parseInt(new String(len))`)
  - `c3b325de` → `in.readInt()`(바이너리 int)
  - `a4883622` "문자열로 받도록 변경" → 다시 문자열
  - `54020b8f` "byte로 변환" → 최종 `readInt()`
  - MTA 쪽과 길이 표현(텍스트 vs 바이너리)을 맞추느라 왔다 갔다 한 것으로 보인다(→ Q4-1). 상대편 기록: `mail-daemon` 계동욱 님 DOPMAIL-218 `a1c6ab21`(12-05 14:00) "stored 통신 시 데이터 사이즈 추가"가 `htonl(len)` 4바이트 **바이너리**를 앞에 붙여 보내고, 응답도 4바이트를 `ntohl`로 읽는다. 내 최종 `readInt()`(빅엔디언 int)와 같은 형식이다.
  - 핵심: `markReaderIndex()` → 길이 읽기 → 덜 왔으면 `resetReaderIndex()` 후 return해서 더 기다린다.
- 12-05 `a296a8a0` "리터널 헤더길이 추가": 응답에도 길이 prefix를 붙였다(`BufferUtil.setHeaderLength`). 본문 앞에도 4바이트 길이를 받아(`VERIFY`), 헤더에서 선언한 크기보다 작으면 `Invalid data size`로 RETURN(500)한다.
- 2024-11-15 `c4c2d104`: 에러 코드를 `MailBoxStatusCode` `OK(200)/RETRY(400)/RETURN(500)`으로 통일했다. MTA는 RETRY면 다시 보내고 RETURN이면 반송한다는 의도였다(→ Q4-2). 그런데 `mail-daemon` 코드상 실제 동작은 다르다. 데몬의 `cmd_ckeck_result`는 code가 200이 아니면 무조건 실패(-1)를 돌려주고, `cmd_stored_append`는 그걸 `QUEUE_STATUS_PERSISTENTFAIL`(defer 큐 → 재전송)로 바꾼다. 즉 store가 400을 주든 500을 주든 MSS는 **다시 보낸다.** 반송(`PERMANENTFAIL`)으로 가는 분기는 200 응답 뒤의 `stored_response_case`에만 있어서 사실상 타지 않는다(2025-06 시점·현재 develop 동일). 그리고 2025-02-03 데몬 `4368c08a`(DOPMAIL-405 "append 실패 시 queueing되게 수정") 전에는 실패 시 -1을 돌려줬는데, MSS는 이 값을 실패로 보지 않고 "Append Success" 경로로 넘겼다. 그 전까지는 store 실패가 메일 누락으로 이어질 수 있었다(코드상 사실, 실제 사례는 기록 없음).

## 사건 5. 수신 실패 뒤 남는 큐 파일과 중복 수신

> **요약**

## 사건 6. 수신 → 저장 → 색인 분리와 큐 디렉터리

> **요약**
> - 메일 저장(mindex 기록, 원문 업로드)은 요청 안에서 동기로 하고, 검색 색인은 이벤트 + `@Async`로 떼어 냈다. 그래서 색인이 느려도 수신 응답은 늦어지지 않는다.
> - 2025-02-05에 "수신 중인 파일"(`received`)과 "색인 대기 파일"(`indexing`) 디렉터리를 나누고, indexing은 1024개 하위 디렉터리로 쪼갰다.
> - 단, 색인 이벤트는 COMMIT **전에** 발행된다. Spring tx가 아니라서 `@TransactionalEventListener(AFTER_COMMIT)`를 쓸 수 없는 구조였다.

### 그때 뭘 하고 있었나
append가 실제로 돌기 시작하고, indexer(다른 분 담당)와 큐 파일로 주고받는 부분을 정리하던 시기다.

### 무엇이 어려웠나
- 처음에는 큐 디렉터리가 `mail.store.qdir` 하나였다. 받는 중인 파일과 색인을 기다리는 파일이 한곳에 섞였다.
- 디렉터리 하나에 파일이 계속 쌓이면 NFS에서 목록 조회가 느려진다(추정 — 1024 분할의 이유로 보임 → Q6-1). indexer의 `BackgroundIndexer`는 하위 디렉터리별로 나눠 처리하지 않고 `Files.walk`로 트리 전체를 훑는다. 그래서 "indexer 병렬 처리용"보다는 "디렉터리 하나의 크기 제한용"에 가깝다(추정).

### 처음 시도와 최종 결정

## 사용자 답변 반영 (2026-11-06)

- **직접 AOP를 만든 이유(Q2-1):** Spring tx를 쓰고 싶었지만, 설정상 DB 하나에 커넥션 하나(고정 DataSource)를 만드는 구조라 모든 사용자가 하나의 SQLite로 접근해야 했다. 우리는 사용자 1명당 SQLite 4개라 맞지 않았다. 그래서 Spring tx 구조를 확인하고 같은 방식(AOP + ThreadLocal)으로 우리 구조에 녹였다.
- **reserv(Q2-2·Q2-3):** "mindex·reserv를 묶었다"는 기억은 MDN과 헷갈린 것. 지금 묶음은 mindex + MDN.
- **Spring tx가 안 맞은 이유 보충:** Spring tx는 프로퍼티에서 접근할 DB(DataSource)를 미리 정하고 시작하는 구조라, 요청마다 사용자 DB가 바뀌는 우리 구조와 맞지 않았다.
- **busy lock(Q3-2·Q3-3):** 직접 계기는 "나에게 쓰기" 때 받은메일함 수신(MTA 쪽 MSS)과 보낸메일함 저장(IMAP APPEND)이 같은 사용자 mindex에 동시에 쓰던 것(`134528c4` 주석). 코드상 "나에게 쓰기" 처리 코드는 store에 없고 주석에만 남음 — store는 APPEND 두 개를 받을 뿐. 사용자 기억으로는 EXCLUSIVE의 또 다른 이유가 IMAP 데몬의 메모리상 seq 계산: 중간에 다른 요청이 메일을 바꾸면 A가 지운 seq 3이 B에게는 4번째가 되는 식의 어긋남. 이 이유는 기록에 없어 면접에서 보조 이유로만 쓴다.
- **색인(Q6-2·Q6-3):** 색인기 자체는 다른 사람 작업. 본인은 큐 파일을 어떻게 넘겨주고 상대가 어떻게 받을지(received/indexing 분리, 로컬 eml 경로 전달)를 만들었다. indexer는 GCS에서 다시 받지 않고 로컬 큐 파일을 읽는다. 커밋 전에 발행한 이유는 기억나지 않음(Spring tx가 아니라 AFTER_COMMIT을 쓸 수 없는 구조).
- **GCS 저장을 DB 쓰기보다 먼저 한 이유(사용자 기억):** SQLite를 연 채로 GCS 네트워크를 타면 그만큼 SQLite를 오래 붙잡으니, 원문을 먼저 GCS에 저장하고 DB 작업을 뒤에 몰았다. 코드 확인: `convertAndSave`(GCS `WriteChannel` 동기 업로드)가 mindex 기록보다 앞에 있다. 단, 트랜잭션 시작은 `MailboxServiceHub.appendMessage`의 `@UseSqlSession`(AOP)이라 GCS 업로드보다 먼저다. 01-21 이전 DEFERRED BEGIN에서는 첫 SQL 전까지 락이 없어 의도대로였지만, 01-21 `BEGIN EXCLUSIVE` 전환 뒤에는 GCS 업로드 동안 쓰기 락을 쥔다(코드 확인: `SqlSessionAspect.begin()` → `BEGIN EXCLUSIVE;`가 `joinPoint.proceed()` 전에 실행).
- **→ 부작용으로 정리(사용자 동의 2026-11-06):** busy lock을 잡으려고 EXCLUSIVE를 트랜잭션 시작으로 앞당기면서, GCS 업로드 시간이 락 안으로 들어왔다. 데이터 오류는 아니지만 같은 사용자의 다른 쓰기는 업로드 시간만큼 더 기다리고, 3초를 넘기면 busy 실패 → MTA 재전송. 개선 방향: GCS 업로드를 트랜잭션 밖으로 뺀다. EXCLUSIVE는 유지 — IMAP 메일 데몬이 메모리에 seq를 들고 있어서, 쓰는 도중 다른 요청이 읽으면 seq 기준이 어긋난다. 그래서 읽기까지 막는 EXCLUSIVE가 맞다(사용자, 2026-11-06). IMMEDIATE(쓰기만 직렬화, 읽기 허용)는 이 이유로 택하지 않는다.
- **IN 절 5,000건 분할(Q7-1·Q7-2):** 04-24 `2dad3023`(DOPMAIL-651 stored NFS 지연)에 넣고 04-28 `8a14a318` "로직 원복". 이유는 기억나지 않음. 사용자 추측: 부하테스트 중 어느 시점부터 응답이 급격히 느려졌는데 원인은 VACUUM을 안 돌린 것이었고, 이와 관련 있을 것. 기록상 VACUUM은 원복 2주 뒤 이승진님이 개발(`2b732757` 05-14, `7696ab78` 05-15, DOPMAIL-686) — 본인 작업 아님. 포트폴리오에서 제외.
- **시작 시점(Q0-1, 2026-11-07):** 2024-07 시작이 맞다. 10월(첫 커밋 10-30)은 본격 개발 시기. 포트폴리오 기간을 2024.7 ~ 2025.6으로 수정.
