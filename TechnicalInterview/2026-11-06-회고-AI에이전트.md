## 0. 프로젝트 전체 그림

### 무엇을 만들었나

그룹웨어(메일·결재·캘린더·메신저 등)를 도구로 부르는 LangGraph ReAct 에이전트 서비스다. 요청은 이렇게 흐른다.

```
Front ──SSE──▶ dop-ai-stream (Java, SSE 중계 · 다른 담당)
                 └─▶ dop-ai-agent-api = ai-home-poc (FastAPI + gunicorn 워커 2개/파드, k8s)
                       ├─ LangGraph 그래프: receive_input → … → agent_model ⇄ tools → finalize
                       │    tools 노드에서 승인·입력이 필요하면 interrupt() (HITL)
                       ├─ 체크포인터 (재설계 대상, 사건 1)
                       ├─ MCP 클라이언트 → dop-ai-mcp (MCP 서버, 타 팀원)
                       └─ ai-file 호출 (첨부 파싱 · 배경지식 색인) ── RabbitMQ / HTTP
                 PostgreSQL · Redis · Elasticsearch · LLM(OpenAI / Anthropic / Gemini)
ai-automation: 예약·수동 업무 자동화를 step 단위로 AI Home에 실행 위임 (사건 8)
```

## 1. 체크포인트가 DB를 무너뜨렸다 — 체크포인터 재설계

> **3줄 요약**
> - 부하테스트에서 PostgreSQL이 두 번 죽었다. 07-27엔 `checkpoint_blobs`가 27GB까지 차서 디스크 풀, 07-31엔 6,000VU 런 도중 PG가 모든 파드 커넥션을 끊었다.
> - 원인은 "요청마다 새 체크포인트를 쓰고, 끝나면 바로 지우는" 구조. 쓴 행이 100% 쓰레기가 됐다.
> - 체크포인트는 프로세스 메모리에만 두고, 인터럽트(HITL)로 멈춘 run만 PG에 남기도록 바꿨다. 인터럽트 없는 run의 체크포인트 DB 작업이 7건에서 0건이 됐다.

### 1-1. 그때 뭘 하고 있었나

7월 중순부터 첨부 파일 읽기 부하테스트를 하고 있었다. 첨부가 많이 붙은 대화에서 파드 메모리가 터지는 문제를 막으려고 07-21에 AI Home에 "첨부 read 게이트"(턴 단위 동시성 제한)를 넣었고, 그 효과를 보려고 k6로 첨부 read를 계속 때리던 중이었다(`2026-07-27-첨부-read-메모리-부하테스트-진행상황.md`). 그 다음 주(07-30~31)엔 첨부 없는 순수 채팅(chat/stream) 트랙으로 넘어가 계층별 병목을 보고 있었다.

### 1-2. 뭐가 터졌나

**첫 번째 (07-27, 첨부 read 부하테스트).** 부하 중 `asyncpg.exceptions.DiskFullError` → PG PANIC → recovery. 실패 응답의 31%가 `PoolTimeout`/`DiskFullError`였다. 테이블 크기를 떠 보니 이랬다 [문서].

```
checkpoint_blobs   568,793 행 / 27 GB (TOAST 27 GB)   ← 원인의 87%
checkpoint_writes    3.7 GB
checkpoints        212,315 행 / 394 MB
그 외 도메인 테이블 전부 350 MB 미만
```

사내 DBA가 "첨부 base64를 PG 체크포인트에 적재하는 현 구조"를 거부했다(`2026-07-28-체크포인트-첨부-base64-DB용량-대안설계.md` 머리말의 트리거 항목).

**두 번째 (07-30, chat/stream).** DB CPU가 올랐고, DBA가 `ai_thread_run_context_item`과 `checkpoint_blobs` **두 테이블의 insert량**을 원인으로 지목했다(`2026-07-30-ai-thread-run-context-item-적재-개선-설계.md`). 요청마다 "로그(run context item)"와 "체크포인트"를 테이블에 쌓고 있었던 것이다.

**세 번째 (07-31, 6,000VU 게이트웨이 우회 런).** 처리량이 214 → 204 → 194 → 179 req/s로 4분간 줄더니 **15:32:08에 PG가 전 파드 커넥션을 일제히 끊었다**(`server closed the connection unexpectedly`, 끊긴 지점이 체크포인터 `aput`). 부하 시작(15:26)으로부터 약 6분 뒤다. 14분 동안 약 116,000 run이 `checkpoint_blobs`에 100만~140만 행을 INSERT하고 같은 수를 DELETE했다. 대기 이벤트 1위는 `LWLock: BufferContent`(최대 150) [문서: `2026-07-31-chatstream-게이트웨이우회-부하테스트-DB중단-분석.md`].

### 1-3. 코드를 열어보니

세 가지가 겹쳐 있었다.

1. **체크포인트 thread 키가 run_id였다.** 체크포인트가 대화 단위가 아니라 **요청 단위**로 새로 생긴다. 재사용 0. 대화 이력은 이미 앱 테이블(`ai_thread_context_message` 등)이 들고 있었으니, 체크포인트는 "그래프 실행 중간 상태"일 뿐이고 실제로 쓰이는 곳은 HITL 재개 하나였다.
   - `app/modules/domain/ai_home/runtime/react_runtime.py:554` `"thread_id": self.run_id`
2. **끝나면 지웠다.** 07-23 dskim의 `fa4f3bea`("delete run-scoped LangGraph checkpoints on terminal runs")가 모든 터미널 경로에서 3테이블을 DELETE했다. 체크포인트가 쌓이는 문제(07-27의 27GB)에 대한 대응이었지만, 결과는 **write-then-delete**다. WAL·TOAST 압축·인덱스 페이지를 다 치르고 남는 건 dead tuple뿐.
3. **체크포인트 1회 기록이 SQL 1개가 아니었다.** run 하나가 만드는 체크포인트 DB 작업은 7건이었다.

```
run 시작   aget_tuple       SELECT 1
run 종료   aput / aput_writes  checkpoint_blobs(채널별 executemany) · checkpoints · checkpoint_writes UPSERT 3계열
터미널     adelete_thread   3테이블 DELETE 3
→ 7건 = 조회 1 + 저장 3 + 삭제 3   (4809e574 커밋 본문에 같은 분해)
```

   여기에 체크포인터 풀이 `autocommit=True`라 문장마다 커밋이 따로 났다. 07-31 측정에서 DB 전체 커밋이 1,771/s ÷ 190 req/s = **요청당 약 9.3커밋**(앱 테이블 커밋 포함, 체크포인터 몫과 나누지 않음) [문서: `2026-07-31-ai-home-DB-현황-및-개선안.md`].

그리고 첨부가 붙은 턴은 base64가 `state["messages"]`에 그대로 들어가 체크포인트 blob으로 통째로 저장됐다. 턴당 18.5MiB(R=10 라운드), 많으면 46MiB. 첨부 없는 채팅 run은 약 2MB [문서].

### 1-4. 처음 시도와 그게 안 된 이유 (커밋 순서)

**① 쓰는 횟수부터 줄였다 — `durability="exit"` (07-27 20:38, `2ccc308e`).** LangGraph 기본값(`async`)은 superstep마다 체크포인트를 쓴다. ReAct 루프는 스텝이 많으니 라운드 수의 제곱으로 커졌다(턴당 102MiB → 18.5MiB). `exit`는 그래프가 끝날 때(정상 종료·interrupt·에러) 한 번만 쓴다. interrupt도 exit에 포함되니 HITL은 그대로다.
→ **안 된 이유**: 쓰는 횟수는 run당 1회로 최소가 됐지만, 그 1회가 여전히 3계열 UPSERT이고 곧바로 DELETE됐다. 구조(write-then-delete)는 그대로.

**② 07-28에 이미 답의 방향은 적어 뒀다.** 대안 설계 문서에서 "안 0 — 메모리 버퍼 세이버 + interrupt 시에만 flush"를 권고했다. 근거는 "거의 모든 run이 18.5MiB를 쓰고 곧바로 지운다. 얻는 것이 0이다". `durability`에는 `none`이 없다는 것도 확인했다(`sync`/`async`/`exit`만). checkpointer를 아예 안 넘기면 저장이 0이지만 `interrupt()`가 안 된다. UI 상호작용 도구가 모든 run에 바인딩되므로 "interrupt 가능한 턴에만 체크포인터를 붙이는" 방법도 막혀 있었다.

**③ 로그 테이블부터 껐다 (07-30).** DBA가 지목한 두 테이블 중 `ai_thread_run_context_item`을 먼저 처리했다. 처음엔 행 수를 줄이려고 INSERT를 한 문장으로 묶었다(`ab729f70`). 그런데 담당자에게 확인해 보니 이 테이블은 **순수 로깅용**이었고, 레포 전수 검색에서도 읽는 경로가 0건이었다. 그래서 줄이는 게 아니라 **적재 자체를 스위치로 끄고** dev/stg/prod 전부 OFF로 뒀다(`1f80236b`).

**④ 07-31 낮: 커넥션을 줄이고, 체크포인터를 빼고 재 보기.** 13:47 커넥션 다이어트(`bf3efc8b`, 사건 3). 15:32 PG 절단. 그 직후 내 메모(`chatstream-checkpoint-blobs-db-kill`)에 적은 순서는 이랬다.
   1. 부하 구간에서 `checkpoint_cleanup_on_terminal`을 끄고 재측정
   2. 체크포인터 풀을 분리해 `autocommit=False`
   3. 그 다음에 앱 풀 완화
   
   16:50엔 진단용 브랜치 `perf/no-checkpointer-probe`(`d31be434`)를 만들었다. 체크포인터 객체와 psycopg 풀을 아예 안 만들어 체크포인트 DB 작업을 0으로 만들고 "DB를 죽인 주범이 체크포인터인가"를 단일 변수로 가르려는 것이다. 여기서 `InMemorySaver`를 일부러 안 썼다. 메모리를 새 변수로 넣으면 판정이 오염되기 때문이다.

**⑤ 같은 날 저녁, 위 ①·②안을 버렸다.** 설계 문서 §3 "검토했다 버린 안"(`2026-07-31-체크포인터-메모리버퍼-Redis전환-설계.md`):
   - **cleanup만 끄기**: DELETE는 줄지만 INSERT는 그대로고 테이블이 무한 누적된다. 별도 배치 정리가 필요해져 관리 대상만 는다.
   - **풀 `autocommit=False`, 인터럽트 때만 commit**: 세이버는 프로세스당 1개이고 `_cursor()`가 인스턴스 `asyncio.Lock`을 먼저 잡아서 run별 트랜잭션 경계가 존재하지 않는다. psycopg_pool의 `pool.connection()` 블록은 끝날 때 자동 커밋한다. 롤백해도 INSERT의 WAL·힙 쓰기는 이미 일어난다.
   - **`langgraph-checkpoint-redis`**: RediSearch/RedisJSON 모듈이 필요하다. 실제로 쓰는 연산은 3개뿐이라 과한 의존.
   - 그리고 07-28에 권고했던 **"메모리 버퍼 + 인터럽트 시 PG flush"도 이때는 버렸다.** `aput`이 바뀐 채널 blob만 저장하고 나머지는 이전 버전을 참조하므로, 메모리와 PG가 섞이면 채널 값 복원이 깨진다고 봤다. 게다가 기동 시 `cp.setup()`이 DB를 요구해 파드가 죽는 문제(07-31 Loki에서 PoolTimeout 254건이 전부 기동 경로, 컨테이너 재시작 약 6회)가 남는다.
   
   → 22:46 **"메모리 버퍼 + Redis 스냅샷"**으로 착수(`1ac1806a`). run 하나의 체크포인트 이력 전체를 Redis 키 1개에 "델타가 아니라 스냅샷"으로 담으면 blob 버전 체인 문제가 없다.

**⑥ 같은 날 밤, 다시 PG를 기본값으로 (23:09 `229aa2ba`, 23:17 `b20a3892`).** 원격 저장소를 `pg | redis` 중 고르게 하고 기본을 pg로 돌렸다. 설계 문서 §9-2에 PG를 버렸던 이유가 왜 해당하지 않는지를 적었다.
   - 복원이 깨진다는 건 *마지막 `aput` 하나만* 보낼 때의 문제다. 체크포인트를 **오래된 것부터 전부** 다시 쓰면 PG 안에 체인이 빠짐없이 남는다. 재인터럽트 때는 워터마크(`_flushed`)로 뒤쪽만 보낸다.
   - `cp.setup()` 기동 의존은 풀 생성과 setup을 **첫 인터럽트까지 지연**해서 없앤다.
   - PG는 신규 테이블이 없고(기존 3테이블에 native 형식으로 재기록), 읽기·삭제는 기존 세이버에 위임한다. 전환·롤백은 Deployment env 한 줄(`AI_HOME_CHECKPOINT_BACKEND`).
   - 왜 기본값을 Redis가 아니라 PG로 했는지 직접 적은 문장은 찾지 못했다 → [확인 필요] 9절 질문.

**⑦ 08-01: 상태 사본을 하나로 (`64aeb354`).** 처음엔 `aput`/`aput_writes` 호출 인자를 op 로그로 따로 쌓았다가 인터럽트 때 replay했다. 이걸 없애고, 인터럽트 순간에 `InMemorySaver`를 `alist`로 읽어 원격에 쓰게 했다. 대가는 읽기 API로 복원할 수 없는 두 인자다. `task_path`는 `""`로 넣었다(그래프가 `Send`를 안 쓴다). `new_versions`는 누적 `channel_versions`로 넣었다. 비우면 복원된 `channel_values`가 `{}`가 되는 걸 실측으로 확인하고 테스트로 고정했다.

**⑧ 08-04: "인터럽트는 소수 경로"라는 전제가 틀렸다.** 설계 문서 §2-3은 "`interrupt()` 호출 지점이 한 곳뿐이니 대부분의 run은 인터럽트 없이 끝난다"고 적었는데, 실제 빈도는 **run의 약 1/3**이었다(승인 요청뿐 아니라 UI 컴포넌트 입력 요청도 같은 지점을 탄다). 호출 지점 수는 빈도의 근거가 아니었다.
   - "요청당 저장소 접근 0"은 **run 단위** 주장이라 살아남는다(나머지 2/3).
   - "기동 시 저장소 의존 0"은 **파드 단위** 주장이라 무너진다. 모든 파드가 뜨자마자 첫 인터럽트를 만난다.
   
   그래서 지연 초기화를 걷어내고 기동 시 `awarmup()`으로 풀·스키마를 준비하되, 실패해도 파드를 죽이지 않고 degraded로 기동하게 했다(`8d445086`). 07-31에 파드를 죽인 건 일찍 연결한 게 아니라 setup 실패가 lifespan 예외로 올라간 것이었기 때문이다.
   
   같은 날 **파드 간 재개 버그**도 잡았다(`3f0a691a`). 재개 요청이 인터럽트를 만든 프로세스로 갈 확률은 1/(파드×워커)인데, 서비스 계층의 pre-check가 prefetch보다 먼저 돌아서 다른 파드에선 "pending interrupt 없음"으로 재개가 실패했다. 런타임 단위 테스트는 서비스 계층 순서를 못 봐서 이걸 못 잡았다.

**⑨ 08-05: 비교 실험을 하려다 PG를 또 죽였다.** "체크포인트 비용"을 단일 변수로 가르려고 arm A(현행) / B(체크포인터 없음) / C(버퍼 세이버) 3안 비교를 준비했다(`2026-08-05-체크포인트-3안-부하테스트-런북.md`). arm A를 **4,000VU**로 넣었더니 첫 완료 후 약 90초 만에 PG가 무너져 다른 서비스까지 영향이 갔다. 그때 agent CPU는 32%, throttle 0, 5xx 0이었다. "우리 서비스는 여유였고 천장은 DB였다". 공용 dev에서는 이 실험을 더 하지 않기로 했다. (그 전 08-01 소규모 실험 run1에선 agent CPU가 2코어에 못박혀 있어서 "이 조건에선 DB 대기가 병목이 아니다"라고 따로 적어 뒀다. 파드 수·limit이 달라서 07-31 관찰과 구분해서 봤다.)

**⑩ 08-07: "0"이 사실은 0이 아니었다 (`1deac2e8`).** 머지 직전 의도 대조 점검에서, 인터럽트 없이 끝난 run도 터미널 회수에서 빈 3테이블 DELETE를 날리고 있는 걸 찾았다. dev Loki 24시간 터미널 회수 407건 중 405건이 빈 DELETE였다. 세이버에 `_remote_state` 장부를 두고 **원격에 남긴 적 있는 thread만** 지우게 했다. 대화 삭제 API는 아무 파드에서나 돌아 장부가 비는 게 정상이라 무조건 지우는 `apurge_run_checkpoints`로 분리했다. 이 커밋으로 "인터럽트 없는 run의 체크포인트 DB 작업 0"이 실제로 성립했다.

### 1-5. 최종 결정과 대가

**결정**: 체크포인트는 평소 프로세스 메모리(`InMemorySaver`)에만 쓰고 run이 끝나면 버린다. **인터럽트로 멈춘 run만** 그 순간 PG 기존 3테이블에 다시 써서, 다른 파드로 온 재개 요청도 상태를 찾게 한다. Redis 저장소도 만들었지만 dev/stg/prod 모두 `backend: "pg"`.

**결과**:
- 인터럽트 없는 run(약 2/3)의 요청당 체크포인트 DB 작업 **7건 → 0건** [코드: `4809e574` 본문 + `1deac2e8`].
- 08-12 3,000VU 재측정에서 체크포인트 DB 쓰기 0회, 앱 지표상 142.5 req/s에서 DB가 제약이 아니었다 [문서: `2026-08-12-chatstream-3000VU-런결과.md`]. 다만 이 런은 SQL 감축(사건 3)도 같이 들어가서 각자의 기여는 나누지 못했다. "DB를 SSD로 바꿔서 버텼다"로 읽으면 안 된다고 당시에 적어 뒀다(투입 부하 자체가 줄었다).

**포기한 것 · 남은 한계**:
- **일반 run의 중간 상태는 파드가 죽으면 사라진다.** 원래 run_id 키 구조상 중간 스텝 재개 경로가 없었으므로(재시도는 새 run) 잃는 기능은 없다고 판단했다. 파드 종료 시엔 preStop 5초 + gunicorn `graceful_timeout=120`(TGPS 150)으로 열린 SSE run을 마저 처리한다. 이 설정은 07-29 `4f410bb7`에서 SSE 드레인 목적으로 먼저 넣은 것이고, 메모리 체크포인트를 종료 시 DB로 flush하지는 않는다. 120초를 넘기거나 OOM·노드 장애로 강제 종료되면 그 run만 유실.
- **인터럽트 run(약 1/3)은 여전히 PG에 쓴다.** 첨부가 붙은 인터럽트면 18.5~46MiB를 flush 순간 메모리에 약 3배로 부풀려 쓴다(§9-6). PG 경로에는 바이트 상한이 없다(`max_payload_bytes` 64MiB는 redis 전용). 근본 해법인 "첨부 base64를 GCS로 오프로드"는 08-06 설계·08-07 구현 스펙까지 썼지만, **저장소 어디에도 구현 커밋이 없다**(`git log --all` 검색 0건). GCS 버킷·IAM과 DBA 인라인 폴백 합의가 선행 조건으로 남아 있었다.
- PG 저장소에는 만료(TTL)가 없다. 사용자가 승인을 안 누르고 떠난 awaiting_user run은 쌓인다(07-27에 실사용 run 934건이 이미 쌓여 있었다).
- 실제 파드 2개로 실 API 재개를 검증한 기록은 못 찾았다(단위 테스트로 pg/redis 양쪽 고정까지는 확인) → [확인 필요].
- 인터럽트 flush가 실패하면 run을 실패시킨다(재개 상태 없이 "인터럽트됨"을 알리면 영영 재개 불가). 이 규칙의 PG 쪽 강화(`_aflush_if_interrupted`가 False에도 예외)는 10-08 `d84719b1`에서 추가됐다.

## 2. 병목은 어느 계층인가 — chat/stream 부하테스트 판정

> **3줄 요약**
> - 6,000VU 채팅 부하에서 처리량이 210 req/s 근처에서 안 올라갔다. 요청 경로가 stream → gateway → agent → PG 4계층이라 어디가 막혔는지부터 갈라야 했다.
> - 게이트웨이를 우회하자 응답헤더가 3.2s → 22ms, 5xx 14.1% → 0%가 됐지만 처리량은 그대로였다. 게이트웨이는 처리량 요인이 아니었다.
> - stream 단일 파드 상한은 코어당 약 19 req/s로 측정됐다. 다만 "142.5 req/s가 천장"이라는 내 판단은 5,000VU에서 226 req/s가 나와 폐기했다.

### 2-1. 그때 뭘 하고 있었나

07-30부터 첨부 없는 순수 채팅 트랙으로 수용량을 재고 있었다. LLM은 스텁(`ttft 700ms + 300토큰 × 20ms`, 설계 6.7초)이라 비용 없이 서버 쪽만 볼 수 있었다.

### 2-2. 뭐가 터졌나

07-30 측정: 6,000VU에서 처리량 100~160 req/s, agent 호출 실패율 **41%**(500 27% + 응답 없음 14%). 그런데 agent CPU는 9~16%로 놀고 있었다 [문서: `2026-07-31-chatstream-부하테스트-계층별-병목-인수인계.md`].

### 2-3. 코드·구성을 열어보니

`dop-ai-stream`의 `ai.agent.url`이 `dop-service-gateway`를 가리켜 모든 트래픽이 게이트웨이를 거쳤다. 증설 전 게이트웨이는 **2파드 × 2코어 = 4코어**였다. 앞뒤로 80코어씩 깔린 사이에서 이 4코어가 처리량을 정하고 있었다. 증설(2 → 20파드) 후 처리량 178~210 req/s, 실패율 14.1%.

그 다음은 닫힌 루프 산식으로 맞춰 봤다.

```
6,000 VU ÷ (ai-stream 내부 23.3초 + agent 호출 3.2초 + k6 think 2초) = 211 req/s  ← 실측 178~210과 일치
```

### 2-4. 처음 시도와 그게 안 된 이유

**① 07-31 게이트웨이 우회 런.** stream이 agent를 직접 부르게 했다. agent 호출 응답헤더 3.2초 → **22ms**, 5xx 14.1% → **0%**. 그런데 처리량은 214 req/s(전날 210)로 그대로였다. 게이트웨이는 지연·에러의 원인이었지 처리량을 정하는 요인이 아니었다. 이 런은 사건 1의 PG 절단으로 끝났다.

**② 07-31 결론: "stream 내부 23초".** 당시엔 stream 내부 지연(페이싱 floor 추정)이 처리량을 정한다고 봤다. CPU가 원인이라고 하진 않았다(stream CPU 4~8%).

**③ 08-12 3,000VU: 142.5 req/s 평탄 → "천장"으로 읽었다가 틀렸다.** 같은 구성(stream 20 + agent 40)에 5,000VU를 넣으니 **226 req/s**가 나왔다. 닫힌 루프에서는 처리량 = VU ÷ (RT + think)라서 RT가 안정되면 처리량은 저절로 평탄해진다. 평탄한 처리량은 포화의 증거가 아니었다. 그 뒤로 포화 판정은 "자원이 리밋에 붙었는가"와 "VU를 올려도 처리량이 안 따라오는가" 두 가지로 했다.

**④ stream 파드당 상한은 우연히 잴 수 있었다.** 08-12 런 중 KEDA가 stream을 1파드로 내린 구간이 있었는데, 그때 1파드가 38 req/s ÷ 2코어 = **코어당 19 req/s**에서 포화했다. 5,000VU 런의 독립 계산(10.5코어 ÷ 226 req/s → 코어당 21.4)과도 맞았다.

### 2-5. 최종 판단과 대가

- 게이트웨이: 지연·에러 요인, 처리량 요인 아님 → 우회로 해소.
- stream: 파드당 상한 코어당 약 19 req/s(단일 파드 포화 실측). 20파드면 약 600~760 req/s.
- 08-12 종합 결론은 stream·agent CPU를 모두 배제한 "공유 병목, DB I/O 유력·미확인"이었다. DB 쪽 지표(`postgres_exporter`)가 없어서 세 런 연속 같은 벽에 막혔다.
- **포트폴리오 문구 "병목은 stream 파드 CPU로 판정"은 기록과 다르다.** 기록은 "게이트웨이는 처리량 요인이 아니었고, stream 단일 파드 상한은 코어당 약 19 req/s"로 둘을 분리한다 → 9절 질문.

## 3. 채팅 1번에 SQL 37문장 — 요청당 DB 왕복 감축

> **3줄 요약**
> - DB가 무너지는 걸 보면서 "채팅 1번에 쿼리 20개"라는 기존 숫자를 의심했다. 요청 전체를 세어 보니 신규 방 37문장 / 7트랜잭션이었다.
> - `nextval` 별도 왕복을 컬럼 DEFAULT로, INSERT 후 재조회를 `RETURNING`으로 바꿔 37 → 23문장. 프로세스당 커넥션은 8 → 5.
> - 제목 사전 판정 트랜잭션을 지우다 한 번 틀렸고, "제목 있음" 방향으로만 생략하도록 고쳤다.

### 3-1. 그때 뭘 하고 있었나

07-31 PG 절단 직후다. 체크포인터(사건 1)와 별개로, 앱 자체 SQL과 커넥션 예산도 같이 봤다.

### 3-2. 뭐가 터졌나

- **커넥션 예산 초과**: 4개 서비스의 PG 커넥션 상한 합이 2,950으로 DB `max_connections`를 넘었다. ai-agent-api 몫이 프로세스당 8(엔진 5 + 체크포인터 3) × 2워커 × 100파드 = 1,600 [문서: `done/2026-07-31-mr212-db-connection-budget.md`].
- **SQL 문장 수**: "채팅 1번에 20쿼리"는 prepare 구간만 센 값이었다. 요청 전체는 **기존 방 31문장 / 신규 방 37문장, 트랜잭션 6~7개**였고 그중 9~11문장이 순수 낭비였다 [문서: `done/2026-08-06-chatstream-요청당-SQL-문장-인벤토리-및-감축안.md`].

### 3-3. 코드를 열어보니

- PK를 앱이 `SELECT nextval`로 따로 뽑은 뒤 INSERT하고 있었다(4~5곳).
- INSERT 후 같은 행을 다시 `SELECT`로 읽고 있었다(4곳).
- prepare가 이미 읽은 thread 행을 제목 판정에서 또 읽었다.
- 요약 백그라운드 트랜잭션이 압축할 게 없어도 매번 3문장을 냈다.
- 커넥션은 LLM 스트림 동안 잡히지 않는다. `astream` 루프는 `async with uow` 블록 밖에 있고 DB 접근은 짧은 블록으로만 쪼개져 있다. 그리고 `AsyncPostgresSaver`는 인스턴스 `asyncio.Lock`으로 직렬화돼 동시 사용 커넥션이 구조적으로 1개다.

### 3-4. 처음 시도와 그게 안 된 이유

**① 커넥션 8 → 5 (07-31, `bf3efc8b`).** 엔진 `pool_size` 5 → 3, 체크포인터 `max_size` 3 → 2·`min_size` 1 → 0. 워커당 약 1.43 req/s, 요청당 점유 200ms로 넉넉히 잡아도 필요 동시성 약 0.3이라 3이면 10배 여유라고 봤다. SQLAlchemy QueuePool은 유휴 커넥션을 회수하지 않으니 `pool_size`가 곧 상시 점유량이다.

**② SQL 관용구 교정 (08-06, `43252a87`).** 시퀀스 6개를 앱에서 뽑지 않고 컬럼 `DEFAULT nextval`에 맡겼다. 앱이 다시 뽑으려 하면 `RuntimeError`가 나게 가드했다. INSERT 후 재조회는 `INSERT ... RETURNING`으로 바꿨다.

**③ 제목 사전 판정 트랜잭션 제거 (`063a0865`) → 틀렸다 → `25f56c0f`.** "thread 락이 막고 있으니 prepare 시점 값과 다를 수 없다"고 가정하고 DB 재조회를 뺐다. 그런데 prepare는 thread 행을 **락을 잡기 전에** 읽는다. 그 사이 같은 방의 직전 run이 제목을 붙일 수 있고, 그러면 유틸리티 LLM을 한 번 더 부르고 usage 이벤트가 하나 더 쌓였다. 고친 방식은 `title_snapshot`의 단조성(제목은 빈 값으로 안 돌아간다)을 이용해, 스냅샷이 "제목 있음"이면 건너뛰고 "미제목"이면 기존대로 DB를 확인하는 것이다. 단조성 전제는 테스트로 고정했다(writer가 하나뿐인지 검사).

**④ 락 해제를 부가 로그 트랜잭션에 합치기 → 되돌렸다.** 종료 구간이 트랜잭션 3개로 보여서 합치면 1개 준다고 봤는데, 툴 호출이 없으면 로그 트랜잭션은 문장이 0개라 애초에 열리지 않았다(SQLAlchemy 세션은 첫 문장에서야 커넥션을 잡는다). 툴 없는 요청엔 이득 0, 취소 보장만 약해지는 거래라 뺐다. "합치면 준다고 세기 전에, 합쳐질 트랜잭션이 실제로 열리는지 먼저 확인할 것"이라고 문서에 남겼다.

### 3-5. 최종 결정과 대가

- 신규 방 **37문장/7TX → 23/6**, 기존 방 **31/6 → 19/4**. 로컬 PG에 `echo=True`로 붙어 전후를 실측했다 [문서 §7-2]. 머지 `add1b0c4` (08-06).
- 커넥션 프로세스당 **8 → 5**(파드당 16 → 10), agent-api 몫 1,600 → 1,000.
- 요약 백그라운드 TX는 압축이 걸릴 수 없는 요청이면 열지 않게 했다(`5dd47a76`).
- 남긴 것: TX5의 `max(sequence)` 제거, 제목 재판정을 가드 UPDATE로 흡수하는 것 등은 로직 변경이라 결정 사항으로 미뤘다.

## 4. ai-file 파드가 5분마다 OOM — glibc mmap 임계값 + MuPDF store

> **3줄 요약**
> - 첨부 `/read` 부하 중 ai-file 파드(limit 1Gi) 메모리가 5분간 우상향하다 OOMKill됐다.
> - 파이썬 누수가 아니었다. glibc가 mmap 임계값을 스스로 올려 큰 블록이 OS로 안 돌아가는 래칫과, MuPDF가 닫힌 문서의 렌더 캐시를 붙드는 것, 두 원인이 겹쳐 있었다.
> - `MALLOC_MMAP_THRESHOLD_=131072`와 렌더 후 `store_shrink(100)`를 세트로 걸어 정상 상태 989MB → 280MB, 요청당 증가 79배 감소(dev 측정).

### 4-1. 그때 뭘 하고 있었나

사건 1·5와 같은 첨부 read 부하테스트다. ai-home 쪽 게이트를 만든 뒤, 실제로 파일을 파싱하는 ai-file 쪽 메모리를 보고 있었다.

### 4-2. 뭐가 터졌나

파드 20개가 `/read` 부하에서 5분간 서서히 올라 1G를 찍고 OOMKill. "요청이 끝나면 반환돼야 하는데 우상향한다"가 첫 관찰이었다. 요청당 RSS 증가 **2.322MB** [문서: `ai-file/done/2026-07-28-부하테스트-OOM원인규명-및-응답지연-분해.md` §1].

### 4-3. 코드를 열어보니 (먼저 "무엇이 아닌지"부터)

파드 안에서 `/proc`·cgroup을 직접 읽었다.

```
anon 989.8 MB / file 10.4 MB / memory.events max 0 / Private_Dirty ≈ RSS
```

- `file` 10MB → 페이지 캐시 아님(`/scratch` 의심 기각).
- `max 0` → 커널이 눌러서 생긴 플래토 아님.
- 전부 private dirty anon → 할당해서 실제로 건드린 힙.

파드가 20개라 엔드포인트를 찔러 볼 수 없어서, 요청마다 스스로 남기는 계측기 `memprobe`를 만들었다(`cf06655`). `perform_read` 한 곳에 걸어 HTTP·큐 컨슈머를 다 덮었다. 핵심 필드는 `sys.getallocatedblocks()`다. **RSS는 오르는데 blocks가 평평하면 파이썬 참조 누수가 아니다.** 6개 런 전부 blocks가 평평했다.

회수 프로브(gc → malloc_trim → store_shrink → malloc_trim)로 회수분 출처를 나눴다. gc는 21샘플 전부 0.00, glibc trim 119.5MB, MuPDF store 97.3MB.

| 원인 | 메커니즘 |
|---|---|
| glibc 동적 mmap 임계값 | 3MB 픽스맵을 free하면 glibc가 임계값을 그 크기(최대 32MB)로 **올린다**. 이후 같은 크기 할당은 힙에서 나와 OS로 안 돌아감 → 하이워터마크 래칫 |
| MuPDF store | `with fitz.open(...)`이 닫힌 뒤에도 죽은 렌더 캐시를 붙든다. `/read`는 요청마다 `mkstemp`로 새 경로에 받아 새로 열기 때문에 요청 간 재사용 가치가 0 |

### 4-4. 처음 시도와 그게 안 된 이유

- **mmap 임계값만 (3차 런)**: 요청당 0.176MB로 줄었지만 1,015MB 플래토에서 결국 OOMKill.
- **store 상한을 낮추려 했다**: `fitz.TOOLS.store_maxsize`는 PyMuPDF 1.27에서 getter/setter가 미구현이라, 대입하면 staticmethod를 정수로 덮어쓸 뿐인 "성공한 척하는 no-op"이었다. 실제로 듣는 건 `store_shrink`뿐.
- **"store 상한 256MB면 플래토 558MB" 예측이 407MB 빗나갔다**: 2차 런의 301.5MB를 "자연 바닥"으로 읽었는데, 그건 20요청마다 강제 회수하는 개입 하의 값이었다. 관찰 런과 개입 런을 나눠야 한다는 걸 여기서 배웠다.
- **둘은 세트였다**: mmap 설정이 없으면 store를 비워도 glibc free list에 반납만 되고 OS로 안 간다(`store_shrink`는 `munmap`을 안 한다). mmap 설정이 큰 블록을 mmap으로 보내 둬야 free 즉시 반환된다.

### 4-5. 최종 결정과 대가

- `MALLOC_MMAP_THRESHOLD_=131072`(기본값 128KB를 **명시**하는 것 자체가 동적 조정을 끈다) + 렌더 직후 `store_shrink(100)`.
- B-2 런: 정상 상태 RSS **275.6~287.8MB**, 요청당 증가 **0.0295MB**(2.322 대비 78.7배) [문서].

- 대가: `store_shrink`는 프로세스 전역이라 동시성을 올리면 다른 in-flight 요청의 캐시를 날린다(정합성은 refcount로 안전, 재파싱 비용만). 지금은 /read가 직렬화(inflight=1)돼 있어 간섭이 없다.
- 후속(07-29~30): 잡 경계 `malloc_trim`을 처음엔 "anon/limit ≥ 0.60일 때만" 걸었는데(`1a8c044`), pptx 최대 45%·xlsx 22%라 한 번도 안 불렸다. 60초 쿨다운 **주기**로 뒤집었다(`2830d7f`). 트림 20~40ms vs 잡 1.8~3.5s라 오버헤드 0.1% 미만.

## 5. 응답 300초의 정체 — 내가 만든 첨부 게이트의 재시도 낭비

> **3줄 요약**
> - 파일 하나를 20번 읽는 턴이 300초 걸렸다. 당연히 ai-file 파싱이 느린 줄 알았는데 파싱은 11.4초(3.8%)였다.
> - 82%(약 247초)는 내가 07-21에 AI Home에 넣은 첨부 read 게이트의 재시도 낭비였다. 30초 기다리다 busy로 돌아오면 다음 라운드에서 처음부터 30초를 또 기다렸다.
> - VU를 60 → 30으로 낮춰 게이트 포화를 없앤 조건에서 120초가 됐다. 게이트 자체 수정(누적 대기 예산)은 제안만 했다.

### 5-1. 그때 뭘 하고 있었나

사건 4와 같은 날, 같은 부하테스트의 지연 쪽이다. 측정 대상은 k6 → ai-home → RabbitMQ → ai-file → Redis → ai-home의 한 턴(ReAct 슈퍼스텝 20회, LLM 스텁 주입 지연 20.7초).

### 5-2. 뭐가 터졌나

VU 60에서 턴 응답이 **300초**.

| 항목 | 시간 | 비중 |
|---|---|---|
| ai-file 파싱 | 11.4s | 3.8% |
| 큐 대기 | 54.3s | 18.1% |
| LLM 스텁 | 20.7s | 6.9% |
| **게이트 busy 낭비** | **~247s** | **~82%** |

### 5-3. 코드를 열어보니

게이트는 07-21에 내가 만든 `AttachmentReadGate`다(`67c0b720` 외 일련). 첨부 base64가 `state["messages"]`에 쌓여 턴 내내 메모리를 차지하니, 게이트 permit을 **턴 단위**로 잡게 설계했다. 문제는 타임아웃 분기였다.

- `executor.py:1535`가 게이트 타임아웃 시 턴을 죽이지 않고 "busy" 관찰을 LLM에 돌려준다.
- 스텁이 다음 라운드에서 또 read를 부른다.
- `acquire_for_run`은 실패하면 예약을 되돌리므로 **처음부터 30초를 다시 기다린다.**

증명은 로그 간격으로 했다. 연속 `gate busy` 간격 9구간 평균 **30.843초**(편차 0.208) = `acquire_timeout_seconds` 30.0 + 라운드 오버헤드 0.843초. 턴당 약 8번 걸렸고, 20회 read 중 12회만 ai-file에 닿았다(의도한 부하의 60%). k6가 타임아웃으로 포기한 뒤에도 ai-home 턴은 계속 돌며 permit을 쥐고 있었다(같은 VU의 iteration이 시간상 겹치는 걸로 확인).

### 5-4. 처음 시도와 그게 안 된 이유

- **"permit을 read 단위로 바꾸면 된다"** → 기각. 메모리가 턴 내내 점유되므로 read 직후 반납하면 게이트가 막으려던 실패 모드(N개 턴이 각자 누적 base64를 들고 있는 것)를 못 센다. 설계 스펙 §7-1에 "read 직후 반납 금지"가 있었다.
- **"acquire_timeout 30 → 3"** → 기각. 대기가 짧아지면 permit 획득 확률도 떨어져 성공 read가 더 줄어든다.
- **"LangGraph 체크포인트 O(n²)가 라운드 오버헤드"** → 결론은 맞았지만 근거가 틀렸다. busy 라운드(143ms)로 오버헤드를 쟀는데, busy 라운드는 read가 거부된 라운드라 응답 파싱·ToolMessage 누적이 일어나지 않는다. 측정 조건이 재려던 대상을 구조적으로 배제하고 있었다. 07-29에 "미설명 24.2초"가 새 병목이 아니라 이 잘못 뺀 값의 잔차였다고 보정했다(진짜 라운드당 오버헤드 1.35초).

### 5-5. 최종 결정과 대가

- **제안**: 횟수 제한이 아니라 **턴 단위 누적 대기 예산**(턴 전체 대기 총량 30초, 각 read는 `min(남은 예산, 타임아웃)`만 대기). 하지만 이후 "우선순위 하락"(§6-5)으로 내려갔고, AI Home 저장소에 이 수정 커밋은 없다.
- **120초는 게이트를 고쳐서 나온 값이 아니다.** VU를 30으로 낮춰 게이트 포화를 없앤 측정이다. 그때 남은 항목은 KEDA 증설 임계값이 만드는 큐 대기 61초와 ai-home 라운드당 오버헤드 27.1초였다.
- 부수 발견: KEDA가 "큐 깊이 > 파드 × T"로 스케일하면 대기 = T × 서비스시간으로 파드 수가 약분된다(5 × 0.569 = 2.85초, 실측 3.28~3.61초). 그래서 임계값 5 → 1~2가 단일 최대 레버라고 적었다.
- 서비스 경계 주의: 게이트는 **ai-file이 아니라 AI Home 코드**다. 포트폴리오에선 "ai-file 부하테스트" 아래에 있다.

## 6. PPTX 한 번 읽는 데 3초 — 창 패키지 재압축

> **3줄 요약**
> - pptx `/read`가 요청당 1.79~3.48초로 PDF(0.569초)의 3~6배였다. 그중 89%가 요청한 슬라이드만 담은 임시 pptx("창")를 만드는 함수였다.
> - 원인은 재압축이었다. 원본 멤버 5,697개를 전부 풀었다 다시 압축했는데, 대부분이 16KB 미만 XML이라 zlib 스트림당 고정 비용이 지배했다.
> - 원본을 바이트 그대로 복사하고 바뀐 매니페스트 2개만 zip 뒤에 덧붙였다. 함수 단위 0.880s → 0.024s(37배), 배포 후 요청 중앙값 약 1.05s.

### 6-1. 그때 뭘 하고 있었나

사건 4의 후속으로 확장자별 테스트(§6-6)를 하던 중이었다. PDF에서 얻은 처방이 pptx에도 통할 거라 생각했다.

### 6-2. 뭐가 터졌나

pptx 요청당 1.79~3.48초. 그리고 30분 창에서 10개 파드 중 3개는 메모리가 끝까지 올랐다(+0.39~0.78MB/req) [문서: `ai-file/done/2026-07-29-pptx-창패키지-재압축-규명-및-메모리래칫-유계판정.md`].

### 6-3. 코드를 열어보니

`_create_slide_window`가 요청 슬라이드만 담은 임시 pptx를 만들 때 `copy(info)`로 원본 `compress_type`을 그대로 가져와 **전 멤버를 inflate → deflate** 했다. 원본과 같은 바이트를 다시 만드는 비용이었다.

### 6-4. 처음 시도와 그게 안 된 이유

**① 멤버별 압축 판정 (`ff37385`, 07-29 14:17).** 이미 압축된 멤버는 다시 압축하지 않게 했다. 합성 픽스처에선 6.6배였는데 실제 파드에선 2.33s → 2.13s로 파드 간 편차 안이었다.
→ **틀린 레버였다.** 실파일은 5,697멤버, 89%가 16KB 미만이라 재분류된 건 198개(3.5%)뿐이었다. zlib은 스트림마다 약 320KB 할당(128KB `head` 테이블을 0으로 채우는 것 포함)의 고정 비용을 내서 200바이트 멤버도 큰 멤버와 같은 비용이었다. read당 zlib 스트림 11,394개, 할당 회전 약 2GB였다. 압축 설정으로는 못 고친다. 스트림 수 자체를 없애야 했다.

**② 덧붙이기 (`48ed080`, 07-29 15:02).** zip은 파일 끝의 중앙 디렉터리로 멤버를 찾고, 같은 이름이면 **뒤 엔트리가 이긴다.** 그래서 원본을 `shutil.copyfile`로 바이트 그대로 복사하고(리눅스에선 sendfile/copy_file_range라 유저 공간 버퍼도 없다) 바뀐 매니페스트 2개만 `mode="a"`로 덧붙였다.

```
rewrite every member   0.880s   11,394 streams
per-member compression 0.544s   11,394 streams
append                 0.024s        2 streams   (37x)
```

### 6-5. 최종 결정과 대가

- 지연: 함수 단위 **0.880s → 0.024s**(macOS, 실파일 모양 픽스처). 배포 후 요청 `latency_ms` 중앙값 **1,048ms**(다운로드 216 + 파싱 832).
- 메모리: 원인은 glibc 파편화였다. 사건 4의 주기 `malloc_trim`(`2830d7f`) 후 30분 재측정에서 9/9 파드 바닥 평평, OOMKill 0 → 유계 확정.
- CPU: 94~97% → 89~90%. "사용률 90%인데 throttle 4%" 조합이라, 워크로드가 직렬이라 1코어 이상을 원하지 않는다고 판단했다. CPU limit 상향은 무의미, 처리량은 파드 수로 늘린다.
- 대가: zip은 멤버를 지울 수 없어 원본 매니페스트가 파일에 남는다. 앞 엔트리를 읽는 리더가 있으면 창이 적용 안 된 것처럼 보인다 → `_warn_if_window_not_applied`로 감시.
- 교훈으로 남긴 것: "확장자마다 원인이 다르다(pptx=서비스타임, xlsx=래칫, pdf=store+mmap). PDF 처방을 일반화하면 안 된다." 그리고 로그 발췌(파드 1~2개, 몇 줄)로 판정하다가 07-29 하루에 네 번 틀린 뒤, Grafana로 Loki 전량(30분 4,992샘플·10파드)을 뽑아 판정하는 쪽으로 바꿨다.

## 7. 메신저·전자결재 MCP 도구 연동 — 결재 카드와 간편 비밀번호 재시도

> **3줄 요약**
> - MCP 서버(dop-ai-mcp)는 타 팀원이 만들고, 나는 그 도구를 에이전트가 쓰게 연결했다. 메신저는 요약 기능을 MCP 조달 도구로 옮겼고, 전자결재는 첫 연동부터 결재 카드까지 했다.
> - 전자결재는 연동 전엔 `appCode=approval`이 요청 전체를 400으로 막고 있었다. 연동 후엔 결재 카드 버튼과 승인 폼을 LLM 없이 서버가 이었다.
> - 간편 비밀번호가 틀리면 LLM을 다시 부르던 흐름을, 서버가 값을 유지한 새 승인 폼을 띄우는 재시도(최대 3회)로 바꿨다.

### 7-1. 그때 뭘 하고 있었나

8월에 메신저 요약 기능을 만들었고(`done/2026-08-11-메신저-도메인-요약-설계.md`부터), 9월에 그걸 도구(tool)로, 다시 MCP 도구로 옮겼다. 10월엔 전자결재 MCP가 열리면서 에이전트 쪽 연동과 결재 UI 카드를 맡았다. 메신저 MCP의 첫 연동 커밋(`97968846`, 09-06)은 외주 jueon21의 것이고, 나는 그 이후의 에이전트 흐름을 맡았다.

### 7-2. 뭐가 터졌나 / 무엇이 문제였나

- **메신저**: 요약 턴은 스레드 맥락을 통째로 버리고, 조달한 원문은 그 턴에만 있다가 사라졌다. 그래서 "이 방 요약해줘" → "3번 항목 자세히"가 **구조적으로 불가능**했다(메모 `messenger-summary-tool-migration-motive`). tool화의 목적은 검색 백엔드 교체가 아니라 후속 대화였다.
- **전자결재**: FE가 `approval`을 보내면 `unsupported appCode`로 요청 전체가 400이었다(`942abf0f` 제목: "appCode approval 이 요청 전체를 400 으로 막고 있었다").
- **간편 비밀번호**: 결재 비밀번호가 틀려 MCP가 400을 주면 LLM을 다시 불러 재시도를 유도했다. 규격서 담당 회신(v2.5)이 서버가 재시도 폼을 맡는 것으로 정리됐다(`done/2026-10-21-결재카드-v2.5-plan.md`).

### 7-3. 코드·계약을 열어보니

- **메신저(09-15~09-28)**: MCP가 조달 도구 2종을 `audience=internal`로 냈다. 처음엔 "서버 코드가 부르고 LLM은 모른다"로 설계했다가, 09-16 확정 계약(『MCP 연동 정의서 v15』)을 받고 정정했다. 가장 큰 정정은 "MCP는 안읽음 경계를 걸지 않고 `room.lastReadMessageId`로 준다"였다. 반대로 적어 뒀으면 맥락 확대가 에러 없이 통째로 죽을 뻔했다(`51648e6f`). 09-17 회의 뒤 `agent`로 바꿔 나노 모델이 고르는 MCP 도구로 옮겼다(`d60a5a53`). 이후엔 방 목록·검색 묶음, 멘션 날조 방지, 이모지·서식 유실 같은 품질 수정이 이어졌다(09-18~09-28 커밋들).
- **전자결재 첫 연동(`942abf0f`, 10-01)**: 메신저 선례를 분석해 "등록 5곳"(앱 메타·appCode 매핑·LLM 투영 passthrough 37종·선행 도구 표·승인 폼 예시)을 공통 가이드로 문서화했다. 결정: 결재 처리(승인·반려·보류)의 docId는 **결재 대기 목록에서만** 가져온다(검색 결과엔 내 차례가 아닌 문서가 섞인다). FE가 안 보내면 영향 0이라 "우리 먼저 배포해도 된다"고 정리했다.
- **결재 카드(10-16 설계)**: LLM은 `show_approval_document_card(docIds)`로 "띄울지·대상"만 정하고, 내용은 서버가 이번 run의 MCP 상세 응답을 변환한다(C안). LLM이 payload 전체를 쓰면 탭 7개 분량 출력 토큰·옮겨 적기 오류가 생기고, 상세 조회마다 자동으로 띄우면 단답에도 카드가 뜬다.

### 7-4. 처음 시도와 그게 안 된 이유

- **카드 버튼 클릭 후 흐름**: 기존 선택 목록 패턴(A안, LLM 경유)은 1~3초 지연이 붙고 LLM이 다른 도구·문서를 부를 여지가 있었다. 그래서 **B안 — 서버 직행**으로 갔다. 같은 도구 호출(tool_call_id)이 재개되면 서버가 MCP `availableActions[].tool`로 run_tool 승인 단계에 바로 들어간다(`cb280664`, 10-16). 카드와 승인 폼의 interrupt가 한 run의 같은 도구 호출에서 연속 두 번 걸리므로, 승인 폼 componentId(run_id + tool_call_id 해시)가 최초·재개에서 같도록 같은 tool_call_id로 위임했다.
- **비밀번호 칸 노출 판단**: "모르면 선택 칸으로 노출"은 비밀번호 미사용 회사가 다수라 빈 칸이 대부분에게 보이고, "숨겼다가 400 나면 재요청"은 사용 회사가 매번 1회 실패하고 첫 폼에서 고친 의견이 유실된다. 그래서 `needsSimpleCode` 기준으로, 상세가 없으면 서버가 폼 조립 전에 1회 조회하게 했다(10-15 설계 D3).
- **비밀번호 원문은 LangGraph 상태를 지나가지 않게 했다(D4).** 체크포인트 flush 때 사후 삭제하는 방식은 세이버가 도메인 키를 알아야 하고, 빠뜨리면 PG에 남는다(사건 1의 flush가 바로 그 경로다). resume 전에 꺼내 요청 범위 메모리에 두고 MCP 호출 순간에만 합쳤다.
- **간편 비밀번호 재시도(`18a36066`, 10-21)**: LLM 재호출 대신 같은 실행 안에서 새 componentId(회차별) 승인 폼을 돌려준다. 다른 칸은 직전 제출값 유지, 비밀번호 칸만 빈칸. 3회째도 틀리면 일반 실패 카드. MCP 문구 변경에 대비해 거절 판정을 "400 + simpleCode/간편 비밀번호/결재 비밀번호 문구"로 넓혔다. 일괄 결재에도 같은 재시도를 붙였고(`fd9781d6`), 일괄 처리 일부 성공 결과 카드는 서버가 조립하게 했다(`4349882e`).

### 7-5. 최종 결정과 대가

- 결정의 공통축: **LLM은 "무엇을 할지"만, 사용자 화면과 재시도는 서버가 결정적으로.** 지연·오동작 여지를 줄이는 대신 서버가 MCP 응답 형식(필드명 `isMe`·`isCurrent`·`isHolding` 등)에 묶인다. 이름이 다르면 변환기 한 곳만 맞추도록 분리했다.
- 대가: 카드·폼 렌더러와 DO AI enum은 FE·다른 팀 몫이라 배포 순서가 얽혔다. MCP 쪽 선행 요청(R1 필드·R3 password 포맷과 로그 마스킹)이 반영돼야 완전해진다.

### 7-6. 그 결정이 들어간 코드 (ai-home-poc)

## 8. DB가 큐 노릇을 하고 있었다 — ai-automation MQ 중심 재설계

> **3줄 요약**
> - 동료가 만든 자동화 실행 구조는 DB 테이블이 대기열, PG NOTIFY가 신호였고, RabbitMQ는 executionId를 Worker 하나에 건네기만 했다. 큐 기능을 앱 코드로 다시 만들고 있었고 대기량은 보이지 않았다.
> - MQ가 대기를 맡는 구조(start/continue 큐 + 지연 큐 + DLQ)로 다시 설계했다. 1판은 담당자 피드백에서 "상태를 저장한 시점과 다음 서비스에 넘긴 시점이 구분되지 않는다"는 지적을 받았고, 2판에서 step 접수 상태·세대 번호로 그 구분을 넣었다.
> - 2판을 하루(10-29) 동안 29커밋으로 구현하고 11-02 develop에 머지했다. 운영 실행은 아직 꺼져 있다.

### 8-1. 그때 뭘 하고 있었나

10월 중순부터 ai-automation 스케줄러·인증 구조를 검토하고 있었다(`2026-10-15-scheduler-and-auth-review.md`). 자동화의 step 실행은 AI Home StepRun API가 하고, ai-automation은 접수·대기·동시 실행 제어·재시도·복구를 맡는다.

### 8-2. 뭐가 터졌나 / 무엇이 문제였나

장애가 터진 건 아니다. 구조가 계속 한 방향으로 무거워지는 게 보였다.

- 10-23: Worker 파드마다 publisher가 1초마다 DB 트랜잭션(전역 잠금 + 조회)을 돌렸다. 밀린 실행이 DB에 있어 RabbitMQ 지표로 backlog가 안 보였다. 회사/사용자 상한에 걸린 실행은 2~4초마다 DB와 큐를 왕복했다(`2026-10-23-queue-split-execution-design.md` P1~P3). 이때 큐 분리안(Q_start/Q_continue/Q_delay)을 제안했지만 채택되지 않았다.
- 10-26: 신규 실행이 100건이어도 큐에는 최대 8건(전역 한도)만 들어가고 나머지는 DB에서 기다렸다. "MQ가 하는 일은 executionId를 Worker 파드 하나에 건네는 것뿐"이라고 정리해 전달했다(`2026-10-26-execution-queue-role-review.md`).
- 10-27: 그 뒤 반영된 변경(`a1bc296`)으로 API 요청 경로에서 MQ가 아예 빠졌다.

### 8-3. 코드를 열어보니

```
[1] 접수: execution INSERT 커밋 → 202 → DB 트리거(migration 008)가 NOTIFY
[2] 발행: Worker 안 리더 publisher(pg_try_advisory_lock로 선출) → reserve(전역 8 / 회사 8 / 사용자 2, lease 10초)
          → 트랜잭션 밖 MQ confirm → token·generation·lease 맞을 때만 SENT
[3] 실행: claim 때 전역+회사 advisory lock 아래서 한도 재검사, 초과면 +2~4초 뒤로 (메모리 RetryDispatch)
[4] 완료: AI Home이 결과 저장 + dispatch PENDING → NOTIFY → [2]
```

큐의 기본 기능(대기열·지연 재시도·TTL·재전달·DLQ)을 DB와 앱 코드로 다시 만들고 있었다. 뿌리는 두 결정이었다. ① AI Home에 MQ 연결을 두지 않음, ② 회사/사용자 동시 실행 한도를 DB에서 엄격히 지킴 [문서: `done/2026-10-28-ai-automation-db-centric-dispatch-issues.md`].

### 8-4. 처음 시도와 그게 안 된 이유

**① 1판 설계 (10-28).** 대기열은 MQ가 맡고, 어느 Worker가 어느 step을 받아도 되게 하고, pg_notify·리더 선출·DB COUNT·메모리 재시도 큐를 없앤다. MQ 재전달은 정상 동작으로 본다.

**② 담당자 피드백 (10-29).** 1~7번 장애 처리 보완 요청이 왔다(`request/done/2026-10-29-mq-centric-critical-failure-feedback.md`). 대표적인 것:
   - Worker가 RUNNING으로 바꾸고 AI Home에 넘기기 전에 죽으면, 재전달된 메시지를 "QUEUED가 아니면 ACK 후 무시" 규칙으로 버려 step이 멈출 수 있다.
   - 슬롯 중복 획득, 오래된 반납, Redis 유실.
   - 승인 재개는 같은 step 행(같은 requestId)을 다시 쓰니 requestId만으로 "이미 발행됨"을 구분할 수 없다.
   
   공통 지적은 **"DB에 상태를 저장한 시점과 다음 서비스에 넘긴 시점이 구분되지 않는다"**였다.

**③ 2판 (같은 날).** 그 구분을 **이미 있는 DB 필드와 세대 번호**로 표현하고, 모든 메시지 처리를 "현재 상태를 보고 남은 넘김을 마저 한다" 하나의 규칙으로 통일했다.
   - 실행 상태(RUNNING)와 step 접수 상태를 분리. step 행 `PENDING` = AI Home 미접수. AI Home이 접수와 같은 트랜잭션에서 RUNNING을 기록하므로 PENDING이면 "아직 안 돌고 있음"이 보장된다.
   - 모든 메시지 처리의 끝은 `ensure_handoff`: PENDING이면 저장된 requestId·body로 재호출(AI Home `accept()` 멱등에 의존).
   - ACK는 AI Home 202 이후.
   - generation(생성 시 1, 승인 재개마다 +1)을 메시지·슬롯 멤버(`executionId:generation`)·발행 기록에 넣어 늦게 온 메시지를 차단.
   - 회사/사용자 한도는 없애고(D8), 예약 tick 발행 순서만 회사 단위 라운드로빈.

### 8-5. 최종 결정과 대가

- **구현**: `feature/mq-centric-execution` `dc13adf..c7b295b` 29커밋(대부분 10-29 하루) + AI Home `feature/automation-mq-callback` 16커밋. develop 머지 `52ad1e1`(11-02). DB 큐·pg_notify 경로는 마이그레이션 010으로 제거(`b25097a`).
- **검증**: unit+integration 518 passed. 장애 주입 스크립트 5개 시나리오(전이 직후·HTTP 응답 직후·202 직후·다음 step 저장 직후 Worker 강제 종료, 커밋 전 응답 유실) PASS — step 실행 1회, 슬롯 누수 없음 [문서: `2026-10-29-mq-centric-implementation-result.md`].
- **대가·남은 한계**:
  - 운영 실행 전. 배포 템플릿이 `EXECUTION_ENABLED=false`, Worker `replicas: 0`. RabbitMQ 3.13.2에서 `reject(requeue)`가 delivery-limit에 잡히는지(로컬 4.x에선 reject만 잡혔다), Redis Cluster 연결, 상한 K 값(K=8/MIN=4/MAX=300은 측정 전 보수값)이 미확인.
  - "큐 길이로 KEDA 증설"은 **설계만**이다. 저장소에 ScaledObject가 없고, 구현된 건 AI Home 부하 게이지에 자동화 step을 합산한 것(`308bba64`)이다.
  - 회사 공정성은 예약 tick 한 번의 발행 순서에만 적용되고, 발행 후엔 FIFO다.
  - 슬롯이 없으면 메시지를 ACK하지 않고 "쥐고 대기"하므로 start 큐에 `x-consumer-timeout`을 두고, 앱 대기 기한(60분)이 그보다 작아야 기동되게 설정 검증을 넣었다. ai-file knowledge 큐에서 `consumer_timeout`(30분)을 넘겨 채널이 끊기고 같은 잡이 두 파드에서 돌던 경험을 미리 막은 것이다.
  - 사용자 없는 예약 실행 인증(IAM 위임)은 요청서·개발 가이드까지이고, 코드는 `auth_mode=disabled`면 거부한다.
  - 머지 후 동료가 static step·admission fence를 위에 올리고 있다(`20a11cd`, `021d59b`).
