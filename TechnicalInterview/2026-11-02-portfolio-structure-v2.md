- 역할: 외주(C 개발만 해옴)가 메일 API 요구사항·전체 아키텍처 설계. 본인은 메일 개발이 처음이었고, C 중심 설계를 Spring 구조에 맞게 함께 재설계 + 사용자별 SQLite 커넥션을 Spring 트랜잭션 기반으로 구현 + append 수신 개발. 7장 역할 제목 "외주와 협업, Java 구조는 본인"
- SQLite 구조: 사용자마다 개인 4종(메일 mindex·대용량 첨부·MDN·웹폴더) + 공용 reserv(예약 메일함) 1개. mindex·reserv를 같은 트랜잭션으로 묶음
- 원자성: 처리 중 예외는 둘 다 rollback, 커밋 단계 원자성은 미보장(69행 f5b8ec23과 일치). 기존 C와 같은 구조, 예약 메일함 한정이라 수용 → 8장 각주 "한계"로 명시
- WAL 미사용: k8s에서 SQLite가 NFS 위라 WAL 불가 → rollback journal. 면접 답변 포인트: 꼭 필요했다면 `ATTACH DATABASE`로 원자 커밋 가능(WAL 아닐 때만)
- busy lock: 주로 mindex, 같은 사용자가 Outlook(IMAP)과 웹메일을 동시에 쓸 때. timeout으로 일부 대기. reserv 쓰기는 드묾
- 배포: 클러스터 9개 각각에 store 2대, 처음부터 증설 가능하게 설계. 사용자 생성 시 담당 store가 DB에 지정 → 한 사용자는 한 store만 접근(파드 간 같은 파일 동시 접근 없음). 재배치는 DB 갱신 후 이동 (덱에는 미기재, 면접 답변용)
