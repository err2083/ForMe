## 0. 전체 그림

**무엇이었나.** 그룹웨어(다우오피스) 서버는 Java·Spring·JPA·Ehcache(Terracotta) 구조다. 2023년 상반기에 약 3,400명 고객사에서 출근 시간마다 조직도 API 때문에 장애가 났고, 그걸 쿼리 쪽에서 고쳤다(사건 A). 같은 해 가을, 직원 약 1만 명(등록 9,724명) 고객사가 단독형으로 들어오면서 "출근 피크를 버티는지"를 오픈 전에 증명해야 했다(부문 KPI). 테스트 장비를 만들고 고객 환경(유저 12,000 · 부서 3,000)을 재현해 JMeter로 출근 시나리오(모바일 로그인 → 홈 → 출근, API 44개)를 돌렸다. 터진 순서대로 조직도(B) → 대화방(C) → 캐시 설정(D) → 근태 표시(E)를 고쳤고, 오픈 직후에는 18시 퇴근 시간 장애(F)를 잡았다.

**내 역할.**
- 테스트 장비 구축, 고객 환경 재현, JMeter 시나리오, Scouter 분석은 혼자 했다(사용자 확인, 리서치 노트 교차 검토 절).
- 서버 1차 개선 10건(엑셀 `개선항목` 시트: 노티파이어 컨텐츠 길이, 조직도 캐시, 유저/부서 쿼리, 대화방 page 제거, 알림 슬로우 쿼리, 조직도 근태 동기화, 2티어 장비, 대화방 부하 2, 조직도 캐시 evict, 조직도 native)은 본인 작업이다.
- 2차 11건 중 본인 담당은 5건이다: 채팅 쿼리 2차, 근태 표시, 게시판·커뮤니티 슬로우 쿼리, `/ehr/timeline/info`. 생일 가젯·badge·공지톡·관리자 권한·DB 커넥션·로그인 부하는 **내 작업이 아니다**.
- 기능 테스트는 품질관리팀·모바일개발팀과 함께 했다(엑셀 `보고` L32). PC 메신저 쪽 렌더링 개선(스레드 분리 등, `개선항목` 1~8번)은 메신저 개발 담당이 한 것이다.
- 쿼리 일부는 DBA(엑셀에 "김한조 대리 의견", "DBA 통해 쿼리 받음")와 같이 봤다. 이 경계는 아래 사건마다 따로 적었다.

## 1. 사건 A — 약 3,400명 고객사, 출근 시간마다 조직도 API가 죽었다 (2023.3~9)

> **3줄 요약**
> - 출근 시간 `users/changed`(조직도 사용자 변경분) 응답이 08:00 10초 → 08:20 30초 → 08:30 장애. 3월 초·4월 초에 반복됐다.
> - 변경 기준 시각(rdate)이 없으면 전 사원을 읽었고, 사용자 한 명을 변환할 때마다 부서원 쿼리가 따로 나갔다. 부서 변경분 조회는 부서원 테이블을 OR 조건 6개로 조인했는데 인덱스가 없었다.
> - 메신저 전용 변환기, 연관관계 LAZY, "부서원이 바뀌면 부서도 바뀐 것"으로 만드는 `dirty()`, 인덱스 3개로 고쳤다. nGrinder 부서 API TPS 0.7 → 8. 하지만 여전히 "변경분" 구조였다.

### 그때 뭘 하고 있었나
고객사 유지보수(SM)를 하던 시기다. 같은 시기 커밋을 보면 전자결재 재기안, 자동결재선, 스패로우 보안 조치, 고톡 서비스 종료 대응(GO-44096, 2023-06~07)을 같이 하고 있었다. 엑셀 `개요` B38~B40에 "현재 고톡 서비스 종료 개발로 인해 멈춘 상태, 1차 개발 반영도 미루어진 상태"라고 적혀 있다. 조직도 일은 장애 대응이었지만 다른 급한 일에 밀려 가며 했다.

### 뭐가 터졌나
- 엑셀 `userschanged`: access log 기준 8시경 응답 약 10초 → 8시 10분 점점 증가 → 8시 20분 30초 → 8시 30분 장애.
- 엑셀 `개요`: "3월 초, 4월 초 장애 발생". 스레드 덤프로 원인 후보를 뽑았다. Apache Tika, ImageMagick은 "원인 아닌 것으로 확인"하고 뺐다. 게시판 가젯·전사게시판 권한 체크·TodayBadge는 담당자 미지정으로 남았다. Gson(유저 알림 설정) 3.5.13.0, 조직도 API(users/changed, departments/children) 3.5.14.0, 근태 동기화·`addSessionId` 3.5.15.0으로 릴리즈 계획을 잡았다.
- "3,400명"은 이 고객사의 `users/changed` 결과 유저 수 3,401명에서 나온 숫자다(엑셀 `userschanged` E319).

### 코드를 열어보니
엑셀 `userschanged`·`departmentschildren`에 쿼리 플랜과 분석이 남아 있다.
1. **rdate가 null이면 전체 유저를 가져온다.** `go_users WHERE company_id=530 AND (OPEN) AND (ONLINE|DORMANT) ORDER BY id LIMIT 5000`. 처음 접속하거나 로컬 데이터가 없는 클라이언트가 전 사원을 받는다.
2. **변환 중 추가 쿼리.** 유저를 모델로 바꾸면서 `UserProfile`, `DeptMember`, `CustomUserProfile`을 읽었다. UserProfile·CustomUserProfile은 2차 캐시 덕분에 이후 요청에선 쿼리가 안 잡혔지만, **DeptMember는 매번 쿼리가 났다**("고객사 2천 명이면 API 하나에 DeptMember 쿼리 2천 번", D359). DeptMember는 사용자의 부서를 보여 주려는 값인데, **메신저는 부서를 `departments/children`으로 따로 받으므로 필요 없었다**(D361~D363).
3. **부서 변경분 조회.** 부서 ⟕ 부서원을 조인해 부서·부서원의 created/updated/deleted ≥ rdate를 OR로 비교했다(`904d25f5c95` 이전 `DepartmentSpecifications.byCompaniesAndDateAsRevisionIncludeDeptMember`). `go_dept_members`에 `department_id` 인덱스가 없었다. DBA 의견은 "리미트가 크게 잡혀 있어 풀스캔, 오더링 없음 → 튜닝 필요"(F152).
4. **rdate가 3월 31일 이전이면 급격히 느려졌다**(`departmentschildren` B31). 메신저는 "변경사항이 있으면 전체를 호출하는 로직"이라 2번 호출했다(B210).
5. 부하 중 `go_config_nodes` 테이블에서 Idle in Transaction 커넥션이 풀리지 않는 현상도 봤다(D327~D330). 테스트 장비 로우가 5만 건이라 생긴 것으로 추정했다.

### 처음 시도와 그게 안 된 이유
엑셀 `개요` C24에 1차 개발 계획과 결과가 그대로 있다.
- `go_config_nodes` 캐시 추가 검증(1일) → **장애 원인이 아닌 것으로 확인**.
- `deptMember` 캐시 추가 검증(2일) → **캐시 추가 불가, 다른 방안 필요**.
- 메신저 조직도 싱크 로직 개선(4일) → **"조직도 트리 관계상 최하위가 변경되면 모든 상위 부서를 반환해야 하는 제약"**이 있어 변경분만 보내는 방식으로는 한계가 있었다. (이 메모가 나중에 사건 B에서 "변경분 대신 항상 전체"로 간 씨앗이다.)
- 그래서 추가 일정으로 "DeptMember·User 관계 Lazy", "DeptMember·Department 조인 쿼리 불필요 요소 제거"를 넣었다.

커밋 순서로 보면:
1. `86c1e3ce598` (2023-05-25) — `users/changed` 전용 경로. 메신저용 변환 `convertUserToMessengerUserChanged`를 새로 만들어 부서원 컬렉션 로딩을 뺐다. `User`에 2차 캐시 1줄, `idx3_go_users(updated_at)`.
2. `904d25f5c95` (2023-06-14) — `DeptMember.user`를 LAZY로, 부서원 setter에서 소속 부서의 `dirty()`를 불러 부서 `updated_at`을 올리게 했다. 그러면 부서 변경분 조회에서 부서원 조인을 뺄 수 있다. `idx1_go_dept_members(department_id)`.
3. `f24a8b92c22` (07-31) — 설정 조회 `readOnly=true`.
4. `c7aed5f0a9a` (08-04) — `/departments/children/changed`: 바뀌었는지만 boolean으로 답한다. 주석이 당시 생각 그대로다: "메신저 로직: 조직도 변경사항이 있는가? → 전체 조직도 호출 / 없다면 로컬 스토리지 데이터 사용". `idx1_go_departments(company_id, updated_at)`.
5. 08-31 ~ 09-05 — 인덱스 DDL 정리(`using btree` 제거, `IF NOT EXISTS` 제거).

같은 사건의 다른 원인 후보였던 **근태 동기화**는 2차로 따로 팠다(엑셀 `조직도 근태 동기화`, 2차 개발 계획 C44). 원인은 (1) `TimelineOneDay`를 조회하다 없으면 생성하는 로직 때문에 트랜잭션이 `readOnly=false`, (2) 자기 상태가 바뀔 때마다 전 사원 Circle 검사, (3) `go_users WHERE id IN (...전 사원)` + `go_timeline_one_days WHERE user_id IN (...전 사원)`. DBA와 같이 보고 "전 사원 IN을 `company_id` 조건으로 바꾸면 효과 있음"을 확인했다(H58). `3cded0178d4` (2023-08-08)가 그 작업이다: `TimelineOneDayNotifier`의 `em.flush()`와 전 사원 로딩 제거, `getUsedCount()`, `findOrCreateOneDay` → `findOneDayToday`(조회만), 회사 단위 조회. **하지만 이 브랜치(`feature/GO-44222_근태_동기화_개선`)는 develop에 머지되지 않았다.** 같은 아이디어가 develop에 들어간 것은 2024-04 `f143c382d99`(사건 E)다.

### 최종 결정과 대가
- 결정: 구조(변경분 조회)는 그대로 두고 쿼리·로딩·인덱스만 고쳤다. 메신저 전용 변환기로 범용 변환을 건드리지 않았다.
- 대가: `dirty()`는 setter를 거치는 변경만 잡는다. 벌크/native update로 바뀌면 부서 `updated_at`이 안 오른다. 그리고 여전히 사용자마다 rdate가 달라 결과를 공유할 수 없다. 이게 1만 명에서 다시 터진다(사건 B).
- 결과(엑셀 `조직도API 성능 측정`, nGrinder): 부서 API는 개선 전 25 vuser에서 TPS 0.7(요청 181건) → 개선 후 25 vuser에서 TPS 8(요청 1,979건). 유저 API는 80 vuser 평균 3.16초 → 1.34초(TPS 4.0 → 4.5). 운영 클라우드 비교(`v2` 시트)에서 유저 API는 고객사별 21~44% 감소, 부서 API는 거의 변화 없음(-25% ~ +5%).

## 3. 사건 C — 부하를 걸면 대화방 API가 커넥션 풀을 먹었다 (2023.11~2024.3)

> **3줄 요약**
> - 부하 중 1초 이상 걸린 API 대부분이 대화방 API였고, 커넥션 풀 장애를 같이 일으켰다. 대화·알림 목록은 `count(*)` 슬로우 쿼리가 있었다.

> - openfire 플러그인 인터셉터에서 `jabber:iq:roster` get을 거부하고, presence는 PC 리소스로 가는 것만 통과(화이트리스트)시켰다. 18:00~18:10 openfire CPU 평균 36.6% → 7.5%, 최대 82% → 14%.

### 그때 뭘 하고 있었나

### 뭐가 터졌나 (GO-45372 이슈 본문 — 사용자 제공, 엑셀 `장애 발생` 시트)

### 코드를 열어보니 (그리고 그 전에 힙 덤프)
엑셀 `장애 발생`에 분석 흔적이 남아 있다.
- openfire 캐시 튜닝: ClientSessionInfoCache 0.25MB → 367MB, Roster MaxLifetime 30분 → 4시간 등. openfire 4.5.3 버전 메모리 이슈를 igniterealtime 포럼·이슈 트래커에서 찾아봤다(OF-2245 "힙 덤프 로그랑 동일한 문제").
- "힙 덤프를 보니 rosterItem이라는 곳에서 메모리를 다 잡고 있다. 하지만 관리 모니터링에서는 해당 캐시가 잡히지 않는다."
- 두 번째 힙 덤프: "11,300개가 나온다 — 클라이언트에서 연락처 목록을 요청하는 것이다. 이게 많이 요청해서 부하가 생기는 건가?"
- "presence 패킷을 차단하니 다른 곳에서 누수가 되는 것 같다." "원인은 모르겠지만 1초 내에 null → 유저로 엄청 많이 쏜다."
- 아이폰·안드로이드 패킷을 캡처해 비교했다(엑셀 A235, A244).

이슈 본문의 원인 정리: notifier GC가 CPU를 과점(코어 부족) → Web이 쓸 CPU 부족 / 모바일 접속마다 roster 요청 → 1만 명 반환 / 아이폰 요청에 JID 리소스(ios) 누락 → routing table 탐색 중 메모리 과점유.

코드로 보면 기존 `PresenceInterceptor`(`713ec09e414^`, 원저자 다른 사람)는 **블랙리스트**였다: "받는 쪽 리소스가 모바일·웹이면 거부, 리소스가 없으면 라우팅 테이블에서 bare JID로 세션을 찾아 다시 보냄". 아이폰 리소스에 `ios`가 없으면 모바일로 인식되지 않아 presence가 그대로 통과한다.

### 처음 시도와 그게 안 된 이유
- 임시 대응(이슈 본문): presence 패킷 차단(6/13), 12 → 36 vCPU·heap 8G → 16G 증설(6/14). 엑셀 메모 "presence 패킷을 차단하니 다른 곳에서 누수" — presence만 막아서는 안 됐다.
- **`713ec09e414` (06-20) "iq-roster 패킷 차단 + 라우팅 로직 제거"** — 이름을 `GoCustomInterceptor`로 바꾸고, IQ get + roster 네임스페이스를 거부. presence는 "PC 리소스가 아니면 거부"로 바꿨는데, `isPcResource(null)`이 false라 **리소스 없는 presence가 전부 버려졌다**(PC 메신저 상태 표시까지 끊길 수 있는 버전).
- **`32110e63e42` (06-21) "블랙리스트 → 화이트리스트"** — 리소스가 있으면 PC만 통과, 리소스가 없으면 라우팅 테이블에서 PC 세션만 골라 다시 보내고 원본은 거부. 재전달 대상 판정도 "모바일·웹 아님" → "PC임"으로 바꿨다.

### 최종 결정과 대가
- 결정: 서버 소스를 고치지 않고 openfire가 모든 패킷마다 부르는 인터셉터(플러그인)만 바꿔 배포. 조직도는 메신저가 HTTP API(사건 B 캐시)로 받으므로 XMPP roster가 필요 없다는 전제로 roster 요청 자체를 막았다. 열거한 것만 막는 블랙리스트 대신 PC만 통과시키는 화이트리스트로, 리소스 누락·새 리소스 종류를 같이 막았다.
- 대가: roster 거부는 모바일만이 아니라 리소스 구분 없이 전부다. 아이폰 리소스 누락의 근본 수정은 모바일팀에 넘겼다(PDF). 이 패치는 고객사 버그픽스 브랜치로만 배포됐고 2024년 당시 develop에는 안 들어갔다. 재전달 루프가 같은 패킷 객체의 수신자를 바꿔 가며 보내는 문제는 2026-11-03에 develop으로 cherry-pick하면서 `createCopy()`로 고쳤다(`afd30758608`, 테스트 7건).

### 사건 E (근태 표시)
17. **8,000명 기준의 출처가 두 개다.** — 사용자 확인은 "9시 출근 6,500명 + 여유 20%", 엑셀 진행 일지는 "근태 OFF 8,000/600초 CPU 62%로 서비스 가능 → 기준 8,000명". 둘 다 맞는지, 면접에서는 어느 쪽으로 말할지. (같은 조건이 측정 시트에는 CPU 70%로도 적혀 있다.)
18. **중간 보고의 "근태 API 약 30초 → 1초로 줄였지만 장애 동일"은 2023-12 GO-44222(근태 캐시 `feff2d34efe`) 결과인가?** — 2차 시트의 "sync 28초 → 0.6초"와 같은 측정인지 다른 측정인지 구분이 안 된다.
19. **고객사가 실제로 relay(`timeline.display.relay=true`)를 켰나?** — 리서치 노트에 "운영에서 고객이 켰는지는 모름". 또 relay 쿼리의 `TO_DATE(..., 'YYYY-MM-DD hh24:mi:ss')`는 PostgreSQL에서 시각이 버려질 수 있다(`13580e920cc`). 운영 PG에서 relay가 실제로 변경분을 보냈는지.
20. **timeline 푸시의 모바일 failover를 끈 이유(`95616fd95a9`)는?** — 커밋에 이유가 없다. 엑셀 1차 원인 후보 "불필요한 FCM 호출"과 연결되는지.
21. **PDF "XMPP 일괄 발송 → 응답 + 스케줄러 방식" 표현** — 코드는 XMPP를 유지하고 "출근 건별 전원 발송 → 회사별 1분 묶음 발송 + 화면 진입은 API 응답"이다. 문구를 고칠지.

### 사건 F (18시 장애)
22. **패치 날짜가 맞지 않는다.** — 이슈 본문은 "커스텀 패치 6/18 22시", 커밋은 `713ec09e414` 6/20, `32110e63e42` 6/21. 6/18 배포본은 무엇이었고, 운영에 최종 올라간 건 어느 버전인가. `ㅁㅁ.xlsx` openfire 18일/19일 비교가 6/18 패치 전후라면 19일 측정은 6/20 커밋 이전 빌드다.
23. **PDF "리소스 누락 요청 Reject"** — 최종 코드는 리소스 없는 presence를 PC 세션에만 다시 보내고 원본을 거부한다. 단순 Reject는 첫날(`713ec09e414`) 버전뿐이다. 첫날 버전이 운영에 나갔다가 PC 상태 표시 문제로 다음 날 고친 것인지.
24. **roster 요청 거부가 PC 메신저에 영향이 없었나?** — 커밋 제목은 "모바일 iq 차단"이지만 코드는 리소스 구분 없이 모든 `jabber:iq:roster` get을 거부한다.
