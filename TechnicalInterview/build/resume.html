소개

부하 테스트로 병목을 찾아 구조를 바꿔 해결해 온 백엔드 개발자입니다. 그룹웨어 서비스에서 고객사 장애 대응과 대형 고객사 성능 안정화, Java 메일 스토어 구축, 그룹웨어 3.0(VM 모놀리식) → 4.0(Kubernetes) 데이터 마이그레이션을 거쳐 지금은 그룹웨어 LLM 에이전트 서비스를 운영하고 있습니다. 다른 사람들이 어려워하는 문제를 맡아 원인을 끝까지 파고들어 해결하는 일을 좋아합니다.

주요 성과

  • AI 에이전트 — 부하 시 DB 커넥션이 모두 끊기던 대화 상태(체크포인트) 저장 구조를 재설계해 3,000VU 부하에서 DB 오류 0건
  • 데이터 마이그레이션 — 고객사를 나눠 담는 서비스 클러스터 9개, 총 약 200TB 첨부를 GCS로 옮기는 Airflow 파이프라인 주 개발, 미이관 0.2%는 모두 사용하지 않는 파일
  • 메일 스토어 — 기존 C 기반 메일 스토어를 Java·Spring으로 재구축해 4.0 메일 스토어로 도입(클러스터마다 2대)
  • 성능 안정화 — 1만 명 고객사 출근 피크 기준 8,000명 / 10분 부하 테스트에서 근태 표시(메신저 출근 상태) ON 시 장애(CPU 85%) → 정상(CPU 71%)

체크포인트 저장 구조 재설계 2026. 7 ~ 8

  • 문제: 부하 테스트 시작 약 6분 만에 PostgreSQL이 모든 파드의 커넥션을 끊음. checkpoint_blobs가 27GB까지 늘어 디스크가 가득 찼고, DBA가 현재 구조로는 운영할 수 없다고 반려
  • 원인: 요청마다 체크포인트를 새로 쓰고 끝나면 바로 삭제하는 구조. 단계마다 대화 전체를 다시 저장해 턴당 102MiB가 쌓였고, 첨부 base64까지 체크포인트에 실림
  • 1차로 종료 시점에 1회만 저장하도록 바꿔 턴당 102MiB → 18.5MiB로 줄였으나, 쓰고 지우는 구조가 남아 DB가 다시 멈춤
  • 2차로 일반 요청은 프로세스 메모리에만 두고, 승인 대기로 멈춘 요청만 PostgreSQL에 저장해 다른 파드에서 재개하도록 변경. 파드 종료 시 graceful shutdown(최대 120초)으로 진행 중인 요청을 마저 처리
결과부하 중 DB 커넥션 끊김 해소: 개선 후 3,000VU 부하에서 DB 오류 0건. 일반 요청의 체크포인트 DB 작업 7건 → 0건(승인 대기 요청만 저장)

부하 테스트로 계층별 병목 확인

  • agent만 보던 측정을 진입점(stream)까지 넓혀 게이트웨이(2파드) 포화를 확인하고, stream → agent 직접 연결로 게이트웨이 병목 제거: 응답 헤더 3.2초 → 22ms, 5xx 14.1% → 0%

ai-file(첨부 파싱·지식 색인) 메모리 개선

  • 부하 테스트 중 발생한 OOM의 원인(glibc mmap 임계값, MuPDF store)을 찾아 메모리 989MB → 280MB
  • PPTX 읽기 요청에서 지연의 89%를 차지하던 불필요한 재압축을 제거해 1.8~3.5초 → 중앙값 약 1초

ai-automation 실행 구조 재설계·구현

  • DB 테이블을 큐로, PG NOTIFY를 신호로 쓰던 구조를 RabbitMQ 중심으로 재설계·구현. 기존 구조는 지연 재시도·TTL·DLQ를 앱 코드로 다시 만들고 있었고 대기량을 관측할 수 없었음
  • start / continue 큐와 DLQ, DB 커밋 후 발행, 같은 요청 재호출에도 안전한 멱등 처리, 세대 번호로 늦게 도착한 메시지 차단
  • Redis 전역 슬롯과 회사 단위 라운드로빈으로 동시 실행 상한과 회사 간 공정성 관리

  • 업로드 후 GCS API로 존재·크기 검증, {회사}/{날짜}/{파일} 경로 매핑과 디스크 병합 시 경로 충돌 자동 교정

2024. 7 ~ 2025. 6
개요
디스크 확장 한계로 메일 원문 저장소를 로컬 디스크에서 GCS로 옮기면서, 기존 C 기반 메일 스토어를 Java로 재구축
역할·범위
외주(C 개발 경험)가 메일 API 요구사항과 전체 아키텍처를 설계. 본인은 C 중심 설계를 Java·Spring 구조에 맞게 재설계(Apache James 참고)하고, 사용자별 SQLite 커넥션·트랜잭션 구조와 메일 append 수신을 개발. 개발을 마친 뒤 더 급한 3.0 → 4.0 데이터 마이그레이션에 차출되어 운영·유지보수는 다른 담당자가 이어받음
기술
Java, Spring, Netty, MyBatis, SQLite (FTS5), GCS
  • 사용자마다 개인 SQLite 4종(메일 인덱스·대용량 첨부·수신 확인·웹폴더)을 쓰고, TCP 채널마다 대상 사용자가 다른 구조
  • 커넥션 컨텍스트가 DB 종류별로 필요할 때만 열고, 없으면 스키마를 생성. Netty 채널에 묶어 재사용하고 다른 사용자 요청은 차단
  • Spring 트랜잭션 방식을 자체 AOP + ThreadLocal로 구현해 여러 SQLite DB를 함께 begin·rollback. 쓰기는 시작부터 EXCLUSIVE 락으로 순서를 세움
  • append 수신: 헤더 → continuation → 본문을 파일로 스트리밍해 대용량 메일의 메모리 부담을 줄이고, 수신 실패 시 받던 파일 정리

기술
Java, Spring, JPA, MyBatis, Ehcache (Terracotta), JMeter, Scouter
