## 사건 1 · 중단·실패해도 다시 돌릴 수 있는 첨부 이관 파이프라인 (공유형)

> **3줄 요약**
> - 클러스터당 약 20TB(총 약 200TB) 첨부를 VM 디스크에서 GCS로 옮겨야 했다. 오래 걸리는 곳은 70시간이 넘었고, 중간에 멈추면 어디까지 됐는지 알 수 없었다.
> - 처음엔 `gsutil -m cp`로 묶어 올렸는데 파일 1개짜리 묶음에서 멈췄다. 그래서 GCS를 FUSE로 마운트해 `cp -n`으로 복사하는 쪽으로 바꿨다. 성공 여부는 cp 결과가 아니라 GCS API로 다시 확인한 존재·크기로 판정했다.
> - 파일마다 상태를 `storage_mapping`에 기록해서, 다시 돌리면 남은 것과 실패한 것만 처리하게 만들었다. 최종 미이관 0.2%는 사용하지 않는 파일이라 대상에서 뺐다.

### 1-1. 그때 뭘 하고 있었나
2025년 6월에 합류했을 때 첨부 이관에는 mjpark가 2025-03에 만든 프로토타입이 있었다(`storage_migration_dag.py`, `storage_upload.py`, `storage_retry.py`, `storage_validate.py`).
- `storage_mapping` 테이블: 파일별 `execute_flag`, `execute_count`, `success_flag`, `metadata_success_flag`, `result_message`
- 업로드: 회사·앱 단위로 파일 목록을 모아 `sudo -S gsutil -m cp 파일들... gs://버킷/` 한 번 호출(`73ae2a55` 시점 `storage_upload.py`)
- 재시도 상한 2회(`c98dd6cd` "재실행 횟수 2 미만")와 content-type 패치

7월 초부터 나는 이걸 다우오피스용(`tasks/do/`)과 경리회계용(`tasks/acc/`)으로 나눠 사실상 새로 짰다. 커밋 순서는 이렇다.
- 2025-07-01~14: "mapping table dag / sync / 기본 툴"
- 07-15~18: "gcs upload", "gcs upload validate 추가"
- 07-22: "acc 추가"
- 07-24: "task 병렬처리 분리 bucket -> company_uuid변경"

`storage_tasks.py`는 2025-07-22 `6dca6632`에서 처음 생겼다.

### 1-2. 뭐가 터졌나 / 무엇이 어려웠나
- 규모: 클러스터당 약 20TB, 총 약 200TB. 오래 걸리는 클러스터는 70시간 이상 걸렸다. 이 수치는 사용자 제공이고 코드·커밋에는 없다.
- **2025-07-29 `83327553` "단일파일 gsutil -m 옵션시 무한로딩"**: 묶음에 파일이 1개뿐이면 `gsutil -m cp`가 끝나지 않았다. 덱에는 "대용량 단일 파일"이라고 적었지만 커밋 메시지에 '대용량'이라는 말은 없다. 수정 코드도 분기 조건이 `len(file_paths) == 1`(파일 개수) 하나뿐이고 크기 조건은 없다. 기록상 맞는 표현은 "파일 1개짜리 묶음"이다.
- 중간에 멈추면 어디까지 됐는지 알 수 없었다. 프로토타입은 gsutil이 실패하면 stderr를 로그 파일로만 남기고 `execute_flag`를 일괄 갱신했기 때문이다(`storage_upload.py` → `_update_execute_flag`).
- 업로드 성공과 메타데이터 반영 성공이 따로 놀았다. 파일은 올라갔는데 content-type이나 custom_time 패치가 실패하는 경우가 있었다.
- 여러 VM 디스크를 합쳐 마운트하면서 같은 GCS 경로로 가는 파일들이 생겼다(1-4 참고).

### 1-3. 코드를 열어보니
- GCS 경로 규칙은 `sql/storage/sync_all_mapping.sql`의 CASE 문에 있다.
  - `gcs_path = {company_uuid}/{YYYYMMDD(upload_at)}/{random_name}` (28~36행)
  - `dest_bucket_path = {app_code}/{company_uuid}/{YYYYMMDD}` (45~53행)
  - 버킷은 앱 코드별(`APP_CODE_MAP`, `dags/storage/common/constants.py`)
  - `random_name`은 원본 경로의 8번째 조각이다: `split_part(replace(path,'//','/'),'/',8)`, 67행
- 그래서 디스크를 합친 결과 회사·날짜·random_name이 같은 파일이 둘 이상 생기면 GCS에서 서로 덮어쓰게 된다.
- `app_code='NONE'`인 파일(어느 서비스에도 매핑되지 않는 파일)은 `dest_bucket_path`가 NULL이라 업로드 대상에서 빠진다(`storage_tasks.py:35`, `:149`).

> **3줄 요약**

  ```python
  query_list.extend([x.strip() + ';' for x in query_content.split(';') if x.strip()])
  ```

## 사건 9 · 단독형: 실물 파일 확인이 스케줄러를 끊다 — NFS hang (2026.6)

> **3줄 요약**
> - 업로드가 안 끝난 첨부의 원본이 디스크에 실제로 있는지 확인하는 태스크가 순차로 돌았다. 너무 오래 걸려 스케줄러 heartbeat가 끊겼다.

> - NFS가 응답하지 않으면 파일이 "없다"고 잘못 세지 않고, 타임아웃 건수가 1 이상이면 태스크를 실패시킨다.

  - SQL에서 `regexp_split_to_array` CTE를 빼고 `split_part` CASE로 바꿨다.
  - `ThreadPoolExecutor(20)`을 도입했다. 커밋 본문: "스케줄러 heartbeat 끊김 방지"
- `e08eb56c` 06-09 10:39 "첨부 예외 추가": ThreadPool 제거, 순차로 복귀
- `36f28ec3` 06-09 11:25 "파일 nfs": `_safe_isfile()` = `subprocess.run(['test','-f',path], timeout=10)`. 반환값은 True / False / None(타임아웃).
  ```python
  if timeouts > 0:
      raise RuntimeError(f"NFS 무응답으로 {timeouts}개 파일을 확인하지 못했습니다. NFS 복구 후 재실행하세요.")
  ```

- 대가: 순차라서 느리다(파일마다 프로세스를 하나씩 띄움). 덱의 "20 스레드 병렬 + 10초 타임아웃"은 최종 코드와 다르다. 최종은 순차 + subprocess 격리 + 10초 타임아웃이다.

- **컷오버 당일 역할(마이그-16):** DAG 실행은 전부 본인. 순서대로 직접 실행하고, 쿼리 변환이 실패하면 해당 서비스 담당자에게 알려 고친 뒤 재실행. 메일 이관은 메일 담당자, DB 복제·4.0 기동은 DAG가 아님, 이관 후 후속작업·개발자 검증은 서비스 담당자(공유형 기준). 단독형에서는 후속작업도 본인이 했다.
- **공유형 vs 단독형 차이:** 공유형은 서비스 담당자 약 10명과 함께 Airflow 구조와 서비스 쿼리를 만들었다. 단독형은 서비스 담당자 없이 3명이 전부 진행(쿼리 수정만 담당자에게 요청). 단독형에서 본인 주 작업은 그룹웨어 서비스 이관(ID 채번 변경 등 추가 작업)과 이관 정책·연동·후속작업 플로우 자동화.
- **네트워크(마이그-24):** 실제 이관은 SSH 터널 방식(황규연님 `0957ec5d` 08-10, `f3176c3c` 08-17 "항상 터널"). 본인의 master 콜백 방식(`de61556c`·`8650791d` 08-14)은 미머지. 본인 작업이 아니라 포트폴리오에서 제외.
- **실물 파일 확인의 목적(사건 9, 마이그-25·28):** 단독형 고객사 첨부를 복제해 우리 Airflow 환경으로 가져와야 했는데, 인프라에서 이 절차가 빠지면 실제로는 파일이 이관되지 않는다. 그래서 그때는 태스크가 멈추도록 확인 단계를 넣었다. NFS 무응답을 "파일 없음"으로 세지 않고 실패시키는 것도 같은 이유.
- **Ingress rewrite(마이그-19, 2026-11-07):** 원인을 찾아가는 길목 중 하나. rewrite 때문에 요청 URL과 CalDAV 응답 href가 달라져 오류가 났고, rewrite 때문에 일부 요청은 서버까지 가지도 못했다.
